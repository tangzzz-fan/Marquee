### ticket 10 修复：放大镜不跟随鼠标（用户实测反馈）

用户报「放大镜没有跟随鼠标移动」。根因是**两处叠在一起**：

1. **判定把两件事混成了一件**：原文是「取样像素没变 → `return`」，
   而"取样像素没变"不等于"什么都不用做" —— 光标位置仍可能变了。
   后果是**盒子留在原地**（1x 屏上尤其明显，2x 屏上间歇性卡住）。
2. **改了状态但没推出去**：`updateMagnifier` 只改 `magnifier` 字段，
   "推给视图"交给调用方顺手调 `refresh()`；而空闲移动走 `updateHover`，
   那里"悬停窗口没变"时**直接 `return`** → 落点之后与悬停在同一窗口内时，
   压根没有任何东西会去推。拖拽中反而是好的（那条路径有 `refresh()`）。

修法：
- 新增 `MarqueeCore.MagnifierTracker` + `Update`（`idle` / `moved(box)` / `resample(box,center)`），
  把三态判定抽到 Core 单测；**换屏也必须重采**（同一像素坐标在两块屏上是两个地方）。
- 控制器改为**谁改谁推**（`pushMagnifier`），并在 `.moved` 时复用已放大的小图只挪盒子。
- `clearMagnifier()` 同时清展示与跟踪状态（只清前者会留下"跟踪器还记得取样点"的中间态，
  下次光标回到同一像素时被判成 `idle`，放大镜再也回不来）。
- 顺带修：`statusText` 烘进 presentation，只 `refresh()` 推的是旧那份 →
  「已复制 …」要等下次移动鼠标才出现；改为重建 presentation（J11）。
- 顺带：长截图抓帧期间**不再显示放大镜**（像素是滚动前冻结的，滚起来后与屏幕无关）。

测试：189 + 6 = **195 全绿**（新增 8 条跟踪器测试）。变异测试分别单独注入两处
（`sameSample → idle`、忽略 `lastBox`）→ 各自被 3 条测试抓住。
验收清单新增 J8–J11。教训写进陷阱 35/36。

| `gap` | 18 | 22 |

### ticket 10 去锯齿（第二轮反馈）

用户：「放大镜的锯齿感还是有点严重」。两个来源：

1. 插值写死最近邻 —— 3 倍时一个源像素只有 1.5 点，斜线的阶梯边就是锯齿。

3. 顺带：盒子边长改由**实际采样边长**推出（`boxSide(sampledSide:zoom:backingScale:)`），

**关键认识（写进陷阱 38/39）**：视图里 `interpolationQuality` 只在非 1:1 时起作用，

### 分辨率支持的现状梳理（用户提问，未改代码）

问「目前如何支持 retina 与更高分辨率」。结论：**只有 `DisplayGeometry` 一个换算点**，
其余全部从它派生，没有任何硬编码的 `2`：

- 采集：`ScreenCaptureKitCapturer` 显式设 `width/height = display.pixelSize`（点×scale）、
  `captureResolution = .best`、`scalesToFit = false`；区域采集的 `sourceRect` 给**点**、输出给**像素**。
- `backingScale` **刻意不用** `NSScreen.backingScaleFactor`，而是 `CGDisplayMode.pixelWidth / width`
  （`SystemDisplayLocator`）—— 缩放分辨率下两者会不一致，采集关心的是像素/点的真实比例。
- 交互全在点上：覆盖层是逐屏 `NSPanel(contentRect: screen.frame)`，AppKit 自己按 backing scale 光栅化；
  放大镜按 `backingScale` 做点→像素，且盒子落位对齐设备像素。
- 跨屏混合 DPI：输出 scale 取**参与屏里最大**的，逐片按**边**取整（不会出现 1 像素的缝/重叠）；
  1x 屏的内容被放大（不丢信息）。测试覆盖 1x+2x 混合。
- 导出：单切片**直通不重绘**；编辑器画布永远持全分辨率图，`viewport.scale` 只影响显示；
  标注存**图像像素**，所以导出像素精确。

**发现一处与注释意图不符的地方（未改，待用户定）**：
`AnnotationRasterizer` 里 `CGColorSpace(name: .sRGB) ?? cropped.colorSpace ?? …` ——
sRGB 在链首且永不为 nil，所以**恒为 sRGB**，而注释写的是"保留来源色彩空间"。
后果：P3 屏的截图导出时会做一次 P3→sRGB 转换（超出 sRGB 色域的颜色被裁），
与屏幕上看到的略有差异。修法是把 `cropped.colorSpace` 提到前面（与 `ImageCompositing` 的做法一致）。

**其它已知空缺**：缩放 HiDPI 模式拿到的是渲染缓冲分辨率（如 3200×1800）而非面板原生 3840×2160
（与系统截图一致）；>2x 逻辑上走通但没有硬件可验；HDR/10-bit 未设置（8-bit BGRA，HDR 会丢）。


### ticket 09：马赛克 / 毛玻璃 + 裁切（编辑器三件套齐了）

**打码**走 CoreImage（`CIPixellate` / `CIGaussianBlur`，typed filter API）、
`AnnotationKind.mosaic` / `.blur`、强度在 `AnnotationStyle.effectStrength`。
`CIContext` 是**共享常量**：冷启动 46 ms 是建上下文 + 编译着色器，
**预热后 400×300 补丁实测马赛克 0.70 ms / 模糊 0.81 ms**（ticket 目标是 ≤ 5 ms）。

1. **补丁贴回时要局部反翻 CTM** —— 当前 CTM 已是"左上原点、y 向下"，
   `draw(image, in:)` 在那种上下文里会把图上下颠倒。
2. **打码缓存在 `onChange` 里重算**，不能在 `Canvas` 绘制闭包里改 `@State`（SwiftUI 禁止）。

**这次最值得记的两条测试教训（都靠变异测试才发现）**：

  这是"纯色图看不出翻转"的变体：**对称的测试图同样是盲的**（陷阱 40）。

验证：263 + 6 = **269 全绿**（新增 26 条）。变异测试注入 7 处 → 全部被抓住

## "EditorDemo 编译不通过"：根因是工程文件没同步（已根治）

用户报 `EditorDemo` 编不过。我这边 `xcodebuild` 完全跑不起来（宿主沙箱，见 DEV-NOTES 4.1），

上一次生成是 13:14 —— **早于**新文件。`scripts/build.sh` 会跑 `xcodegen generate`，
但 **Xcode 的 Run 不会**，它只读当前的 `.xcodeproj`。所以从 Xcode 跑就报
`cannot find 'EditorDemo' in scope`，而且**报在调用方**（`MarqueeAppDelegate`），
看起来像新文件写错了。

**根治**：`App/Sources` 从逐个列出的 `PBXFileReference` 改成 Xcode 16+ 的
**文件系统同步组**（`type: syncedFolder` → `PBXFileSystemSynchronizedRootGroup`）。
目录本身挂进工程，以后增删源文件不需要重新生成。改动前备份了工程文件，
生成后用 `xcodebuild -list` 验证工程可被解析、并核对了同步组的挂载路径
（`App` group → `Sources`，即 `App/Sources`）与 target 的 `fileSystemSynchronizedGroups`。

记进 `DEV-NOTES.md` 2.2 + 陷阱清单第 41 条。

- `SelectionOverlayController.runAutoScrollLoop`：与手动模式同一种"被宿主逐拍驱动"的写法

**三个刻意的决定**：①"到底"看**长图高度有没有增长**（连续两步无新内容），不复用会话的提示；

（`docs/PITFALLS.md` 55）：

`AnnotationEditorWindowController.init` 里先 `NSWindow(contentRect: 960×680)`，
紧接着 `contentViewController = NSHostingController(rootView:)` ——
**`contentViewController` 的 setter 会按 SwiftUI 视图的 `fittingSize` 重排窗口**，
而画布用的是 `GeometryReader`（**没有固有尺寸，ideal size 就是 10×10**）。
结果：init 里给的 960×680 被覆盖，窗口缩成"工具栏那一条"。

这个坑的症状和"窗口没弹出来"**完全一样** —— 窗口确实创建了、也叫到前台了，
只是面积几乎为零。修法是设完 `contentViewController` 之后补一次 `window.setContentSize`。

另外把整条链路的日志补齐了（截屏请求 / 权限门 / 覆盖层呈现 / 采集结果 / 打开编辑器），
这样用户跑一次就能定位断点：
**"打开编辑器：W×H" 出现而窗口看不见 → 100% 是窗口呈现问题；不出现 → 链路在前面就断了。**

### 用户的日志定案：不是窗口的问题，是 `⏎` 根本没生效

用户贴回的日志（关键就四行）：

```
截屏请求：屏幕录制权限 = granted
权限放行，呈现覆盖层
覆盖层已呈现（mode=singleShot）
选区已取消                      ← 只有这一条，没有"截图完成"
```

**`⏎` 那一步没有任何痕迹，只有 `Esc` 的取消。** 一读代码就明白了 ——
覆盖层的键盘有**两条路**：

| 键 | 走哪条 | 依赖什么 | 实测 |
| --- | --- | --- | --- |
| `Esc` | `NSEvent.addLocalMonitorForEvents`（应用级本地监听） | 无（应用能收到事件即可） | ✅ 生效 |
| `⏎` / `⌘S` / 方向键 | 视图的 `keyDown` | 面板**是 key window 且视图是 first responder** | ❌ 完全没反应 |

而面板是 `.nonactivatingPanel`（刻意不激活本应用，免得把用户从当前应用拽走）——
"视图 `keyDown` 能收到按键"这条前提在真实使用中**并不成立**。
用户拖完选区按 `⏎`，什么都没发生；他只能按 `Esc` 退出；而他报上来的现象是
"**正常截图弹不出编辑器窗口**" —— 现象与根因隔了三层。

**这正是 `STATUS-AND-ACCEPTANCE.md` 里长期标着"这是覆盖层最没把握的一条"的 B1。**

**修法**：把覆盖层的全部功能键（`Esc` / `⏎` / `⌘S` / 空格 / 方向键）统一收进那个本地监听，
一条路走通就不要留第二条只在特定前提下成立的路。
（`NSEvent` 不是 `Sendable`，闭包只回传"消费了没有"，跨隔离域回传 `NSEvent` 编译不过。）

**这一轮的教训**：一个功能留两条输入路径、而其中一条只在特定前提下成立 ——
这是**最难查的一类**：出问题时另一条路（`Esc`）还是好的，
于是所有证据都指向"另一件事"（窗口没弹出来），而不是"键没收到"。
下次遇到"某个操作没反应"，先问一句：**它和那些能用的操作，走的是不是同一条路？**

### 修复被用户日志确认 ✅

这条链路上我连堵三个洞（窗口层级 / 窗口尺寸 / 键盘路径），**第三个才是用户真正撞上的那个**——
前两个是真的缺陷，但都不是本次现象的原因。教训：一次报三个"看不到"，
应该先要日志定位**在哪一步断**，而不是照着最像的假设去改。

## ticket 20（覆盖层浮动工具栏）实现完成

用户放行后开工，一次做完。

**代码落点**（沿用「Core 持编排、实现层只给绘制」）：

| 关注点 | 落在哪 |
| --- | --- |
| 位置计算 + 按钮几何 | `MarqueeCore.OverlayToolbar`（纯函数，11 条单测） |
| 绘制 | `SelectionOverlayView.drawToolbar`（AppKit，**与命中测试共用同一份几何**） |
| 命中拦截 | `SelectionOverlayView.mouseDown` —— 点在工具栏上就**不进入拖拽** |
| 动作 | `SelectionOverlayController.perform(toolbarButton:)` |
| 「要不要开编辑器」 | `Outcome.completed(_:openEditor:)` |

**几个刻意的决定**：
1. **绘制与命中用同一份几何**（都走 `OverlayToolbar.hitFrame`）。各算各的会偏几点，
   而那种偏差的表现是"按钮看着在这儿、点它没反应"，很难联想到是布局算错。
2. **工具栏在 `refresh()` 里统一挂一次**，不塞进"区域落点 / 窗口落点"每个分支 ——
   否则以后加第三种落点方式时一定漏一处。
3. **`openEditor` 做成显式关联值**，不是 controller 上的隐式状态 ——
   改枚举后编译器把 6 个调用点全列出来，一处都漏不掉。
4. **`mouseDown` 里拦工具栏**（而不是在 delegate 里拦），否则在按钮上按下再挪一下
   就会把刚框好的选区改掉。

**一个当场抓到的小错**：工具条宽度按"间距在两组之间"算，而按钮偏移按"间距在末尾"算 ——
差 4 点，最后一个按钮会探出右边一点。两条规则各自都对，凑在一起才错。
补了 `buttonsFitInsideToolbar` 钉住它。

验证：287 + 11 = **298 测试全绿**。变异测试注入 1 处（去掉"放不下就翻到上方"）
→ **3 条断言变红**。App 层 typecheck 退出码 0。

**`⏎` 的语义已经改掉**：普通截图不再打开编辑器窗口，直接出图。
工具栏三个按钮：`✓ 完成`（= `⏎`）/ `✎ 编辑`（过渡入口，覆盖层内标注能力要到 22 才齐）/ `✗ 取消`。
**长截图仍然进编辑器**（放不进一屏，没法在覆盖层里标注）—— 在 `finishScrollCapture` 里显式传 `true`。

STATUS 同步了：§3 开头加了变更说明，F1 拆成 F1 / F1b / F1c。
**PRD 的编辑器章节没动** —— 它和 ticket 23 的"编辑器去留"是同一处收口，放一起改，免得改两遍。










## ticket 21：覆盖层里就地标注（用户纠正了 20 的方案）

**用户原话**：「我的意思是实现我前面给你截图提供的一个工具栏 类似的效果，
**不是**使用一个编辑按钮跳转的方案」。

也就是说：20 那三个按钮（完成/编辑/取消）里，「编辑」这个**跳转到编辑器窗口**的过渡方案
被否掉了。要的是**工具栏本身就是标注工具条**，在覆盖层里直接画。

**改法**：`OverlayToolbar` 从 3 个动作按钮重写成 **18 格的完整工具条**（588×40 点）：

```
[▭][◯][↗][✎] │ [●×6 色板] │ [•×3 线宽] │ [↶][↷] │ [↓][✗][✓]
 矩形 椭圆 箭头 画笔          六色         三档     撤销 重做  保存 取消 完成
```

「编辑」按钮删掉，`wantsEditorAfterCapture` 随之变成死代码 → 一并删掉
（普通截图一律就地完成，只有长截图那条路显式传 `openEditor: true`）。

### 三个关键决定

1. **抽出 `AnnotationDrawing`（Core）**：覆盖层与导出共用同一份 CG 绘制。
   覆盖层把 CTM 平移 + 翻一次 y 之后就是同一套代码。反面做法（`NSBezierPath` 各画一遍）
   会让线宽/颜色空间/文字基线漂移，而且**只在某些图上看得出来**。
2. **标注用「选区局部点」存**，到像素只在栅格化那一刻换算一次
   （`InlineAnnotations.scaled(toPixelSize:)`，倍率由采集流程定 —— 它才知道最终像素尺寸）。
   ⚠️ 线宽/字号/打码强度**必须跟位置一起缩放**，否则 Retina 上导出的线细成一半。
3. **会话在 Core**（`OverlayAnnotationSession`）：工具 toggle、落笔/收笔、最小尺寸丢弃、
   撤销重做栈。放 `MarqueeOverlay` 就只能靠人手点，而"误点留下一个 1×1 脏点"
   恰恰最不容易手工复现。

### 当场发现并修掉的一个真缺陷

**带阴影的窗口截图比窗口矩形大一圈**，而标注坐标是相对窗口矩形算的 ——
差这一圈所有标注整体偏移，且偏移量随阴影大小变（浅色背景下阴影大）。
修法：**有就地标注时强制 `includeShadow: false`**。这是从坐标空间推出来的，不是试出来的。

### 验证

- **325 + 6 测试全绿**（新增 12 条会话用例 + 6 条工具条排布用例 + 5 条换算用例）
- **两轮变异**：
  - ① `isUsable` 的矩形阈值改成恒真 → 4 条断言变红 ✅
  - ② 组间间距 9 → 1 → **全绿通过** ❌ ← **测试盲区**
    原测试只断言"不重叠、不越界"，间距变小时照样成立。
    补了「组间间距必须明显大于组内间距」与「工具条必须放得进 1024 点的屏」
    两条**意图**断言，再注入才变红 ✅
- App 层 typecheck 退出码 0

> 教训（已进 PITFALLS 58）：**断言只写"不能违反的边界"是盲的。**
> 变异测试的价值就在这儿 —— 它证明的不是"代码对"，而是"测试真的在看着"。

## ticket 19：选区几何编辑与边缘吸附（用户早前点名要的那件事）

> 用户原话（更早一轮）："正常应该有对拖拽区域的大小编辑功能，我看到当前项目的 prd 还没有。"

补上：8 个控制点拖拽改大小、框内拖动移动整框、`⇧` 锁比例、边缘吸附（带提示线）。
**「输入精确尺寸」挪到 ticket 22** —— 它和文字工具卡在同一个前提上（覆盖层里要有输入框）。

### 为什么挪走而不是顺手做

覆盖层的键盘统一走控制层的**应用级本地监听**（PITFALLS 56）。有输入框在编辑时
必须**整条让行**，否则用户敲的字全被当快捷键吞掉 —— 而这件事本身是个未知项。
一个前提、两处用途（尺寸输入 + 文字工具），所以整体在 22 里做，不在这里各做一半。

### 落点

| 能力 | 在哪 |
| --- | --- |
| 控制点几何/命中/缩放/锁比例/吸附 | `MarqueeCore.SelectionGeometry`（纯函数，可脱机单测） |
| 拖拽分派 | `SelectionOverlayController.DragMode`（一个枚举替掉几个布尔量） |
| 吸附线来源 | `snapTargets()` = 屏幕可见区 + **与选区相邻的窗口** |
| 画控制点、画吸附线、光标 | `SelectionOverlayView`（`NSCursor.frameResize`，macOS 15+ 可用） |

### 几个刻意的决定

- **按下分派顺序「控制点 → 框内 → 框外」不能换**：调过来会出现"想拖角改大小、
  结果整框被挪走"，而两者看起来都像"生效了"。
- **基准矩形取「按下那一刻那一版」**，不是上一帧 —— 用上一帧会累积误差，
  且 `⇧` 锁比例会越锁越歪。
- **`⇧` 锁比例取"位移较大的那一轴"**：只看横向的话，往下拖得再多框也纹丝不动。
- **最小尺寸是"停住"不是"翻转"**：翻转看起来像"框突然跳到另一边"。
- **吸附线只取相关的窗口**（见下），且**只取一个方向里最近的一条**。
- **吸附画贯穿全屏的提示线** —— "可感知"是吸附能不能用的关键。
- **整框拖出屏幕时这一帧不动**：出屏后鼠标够不着，只能 Esc 重来。
- **拖几何时收起工具栏**（它贴着选区，会压住右下角控制点）；画标注时不收。

### 变异测试：一次"假阴性"暴露了方法论问题

| 变异 | 结果 |
| --- | --- |
| 去掉"最小尺寸停住" | ✅ 4 条断言变红 |
| `match` 的 `<` 改成 `<=` 并 `break` | ❌ **全绿通过** |
| x 方向改成"每条边各吸各的" | ✅ 3 条断言变红 |

## 回归修复：工具栏在框选之后不再出现（我引入的，已修）

用户报：「前面在框选完成后出现工具栏的，现在没有出现了」。

**根因（确定，不是猜的）**：
`beganDragAt` 里画选区时把 `dragMode` 置成 `.select`，而 `endedDragAt` 的 switch
**只给 `.stroke` 与 `.move/.resize` 两种情况写了收尾，`.select` 那条分支漏了重置**。
于是拖完选区后 `dragMode` 永远停在 `.select`；
而我在 ticket 19 里刚好加了一句 `if isEditingGeometry { return nil }` 到
`toolbarPresentationIfSettled()` —— `isEditingGeometry` 把 `.select` 也算成"正在拖几何"
⇒ 工具栏**永远返回 nil**。

**两层修法**：

1. **把那条依赖整个删掉**（关键）。工具栏贴在选区**下方 10 点**，控制点命中半径 6 点 ——
   两者根本碰不到，所以"拖几何时收起工具栏"这条规则**本来就没必要**。
   删掉之后这一整类 bug 不存在。
   （重画选区时工具栏本来就会消失：那时会话是 `.dragging`，`isSettled` 已经是 false。
   **判"会话状态"就够了，不要判"鼠标按着没有"。**）
2. **收尾只留一个 `defer`**，不在每条 `case` 里各自清 ——
   "每条分支各自收尾"这种写法，加第三种拖拽时一定会重演。

另外加了一条**交叉验证日志** `warnIfDragStateLeaked()`：
用一个独立事实（`NSEvent.pressedMouseButtons`）去对 `dragMode`，对不上就记 warning。
**只记日志不自动纠正** —— `pressedMouseButtons` 偶发不准的话，自动纠正会让工具栏
在拖动中闪一下，那比漏一条日志更难查。

> ⚠️ 这类 bug 的现象与"这个功能没做"**完全一样**。以后凡是"某个 UI 再也不出现"，
> 第一件事是查它依赖的标志位有没有哪条分支漏了收尾。（已进 PITFALLS 66）

**澄清**：已在主干上的 `8591d98`（ticket 21）**没有这个问题** —— 回归是完全在
ticket 19 那批未提交改动里引入的。用户跑的是带 ticket 19 的构建。

## ticket 22（部分）：覆盖层里加马赛克 / 模糊

用户要求：「工具栏中需要有支持马赛克的功能」。

### 难点：底图从哪来

覆盖层刻意不铺整屏截图（PRD 5.5）—— 屏幕内容是**穿透看到的真东西**，不在我们手里。
而马赛克必须拿到那块像素才能算。

**解法：复用放大镜那套冻结帧**（`LensFrameProviding` 在覆盖层出现时已经取过一屏）。
不额外采一次屏，也就不会因为"再采一次"把覆盖层自己拍进去。

### 三个关键决定

1. **预览的底图与导出共用同一套布局**：`OverlayRedactionSource` 复用
   `SelectionLayout` + `ImageCompositing`，而不是"从选区所在那屏裁一块"。
   自己裁在单屏下看不出差别，**跨屏时尺寸与对齐都会跟导出不一样** ——
   而马赛克看起来"差不多"，这种不一致极难发现。
2. **`AnnotationDrawing.sourceScale`**（底图每点多少像素）。它同时作用于两处：
   裁底图的像素矩形 **+ 传给滤镜的强度**（滤镜按底图像素工作）。
   漏掉第二处 → 2x 屏上预览的格子**小一半**，而"格子小了点"会被当成强度没调对。
3. **三档尺寸按工具换意义**（与编辑器同一套做法）：画图形 = 线宽（圆点），
   画打码 = 打码强度（方块）。**不新增控件** —— 工具栏每多一格就更宽
   （硬约束"放得进 1024 点的屏"，现在 652 点）。
   打码强度另立一组值 `AnnotationPalette.overlayRedactionStrengths = [4, 8, 16]` **点**：
   编辑器那三档单位是**原图像素**，直接复用会在 2x 屏差一倍。

### 拿不到底图时：说清楚，不静默

缺任何一块屏的冻结帧 → **整体放弃**（不给残缺底图，缺的那块会显示成原图、
看着像"打码没生效"）。此时预览不画打码，但**导出仍会应用** ——
所以提示行会说「⚠️ 打码预览不可用（没拿到屏幕像素）—— 标记仍然会写进成品图」。

### 验证：359 → 360 测试全绿（新增 13 条）

**最有价值的一条**：`previewMatchesExportPixelForPixel` ——
同一个标注、同一块底图，一边按像素画（倍率 1）、一边按点画（倍率 2），
两张 400×80 的图**逐点比亮度**。它同时钉住位置、格子大小、模糊半径三件事。

**两轮变异**：
- ① 无视 `sourceScale` → 马赛克 432 处 + 模糊 112 处不一致 ✅ 抓住
- ② 缺帧时改成 `continue`（交残缺底图）→ **全绿通过** ❌
  → 原因：原用例只有**单屏**，而单屏缺帧时 `ImageCompositing` 会因为
  "一片切片都没有"碰巧返回 nil。**测试是绿的，但没在测那件事。**
  补上跨屏缺一块的用例后立刻变红 ✅

> 变异没变红时，先问那个变异有没有产生用户可见的错误，再问**用例有没有覆盖到那条路径**。

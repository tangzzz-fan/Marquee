## 编辑器窗口：工具条即标题栏 + 尺寸单位分家（设计稿第 3 轮 B）

### 窗口

`1200 × 760`：**工具条即标题栏**（`.fullSizeContentView` + `titlebarAppearsTransparent` +
`titleVisibility = .hidden`）—— 那 48 点里放的是工具，而不是"标题 + 工具"两行，
省下的一行全给了画布。窗口底 `--c-bg`、画布（台面）`--c-inset`（比窗底再暗一档：
"图是亮的，桌子要比墙暗"）。

⚠️ **画布 690 不是稿子写的 688**：稿子按 48 + 688 + 22 = 758 算，而窗口 760 ——
差的 2 点是它把工具条的 1px 下边线与状态行的 1px 上边线**各算了一次**。
画布取剩下的全部（`EditorChrome.canvasHeight`），因为它才是这扇窗存在的理由。

⚠️ **窗口下限由 Core 算**（`EditorChrome.minimumWindowSize` ← `minimumToolbarWidth`）：
整条放不下时 `HStack` 的 `Spacer` 会先缩成 0、然后**最右边那几格被静默裁掉** ——
历史上真的发生过（用户报"OCR 入口我不知道在哪"）。整条 1146 点，窗口下限 1154。

### 工具条

分组顺序：**八个标注工具 ｜（分隔线）裁切 ｜ 色板托盘 ｜ 尺寸 + 读数 ｜ 缩放 ‖（空档）右簇**。
分隔线放在裁切前面是**刻意的**：它不改标注、改画布 —— 用线承认它不同类，
但不把它挪出工具组（判断 2：挪到缩放旁会把"有代价的破坏性操作"与"随手来回的视图控制"混成一堆）。

- **色板与尺寸从覆盖层的「样式」弹层搬进条上**（登记项）：编辑器停留最久，这两个是最高频控件，
  收进弹层等于每次多一次点击 ⇒ **编辑器因此没有「样式」格**。
- **尺寸芯片 54 × 38 + 常显读数**（数字 12 点 / 单位 10 点）。芯片画"细中粗"**不追真值**
  （88 px 的字装不进 38 高的芯片），真值交给读数 —— 那是"编辑器用原图像素"这件事的**唯一可见证据**。
- **文字预设改住弹层**（挂在文字格上，选中工具自动出现）：第一行因此**永不重排**（判断 3）。
  弹层里两段（文字 / 序号）+ 选序号时长出「从几开始」。
- 「撤销 / 重做」是全条**唯一允许变灰**的两格；识别文字带 Pro 小锁但**永不灰**。

### 尺寸单位分家（这一批的实质改动）

编辑器：线宽 4/8/16、打码 8/16/32、字号 36/56/88（**原图像素**）；
覆盖层：2/4/8、4/8/16、18/28/44（**点**）。
⚠️ 量出来**正好差 2 倍** —— 目标机器是 Retina，2x 就是两座表之间的桥：同一组视觉粗细，两套单位。
这条关系**写成了断言**（把两张表拴在一起：同值不行、错位也不行）。

`AnnotationPalette.lineWidths` 改名 `overlayLineWidths`（原先名字像共用的，而它只属于覆盖层）；
新增 `editorLineWidths` / `editorRedactionStrengths` / `editorFontSizes` + `editorDefaultStyle`。
⚠️ 编辑器原先进来点亮的读数是 **4 px**（最小那档）—— 因为它用的是 `AnnotationStyle.default`（覆盖层那套）。
顺带修掉一个**从来没被发现的错**：打码默认 12，而档位是 8/16/32 ⇒ **三个芯片一个都不亮**。

### 图标：一份来源

新增 Core `AnnotationIcon`：七种标注类型 + 选择 / 裁切 / 表情 + 动作格（撤销/重做/保存/✕/✓/识别文字/锁）。

### 识别文字面板：三态四张脸

260 宽、默认落**右下角**（阅读长图时目光最少停留的角）、距右下 16。
**「没有文字」与「识别失败」是两张脸**：前者安静（次要色、无红、**没有重试** ——
重试会得到同一个答案），后者红 + 警告三角 + 多一行「重试」。
「只读」标签常显（它是能力声明：能划、能 ⌘C，不是限制声明）。「4 行 · 41 字」告诉用户这段有多长。

### 键盘与状态行

## 用户报的 bug：录制快捷键时按「自己正用的那颗键」→ 设置无效 + 真的开始截屏

### 根因

Carbon 的 `RegisterEventHotKey` 是**系统级**的：它在按键送进本应用响应链**之前**就吃掉了它。
于是录制器（一个 `acceptsFirstResponder` 的自定义视图）收不到 `keyDown`，
而 Carbon 那边照常回调 `handler` ⇒ `performCapture()`，屏幕上真的浮出覆盖层。
最讽刺的是**用户最想按的恰恰是当前那颗键**（默认 `⌃Q`），所以一撞一个准。

### 修法

| 层 | 改动 |
| --- | --- |
| Core `ShortcutService` | 新增 `suspendForRecording()` / `resumeAfterRecording()`，**计数式**（`recordingDepth`）。`apply` 里把深度清 0 ⇒ 改键成功后那次收尾自然成空操作 |
| `ShortcutRecorderView` | 新增 `onRecordingChanged: ((Bool) -> Void)?`；`beginRecording`/`endRecording` 收成各一处；`update(combo:)` 也走收尾 |
| 设置页 / 引导页 | 各接一次：开始录制 → suspend，结束 → resume |

三个不肯踩的坑：

1. **恢复不能走 `apply`** —— 它里面那道独占探测一旦返回 `.conflict` 就**什么都不注册**。
   而"别的应用也占着同一个键"时非独占注册本来是成功的、共存在正常工作 ——
   挂起一次把它变成"被占用"，等于用一次探测把自己弄瘸。恢复只需 `register`。
2. **收尾不能只挂在 `resignFirstResponder` 上** —— 点窗口红叉时第一响应者不一定变
   （按钮不抢焦点）⇒ 挂起状态留下 ⇒ **全局快捷键彻底失灵且毫无提示**，比原 bug 更糟。
   故另加兜底：`viewDidMoveToWindow` 里挂 `didResignKey` / `willClose`。
3. **顺序**：录到键时先 `change(to:)`（它注册并清深度）**再**报"录制结束"。
   反过来会把同一组合注册两遍 —— Carbon 对同一进程内同一组合的重复注册返回
   `eventHotKeyExistsErr`，等于把刚设好的键弄坏。

**为什么用计数而不是布尔**：设置窗与引导窗**各有一个录制器**、共用同一个 `ShortcutService`。
布尔会让"先结束的那个"把全局注册提前装回来，而另一个还在录 ⇒ 同一个 bug 换个入口复发。

### 验证

Core 测试 +10（`ShortcutRecordingSuspensionTests`）：摘得掉 / 重复挂起只注销一次 /
两个录制器并存 / 装得回 / **恢复不做探测** / 当前键能重录 / 改键成功后不重复注册 /
改键失败仍装回 / 未挂起时是空操作 / `stop` 清深度。**Core 704 全绿 + BUILD SUCCEEDED。**

变异复验 **3 处全红**（`apply` 不清深度 / 恢复时插一次探测 / 去掉深度归零守卫）。
⚠️ 第一次变异只加了注释没删那一行，白跑一次 —— 与 PITFALLS 173 同源（变异要看住"真的改到了")。

PITFALLS 补 **179**。同时把 `MEMORY.md` 拆分瘦身（原 21 KB 在注入时被截断）：
逐条交互实现移到同目录新增的 `INTERACTION.md`，`MEMORY.md` 只留决策与索引（10 KB → 5.8 K 字符）。

## 用户报的 bug：「恢复购买后取消，提示网络失败，但是我的网络是好的」

### 根因

`AppStore.sync()` 会弹 Apple ID 登录/确认框，而**用户按取消时它也抛错**。
编排层（`restorePurchases`）把所有抛出来的错一律归成 `.failed`，
界面又只有一句「恢复失败 · 检查网络后重试」——
于是**一个网络完全正常的人被派去查网**。

这类错比"报不出原因"更糟：它给出一个**看起来可执行、实际是错的**下一步。

### 修法（分工才是关键）

| 层 | 改动 |
| --- | --- |
| `MarqueeCore/StorefrontSeams` | 新增 `StorefrontRestoreFailure`：`cancelledByUser` / `network` / `other`。协议 `restore()` 明确要求抛这一档 |
| `MarqueeCore/EntitlementCoordinator` | `RestoreOutcome` 由三档扩到**五档**（加 `.cancelledByUser` / `.networkFailed`），按抛出的档分别映射；认不出的一律 `.failed` |
| `MarqueeStore/StoreKitStorefront` | 新增 `classifyRestoreFailure`：平台错误码 → 三档语义 |
| 偏好页 | 五档对应五句话；只有 `networkFailed` 提网络 |

- **翻译在适配器**：只有它知道平台错误码长什么样 —— 而**同一个"取消"有三种形态**：
  `StoreKitError.userCancelled`、老的 `SKErrorDomain` code 2（`SKErrorPaymentCancelled`）、
  以及 `NSURLErrorDomain` code **-1012**（`userCancelledAuthentication`）。
  ⚠️ 最阴的是 -1012：Apple《Handling errors》把 `NSURLErrorDomain` 整片归成
  "StoreKit 的网络错误"，而那张表里就列着它、含义是**用户取消了这次认证** ——
  按域名一刀切（网络域 ⇒ 网络故障）会让这条 bug **原地复活**。网络域里也得逐码判。
- **态度在 Core**：Core 不 import StoreKit，所以"哪一档说什么话"脱机测得动。
- **取消也要有回话**：上面那行还停在"正在恢复…"，一句不回等于让人以为卡住了 ⇒
  「已取消，没有改动」（中性色，不报红）。

### 验证

- Core **+4**（取消单独一档 / 网络只此一档 / 其它不许冒充网络 / 三档互不相同）。
- `MarqueeStoreTests` 新增一个文件 **+9**（含老 SKErrorDomain 码、**-1012 三形态**、
  `systemError` 只剥一层、认不出落 `.other`）。
- **Core 708 · History 18 · Vision 6 · 商店 16 全绿 + BUILD SUCCEEDED。**
- 变异复验 **3 处全红**（未分类失败冒称网络 / 摘掉 SKErrorDomain 分支 / -1012 被整片当网络）；
  另抓出**两处死代码**：`as? SKError` 与 `NSError.domain == SKErrorDomain` 覆盖同一批错误，
  以及 `error is URLError` 与 `NSURLErrorDomain` 域判断重复 ⇒ 各省一条
  （PITFALLS 117 那两种可能里的"代码是死的"）。
- 文案走生成器：`translations.py` 加 2 条（**已取消，没有改动** / **恢复失败 · 请稍后再试**），
  `./run.sh write` 重出 catalog（256 条，缺 0 / 孤儿 0）。

PITFALLS 补 **180**。

### 先否掉两条走不通的路（都是实测，不是推测）

1. **"抓自己的窗口总不用授权吧" —— 不行。** `CGWindowListCreateImage` 在 macOS 15+ 的 SDK 里
   **直接标成不可用**（`error: 'CGWindowListCreateImage' is unavailable in macOS:

   ⇒ **没有任何"程序自己拍自己"的捷径**。（PITFALLS 188）
2. 离屏渲染更不行：`NSVisualEffectView` / `NSGlassEffectView` 要真实窗口才有东西可糊，
   拍到的只会是**回退档**（PITFALLS 187）。

### 顺带确认了一件容易搞错的事（结论是"对"）

| --- | --- | --- |

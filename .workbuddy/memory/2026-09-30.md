**产出 1：`docs/RENDER-BENCH.md`** — 渲染技术实测报告。
基准源码：`.scratch/render-bench/main.swift`（`bench`）、`bench2.swift`（`bench2`）。
环境：Apple M2 8 核，画布 1600×1000pt @2x = 3200×2000px，`swiftc -O -swift-version 5`。

实测（ms/帧 p50）：
| 图元数 | CG 朴素 | CG 优化 | SwiftUI Canvas | Metal |
|---|---|---|---|---|
| 51 | 7.46 | 5.41 | **0.08** | 0.35 |
| 501 | 46.98 | 91.12 | **0.54** | 1.10 |
| 2400 | 252.70 | 185.37 | **1.48** | 3.54 |
| 24000 | 1061.55 | — | 19.64 | **7.37** |

文字：CoreText 冷栅格化 200 段 = 3.60ms；Canvas 画 200 段 ≈ +4.2ms。
马赛克/模糊（全画布）：CI 高斯模糊 2.64ms、CI 像素化 2.52ms、CG 手工像素化 15.96ms。

**结论：Canvas 为主渲染，CG 只走非交互路径（导出/剪贴板/降采样），滤镜走 CoreImage，Metal 首期不引入。**
关键洞察：**真实标注量级（几十个对象）下 Canvas 比 Metal 更快**（0.08 vs 0.35ms，Metal 每帧有固定提交+同步开销）；Metal 只在 24000 图元才领先（2.7×），而那时 Canvas 也才 19.64ms。留 `CanvasRendering` 协议作升级路径。

## 追加（同日）：坑点清单 + 提前验证（SPIKE）

**用户要求**：对坑点/难点/重点列出清单，在 Mac 上提前验证。

**产出：`docs/SPIKE-PLAN.md`** — 37 项清单（7 组），17 项已自动验证 **全部通过**，20 项待人工验证（含可直接执行的操作步骤）。
验证工具：`.scratch/spikes/main.swift` → `./spikes`（基础探测）/ `./spikes scroll`（滚动配准）/ `./spikes dump`（导出诊断图）。

### 关键结论

1. **滚动截屏（原 R1 高风险）→ 中风险，可行性已验证**：合成长页 1200×9000、步长 600、重叠 200，端到端拼接 vs 真值 **MAE 0.000/255**；Vision `VNTranslationalImageRegistrationRequest` 给出 **tx=-0.00 ty=600.00 精确无误差**；自研 SAD 也对但 **258ms/次太慢** → 主方案用 Vision。亚像素：整数误差 0.5px → 抛物线精化 0.04px。
2. **R4 全局快捷键风险消除**：Carbon `RegisterEventHotKey` 在**未申请辅助功能权限**下注册成功（OSStatus=0）；重复注册返回 **-9878 = eventHotKeyExistsErr** 可检测冲突。`NSEvent.addGlobalMonitorForEvents` 返回非 nil 但强依赖输入监控授权，**降为备选**。
3. **权限 API 确证**：`CGPreflightScreenCaptureAccess()` / `CGPreflightListenEventAccess()` / `AXIsProcessTrusted()` 编译链接通过（符号在 `CoreGraphics.tbd`，头文件位置与常见文档不一致）。本机三项授权均 false。
4. **Liquid Glass 是 macOS 26+ 的 AppKit API**：`NSGlassEffectView` / `NSGlassEffectContainerView` = macos(26.0)，`effectIsInteractive` = macos(27.0)，`SCScreenshotConfiguration` = macos(26.0) → 最低系统 15.0 下必须 `if #available` + 降级。
5. **OCR 首次调用约 25 秒**（模型未缓存），缓存后冷启动 177ms、稳态 p50 60ms（900×260, accurate, 中英）→ 必须启动时后台预热。
6. 剪贴板：写原始 PNG 数据保真（200×200 读回不变）。

### ⚠️ 验证过程中实际踩到的 3 个坑（已解决，写入 PRD 5.6 与 SPIKE-PLAN）

- **K1 位图行序**：`CGBitmapContext` 内存行序本就自上而下，再做"翻转"会**相对各自图像高度镜像**，导致帧间位移**符号整体反转**，配准搜索永远找不到正位移（输出 788/753/658 垃圾值）。教训：这类 bug 不崩不报错，只悄悄错。
- **K2 取帧**：`ctx.draw(page, in: rect(origin.y=-8200))` 负坐标绘制不可靠 → 改用 `CGImage.cropping(to:)`。
- **K3 拼接取行区间**：新内容 = 本帧顶部 d 行，即 `(viewH-d)..<viewH`，不是 `d..<viewH`。

**方法论**：先做"装置自检"（用已知位移的合成图验证取帧+位移正确），再验证算法。本次正是靠自检才发现 K1/K2/K3。

**PRD 已回填**：R1 降级、R4 消除、新增 R10（OCR 预热）/R11（超长图画布渲染）、5.3 未确证项补齐、5.6 加验证结果、M0/M1/M3 里程碑加入验证项与自检回归、附录 C 加 SPIKE-PLAN。

# 渲染技术实测报告 — SwiftUI Canvas vs Core Graphics vs Metal

> 目的：为"标注编辑器画布用哪套渲染技术"提供本机实测依据，而非经验判断。
> 复现命令见文末。**结论在第 5 节，可直接跳读。**

| 项 | 值 |

## 1. 方法

同一份**确定性随机场景**（固定 LCG 种子）分别交给三种渲染后端绘制，比较每帧耗时。场景为截屏标注工具的典型图元：

| 图元 | 说明 |
| --- | --- |
| 圆角矩形 | 填充 + 描边两种模式随机，含圆角半径 |
| 椭圆 | 填充 / 描边 |
| 线段 | 细长旋转矩形（箭头主干、画笔折线、箭头头部均由线段组合） |

计时：预热 5–8 帧后采样 30–60 帧，取 **p50 / p95**。所有实现每帧都先清屏再绘制全部图元。

三种实现的差异：

| 后端 | 实现 | 是否测到 GPU |
| --- | --- | --- |
| CG 朴素 | 每个图元 `saveGState` / `translate` / `rotate` / 新建 `CGColor` / `CGPath` / `restoreGState`，绘制到 `CGBitmapContext` | 否（软件光栅化） |
| CG 优化 | 路径与颜色**预变换缓存**（几何只在对象变化时重算），每帧仅设色 + 提交路径 | 否 |
| SwiftUI Canvas | `Canvas { context, size in ... }` + `ImageRenderer` 离屏出图 | 部分（经图形栈合成） |
| Metal | 单次 instanced draw（SDF 圆角矩形/椭圆 + 描边环），渲染到离屏 `MTLTexture`，`waitUntilCompleted` 后计时 | 是 |

**已知的方法学局限（务必连同数据一起看）**

1. `ImageRenderer` 是**离屏出图**路径，与窗口内实时 `Canvas` 渲染不完全等价（实时还要经 Core Animation 合成）。量级可信，绝对值仅供横向比较。
2. Metal 数字包含 `waitUntilCompleted` 的 **CPU–GPU 强制同步**，真实实现可用三重缓冲流水化，故 Metal 的固定开销在此被**高估**。这只会强化"Metal 上限更高"的结论，不影响最终决策。
3. CG 成本强依赖**填充面积**，Canvas / Metal 对面积几乎不敏感。跨场景的 CG 绝对值不可直接比较（见附录 A 的差异说明）。

## 2. 结果：几何图元重绘（ms / 帧，p50｜p95）

| 图元数 | CG 朴素 | CG 优化 | SwiftUI Canvas | Metal（离屏+同步） |
| ---: | ---: | ---: | ---: | ---: |
| **51**（≈真实重度标注） | 7.46 ｜ 22.50 | 5.41 ｜ 9.16 | **0.08 ｜ 0.20** | 0.35 ｜ 0.74 |
| **501** | 46.98 ｜ 96.99 | 91.12 ｜ 113.60 | **0.54 ｜ 1.60** | 1.10 ｜ 5.98 |
| **2400** | 252.70 ｜ 447.52 | 185.37 ｜ 219.03 | **1.48 ｜ 1.88** | 3.54 ｜ 3.78 |
| **24000**（附录 A 场景） | 1061.55 ｜ 1204.88 | — | 19.64 ｜ 28.65 | **7.37 ｜ 8.34** |

**这张表要读出的三件事：**

1. **在真实工作负载（几十个标注）下，Canvas 是最快的，不是 Metal。** 51 图元时 Canvas 0.08 ms、Metal 0.35 ms —— Metal 每帧有固定的命令缓冲提交与同步开销（约 0.3 ms），而图元太少，GPU 根本没活干。
2. **Metal 只在图元量级极大时才领先**（24000 图元：7.37 ms vs Canvas 19.64 ms，约 2.7×）。但此时 Canvas 用了 19.64 ms 才刚碰到 60 fps 的 16.7 ms 帧预算 —— 也就是说 Canvas 的余量覆盖了 **比真实需求高两个数量级**的负载。
3. **Core Graphics 是明显的性能陷阱**：2400 图元时朴素实现 252 ms，即使做了路径/颜色预缓存仍有 185 ms（约 10 倍差距量级）。**不能用 `CGBitmapContext` 做交互式重绘。**

## 3. 结果：文字

| 项 | p50 | p95 |
| --- | ---: | ---: |
| CoreText 冷栅格化 200 段文字（24pt，含属性字符串构造 + `CTLineDraw`） | 3.60 ms | 4.63 ms |
| Canvas 绘制 200 段文字（几何+文字 − 几何，场景 A） | +4.20 ms | — |
| CG 绘制 200 段文字（几何+文字 − 几何，场景 A） | +1.33 ms | — |

结论：

- 文字在三个后端都**不是瓶颈**（200 段是极端数量；真实截图通常 3–10 段文字标注）。
- Canvas 的 `context.resolve(Text)` + 绘制单段成本约 20 µs，可接受；如需极致可把已确认不变的文字行缓存为 `GraphicsContext.ResolvedText`。
- **Metal 路径的文字是纯新增工程量**：需要自建 glyph 图集（CoreText 栅格化 → 纹理 → UV 实例），以及文本编辑、选区、光标、可访问性全都要自己写。这是"简洁"原则下最不划算的一块。

## 4. 结果：马赛克 / 毛玻璃模糊（标注 P1 功能）

全画布 3200 × 2000 px 的整幅处理耗时：

| 方案 | p50 | p95 |
| --- | ---: | ---: |
| CoreImage `CIGaussianBlur`（r=24）→ `CIContext.createCGImage` | **2.64 ms** | 3.15 ms |
| CoreImage `CIPixellate`（scale=16） | **2.52 ms** | 3.04 ms |
| CG 手工像素化（降采样 + 最近邻放大） | 15.96 ms | 16.33 ms |

结论：**模糊/马赛克一律走 CoreImage**（GPU 路径，比手工 CG 快 6 倍），不需要为它引入自写 Metal kernel。

## 5. 决策与理由

### 结论

| 用途 | 选型 |
| --- | --- |
| **编辑器画布交互式重绘** | **SwiftUI `Canvas`** |
| **导出 / 落盘 / 剪贴板 PNG 数据** | **Core Graphics + ImageIO**（非交互路径，性能无关） |
| **模糊 / 马赛克 / 高亮滤镜** | **CoreImage**（`CIGaussianBlur` / `CIPixellate`） |
| **文字输入与编辑** | AppKit `NSTextField` / SwiftUI `TextField` 作为 overlay，Canvas 只负责绘制已落定的文字 |
| **Metal** | **首期不引入**，仅在 `SnipoEditor` 内预留渲染协议边界（见下） |

### 理由

1. **性能不是本项目的约束，复杂度才是。** 实测 Canvas 在 2400 图元下 1.48 ms，相对 16.7 ms 帧预算有 **10 倍以上余量**；真实标注量（10–100 对象）下余量超过 100 倍。为一个用不到的性能上限引入 Metal，代价是自建字形图集、文本编辑、命中测试、可访问性与全套渲染调试——直接违背第 9 条"功能简洁、交互流畅"里的前半句。
2. **Metal 在目标负载下反而更慢**（51 图元：0.35 ms vs 0.08 ms）。买不到任何东西。
3. **CG 必须留，但只用在非交互路径。** 导出、剪贴板数据、马赛克降采样都需要 `CGBitmapContext`；它慢没关系，因为一帧只跑一次。
4. **CoreImage 承担滤镜**，避免自写 kernel。
5. **保留升级路径**：`SnipoEditor` 的渲染入口收敛到一个 `CanvasRendering` 协议（`func draw(document:in:)`），未来若真需要（例如引入可交互的液化/自由形变效果），可以新增 `MetalCanvasRenderer` 实现而不动上层。

### 什么时候应该推翻这个结论

出现下列任一情况时，重新评估 Metal：

- 单个文档常态超过 **5000 个标注对象**（现实中不会；截图标注是"人手工画几十个"的量级）
- 需要**逐像素实时效果**（如跟随鼠标的液化、自由形变、实时景深）
- 需要在画布上做**视频帧序列**的实时处理（屏幕录制预览的实时滤镜）

## 6. 交互流畅性的性能预算（写入验收标准）

基于以上实测设定的预算，供 M2/M3 里程碑验收使用：

| 交互 | 预算 | 实测余量 |
| --- | --- | --- |
| 覆盖层出现（快捷键 → 蒙层可见） | ≤ 1 帧（16.7 ms） | 待 M1 实测 |
| 选区拖拽 / 窗口悬停高亮刷新 | 120 fps（8.3 ms/帧） | Canvas 绘制 ≈0.1 ms，余量 >80× |
| 编辑器重绘（≤ 100 标注） | ≤ 4 ms | 0.20 ms（51 图元），余量 20× |
| 马赛克/模糊操作一次 | ≤ 5 ms | 2.64 ms |
| 落点 → 剪贴板可用 | ≤ 150 ms | 待 M1 实测（含采集开销） |

## 附录 A · 跨场景数据对照（scenario A: 含箭头与画笔折线）

`main.swift` 的场景 A 额外包含箭头（主干 + 2 段头部）与画笔折线（6 段），几何分布与 `bench2.swift` 的场景 B 不同：

| 图元数 | CG 朴素 | SwiftUI Canvas | Metal |
| ---: | ---: | ---: | ---: |
| 2400（场景 A） | 108.94 ｜ 136.39 | 2.26 ｜ 6.50 | 0.97 ｜ 1.71 |
| 24000（场景 A） | 1061.55 ｜ 1204.88 | 19.64 ｜ 28.65 | 7.37 ｜ 8.34 |

同一图元数下 CG 场景 A（108.94）比场景 B（252.70）**更快**，原因是场景 B 的图元尺寸更大（单图元像素覆盖面积更高），印证第 1 节局限 3：**CG 成本由填充面积主导，Canvas/Metal 几乎不敏感**。

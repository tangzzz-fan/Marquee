## 一、玻璃材质

### 先看两份「已存在」的分叉

实装的玻璃来自 **ticket 17**（早于这份稿），走的是**系统原生材质**这条路：

| | 新稿 §01 | 实装 |
| --- | --- | --- |
| 配方 | 深色色膜 `oklch(26.5% 0 0 / .72)` + `blur(24px) saturate(160%)` | macOS 26+ `NSGlassEffectView(.regular)` + 黑 tint **α 0.25** |
| 15.x 降级 | 「低透明度」开关切回不透明 `--c-panel` | `NSVisualEffectView(.hudWindow)` + 黑衬底 **α 0.35** |
| 上缘高光 / 描边 | `inset 0 1px 0 white .15` / 描边 12% → **16%** | 由系统材质自带；**不自绘描边** |
| 验收依据 | 最坏情况（纯白内容）**6.10 : 1** | `ChromeMaterialTests` 只断言 `scrimAlpha >= 0.25` / `glassTintAlpha >= 0.1` |

> ⚠️ **两条路各有各的道理，但它们不是同一件事**：
> 稿子的 α .72 深色膜明显比实装的 α .25 深得多 —— 稿子那套对比度账
> 是**算出来的**，实装这套是**靠系统自适应兜的**，两者没有对过账。
> `ChromeMaterialTests` 那两条断言写的是**边界**（`>= 0.25`）而不是稿子的**意图**（6.1:1）——
> 与 PITFALLS 98 同一条：拦得住「忘了设」，拦不住「设得不够」。
> 换成原生玻璃之后这个账该怎么记，是这份稿真正要回答的问题（稿子没答）。

## 二、钉图图标（§06）

### 现状

实装用的是 **SF Symbol `pin`**（`AnnotationIcon.pin`，`AnnotationIcon.swift:136`）。

### 稿子给的三条理由，在实装里**一条都不成立**

稿子说旧图「在 16px 下糊成一团」，列了三条缺陷。逐条对：

| 稿子说旧图的问题 | 实装（SF Symbol `pin`） |
| --- | --- |
| 轮廓不闭合（收口边没画） | 闭合路径 |
| 右肩两笔相距 0.92 → 并成 2.4 的糊带 | 无并线 |
| **斜置 —— 全条唯一不站直的图标** | **站直**（见 `shots/sf-pin-family.png`） |

⇒ **那三条是稿子自己手绘转录时的缺陷**（稿子里的 `#i-pin` 是一条不闭合的斜折线，
`shots/pin-icon-compare.png` 左二就是把那条路径按原样画出来的样子）。
实装用的是系统符号，从来没有那个问题。

### 但形状确实和稿子不一样

| | 头 | 领口 / 横档 | 针 |
| --- | --- | --- | --- |
| 稿子 §06 新几何 | **正圆** ⌀4.8 | 梯形，宽 **6.2** | 直线 4.5 |
| SF Symbol `pin` | 喇叭形（上宽下收） | 宽檐 | 直线 |

稿子的几何（16 格）：`circle 8 4.8 r2.4` · `M6.3 6.5 4.9 8.9h6.2l-1.4-2.4` · `M8 8.9v4.5`；
视觉边界 x 4.15–11.85 · y 1.65–14.15（横竖都居中），针只占 x 7.25–8.75，
**右下 9×9 完整留给 Pro 锁**（这一条实装也满足）。

### ⚠️ 稿子的定调需要复核

稿子写：「**故意不随 macOS 的 45° 斜针惯例**，登记在案」。
但 SF Symbols 的 `pin` **不是 45° 斜的** —— 那句话针对的仍是稿子自己那张转录图。
所以这不是「跟着稿子改掉一个系统惯例」，而是**「把系统符号换成一枚自绘符号」**。

代价有两条，都得认：

1. **多一份要自己维护的图形资产** —— `AnnotationIcon` 现在是「工具 → SF Symbol 名」的纯映射
   （文件头那条：「图标名全项目唯一一份」）。自绘会把它变成「一半取系统、一半养路径」。
2. **自绘路径要在两处同时成立** —— 覆盖层是 `NSBezierPath`（`SelectionOverlayView.drawSymbol`），
   编辑器那侧走 SwiftUI `Image(systemName:)`。自绘得两边各画一遍，
   而**它们不会报错，只会某天悄悄分叉**（同 `AnnotationIcon` 文件头记的那类错）。

**这是设计决定，得你点头，我不擅自改。**

### 2. 顺带补上一条**完全没实现**的规则

稿子 §07 的规则表里写着：

> **「降低透明度」是回退开关**：一开，全部 `.glass` 切回 `--c-panel` 不透明 ——
> 现有 8 份稿的不透明面就是回退稿，不需要第二套设计。

实装里**一条判断都没有**（`ChromeBackground.isGlassAvailable` 只看系统版本与一个现场开关），
而且原来那两条路（`.glass` / `.hud`）**都半透明** —— 拿一个半透明去答
"我要减少透明"，等于没答。而开这个开关的往往正是最赔不起的那一类用户。

现在 `ChromeMaterial` 有第三档 `.opaque`，判据进 Core（可脱机单测）：

```swift
public static func resolved(glassAvailable: Bool, reduceTransparency: Bool = false) -> ChromeMaterial {
    if reduceTransparency { return .opaque }   // ⚠️ 顺序：它优先于"玻璃可用吗"
    return glassAvailable ? .glass : .hud
}
```

顺序写反**只有在新系统上才看得出来**（15.x 上两条都落 hud/opaque，恰好也对），
所以那条断言单开了一个用例。

## 五、玻璃怎么验（这一层只能实机看）

### 为什么不能靠出图

`NSVisualEffectView` / `NSGlassEffectView` 都要**真实窗口**才有东西可糊。
任何 `ImageRenderer` / `cacheDisplay` / PDF 导出都拍不到玻璃 ——
拍到的只会是**回退档**（实色），看起来像"忘了画底"（PITFALLS 187）。

顺带一条被否掉的路：**"抓自己的窗口总不用授权吧"——不行。**
`CGWindowListCreateImage` 在 macOS 15+ 的 SDK 里**直接标成不可用**
（`error: ... is unavailable in macOS: Please use ScreenCaptureKit instead`），
而 ScreenCaptureKit 一律要屏幕录制授权 ⇒ **没有任何"程序自己拍自己"的捷径**（PITFALLS 188）。

> ⚠️ 一个容易搞错、但结论是"对"的地方：覆盖层显示的是**实时桌面**（蒙层只是压暗它），
> **冻住的只有采集到的像素**（供裁剪与放大镜取色用）。
> 所以材质用 `blendingMode = .behindWindow` 采样"窗口背后"是**正确**的 ——
> 它采到的正是用户在玻璃底下看到的那张画面。
> （若哪天把冻屏图改成画在覆盖层窗口**内部**，这一条就会立刻反过来，
> 那时玻璃会开始糊桌面而不是糊用户看的内容。）

### 一条命令

```bash
APP="$PWD/DerivedData/Build/Products/Dev/Marquee.app"

# ① 先看权限（权威判据，别靠猜）
"$APP/Contents/MacOS/Marquee" -marqueeDiagnostics | grep 屏幕录制

# ② 没授权就触发一次系统框 —— **必须 open -a**，直接 exec 会把授权算在终端头上
open -a "$APP" --args -marqueeRequestPermission
#    弹框里点「打开系统设置」→ 隐私与安全性 → 屏幕录制 → 勾上 Marquee

# ③ 出图（会新起进程，不必手工重启应用）
open -a "$APP" --args -marqueeSmokeOverlayShot
#    结果：<数据根>/reports/overlay-shot.png
```

`-marqueeSmokeOverlayShot` 做三件事：真把覆盖层摆出来 → **走真实的三段委托**
拖一个占屏 56% 的选区（不是往会话里塞矩形，否则拍到的排布不代表运行时）→
用采集器抓一次屏。没有权限时它**不闷着**，直接把它自己那条 `open -a` 命令
（路径是运行期的真实值）打出来，可以直接复制。

### ⚠️ 三条路只有一条同时成立

| 方式 | 参数送到？ | TCC 认它是自己？ |
| --- | --- | --- |
| 直接 exec 可执行文件 | ✓ | ✗ —— 算在**父进程（终端）**头上 |
| **`open -a <路径> --args <flag>`** | ✓ **（但要在你自己的终端里）** | ✓ |
| `launchctl submit` | ✗ | — |

**`open --args` 会静默丢参**（`open -a <路径>` / `open <路径>` / `open -b <id>` /
`open -a <名字>` / 加 `-n`，五种写法在被沙箱包裹的 shell 里**全丢**，PITFALLS 189）。
那种失败**极其像"这个开关没实现"**：进程正常起来、正常进事件循环、一行输出都没有。
所以现在只要带了命令行参数就落一份 `reports/launch-arguments.txt` ——
**没有这个文件 = 参数根本没送到**，与"送到了但分支没跑"一眼分得开。

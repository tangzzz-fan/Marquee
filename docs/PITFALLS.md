## A. 位图、色彩空间与坐标

1. **`CGBitmapContext` 的内存行序本就自上而下**，不要再"翻转为自上而下" —— 那是相对各自图像高度的镜像，会让帧间位移**符号反转**，配准静默出错。
2. 取帧一律用 **`CGImage.cropping(to:)`**，不要用负坐标 rect 的 `ctx.draw`（结果与预期不符，K2）。
3. **`CGBitmapContext.bytesPerRow` 必须对齐**（用 16 的倍数）。给 `width * 4` 这种未对齐值（例如 2 px 宽的图 = 8 字节）会**整行读出垃圾且不报错**。
4. 位图行步长必须用 **`ctx.bytesPerRow`（字节）**，不能 `bytesPerRow / 4` 再乘像素下标 —— 单位混用会读出毫无关系的字节，且不报错，只是断言在胡说。宽度不是 16 倍数时 `bytesPerRow` 还会被 CG 补齐（实测 400 宽 → 416）。
5. **`CGColorSpaceCreateDeviceRGB()` 在本机（P3 屏）就是 Display P3**：用它建上下文 + 用 `CGColor(red:green:blue:alpha:)` 填色，"纯红"读回来是 `(255,38,0)`，颜色断言变成碰运气。测试里一律用 `CGColorSpace(name: .sRGB)` + `CGColor(colorSpace:components:)`。
6. **导出底图必须保留来源色彩空间**：`AnnotationRasterizer` 曾经恒用 sRGB，把 P3 截图悄悄转掉。要优先取 `cropped.colorSpace`；`AnnotationColor.cgColor(in:)` 也必须走 `converted(to:)` 而不是把 sRGB 分量塞进目标空间。
7. **翻转 CTM 之后再 `draw(CGImage, in:)`，图会上下颠倒。** 翻转后图像的顶行仍在 `rect.maxY`，而 `rect.maxY` 已是视觉上的**下**边（实测：自上而下 10/20/30/40 的四行图落在第 2 行，翻转得 `40,30,20,10`）。所以**底图要在默认 y 向上坐标系里画**，需要"左上原点"时再把 CTM 翻过来画别的（标注）。`AnnotationRasterizer` 与 `ScrollStitchRenderer` 都踩过；**纯色底图看不出翻转**，所以 `TestSupport` 里加了 `topBlackBottomWhite`。
8. **"1:1 直通拷贝"也需要对齐设备像素。** 只要目标矩形落在半个像素上（`origin = 光标 + 间距`，光标天然带小数），CG 就会插值一次 —— 平滑档看起来发虚，最近邻档则是**个别格子被拉宽、个别被吃掉一行**。画任何"像素到像素"的图（放大镜、像素对齐的预览）都要把落位按 `backingScale` 取整。
9. **"坐标空间已对齐"这件事要能实测，不能靠猜。** 编辑器画布走 SwiftUI `Canvas.withCGContext`，导出走自建 CGContext —— 两者的 y 方向若不一致就是**镜像文字**，而"有没有墨"这类断言完全看不出来。解法：用 `ImageRenderer` 把画布离屏渲染成图，再读像素判方向（`AnnotationTextCanvasTests`）。
10. **CoreText 的局部翻转（平移到基线 + `scaleBy(1,-1)`）不能省**，否则文字镜像/跑位。且编辑器与导出必须共用 `MarqueeCore.AnnotationText`，各画各的会出现"编辑器里放得下、导出后被裁掉半个字"。

## B. 滚动拼接与配准

11. **长图拼接的取行区间**：新内容 = 本帧**顶部** d 行 = `(viewH-d)..<viewH`，不是 `d..<viewH`（写反了高度对、内容错位，MAE 75.78）。
12. **长图总高与每片底边都取 `floor`，不要 `ceil`。** 取 `ceil` 会多出一行"只覆盖一半"的行，谁都不完整覆盖它 → 长图上一条**半透明横线**。
13. **Vision 位移符号是 `rows = +ty`**（`targetedCGImage:` = 上一帧、handler = 当前帧）。按"Vision 原点在左下"取负会让所有位移变负 → 每帧都判成"没动"，长图永远只有一屏（不崩不报错）。
14. **配准模块必须内置"装置自检"**：用已知位移的合成图做回归。上面 A/B 两组里好几个坑都是靠自检才发现的。这条不是"建议"——没有它，出错时无从下手。
15. **落地测试要覆盖亚像素**：整数位移会累积 ±0.5 px 误差，长图越长错位越明显。抛物线精化后按**累计小数位移重采样**。

## C. 权限、签名与 TCC

16. **别用自己持久化的标记去推断 TCC 的 `denied`**：签名身份一变，TCC 状态重置而标记还在，于是再也不敢调 `CGRequestScreenCaptureAccess()`；而 macOS 只在应用调用采集 API 时才把它登记进「屏幕录制」列表 → 用户永远授权不了。见 `DEV-NOTES.md` 1。
17. **macOS 只在应用真的调用采集 API 时才登记进「屏幕录制」列表**。权限门若拦在采集之前，"请求权限"里也必须真的碰一次 `SCShareableContent` —— 碰一次**枚举**就够了，**不要**再截一帧：`SCScreenshotManager.captureImage` 在 macOS 15+ 会叠出第二张系统授权框。
18. **授权框连弹**：`requestPermission()` 里截帧 + preflight 在重启前一直是 false 仍报 `.notDetermined` + 刚授权还去采集，三者叠在一起会让每次快捷键都弹系统框。进程内记住"问过一次"（**不要**写 UserDefaults），刚授权只提示重启。见 `DEV-NOTES.md` 1.3。
19. **`DEVELOPMENT_TEAM` 要填真正的 team id**（`codesign -dvvv` 里的 `TeamIdentifier`，本机 `UKXWZ3FS84`），**不是**证书名括号里那串（`Apple Development: … (7H6TJ2PN25)` 里的是证书标识）。填错报 `No signing certificate "Mac Development" found`。
20. **签名必须由工程负责**（`project.yml` 的 `CODE_SIGN_IDENTITY` + `DEVELOPMENT_TEAM`），**不能只写在构建脚本里** —— Xcode Run 不执行脚本，只改脚本等于没修。
21. **自动滚动需要「辅助功能」授权**（本项目唯一一处）：往别的进程注入事件属于辅助功能授权范围。所以它必须**按需**申请 —— 只有用户主动触发才问，拒绝即降级回手动。

## D. 状态推进与 UI 反馈

22. **可选回调漏接线 = 静默 no-op，且毫无线索。** ticket 11 把 `MenuBarController.onScrollCapture` 写成可选 `var` 却忘了在 app delegate 注入 → 菜单项看着是启用的、点下去什么都不发生。**判据：用户说"点了没反应"时，第一件事是验入口通不通，再看下游渲染。** 修法是把 UI 回调做成 `init` 的必填参数（漏接即编译错误）。
23. **"状态没变"的判定必须先验前提。** 长截图把"连续几帧没动"解读成"滚到底"，但用户**还没开始滚**时它只意味着"还没开始" → 进门 1 秒就误报到底。同类陷阱：任何"结束了/到底了/完成了"的自动判定，都要先问"有没有真的开始过"。
24. **误判不能做成终局。** 上面那个误报原来还会**停掉抓帧循环** —— 用户再往下滚就彻底没反应，长图还缺后半段，比误报本身更糟。自动判定触发时应当降级为**提示 + 可恢复**，而不是停机。
25. **改了状态 ≠ 状态会被推出去。** 放大镜更新只改 `magnifier` 字段，把"推给视图"交给调用方顺手调 `refresh()` —— 而空闲移动走的是 `updateHover`，那里"悬停窗口没变"时直接 `return`，于是**落点之后与悬停在同一个窗口内时放大镜定格不动**。规矩：**谁改谁推**（`pushMagnifier`）。同源：`statusText` 是烘进 presentation 的，只 `refresh()` 推的是算好的旧那份 → 反馈要等下次鼠标移动才出现，必须**重建**。
26. **判定要分清"内容没变"与"位置没变"。** 放大镜原来把"取样像素没变"直接当成"什么都不用做"，而光标位置仍可能变了 —— 混在一起就会**该动的没动**。抽成三态（`idle` / `moved`（复用小图、只挪盒子）/ `resample`（重采））后既可测也不再含糊。
27. **说"某键被占用"之前，先确认它被占用的**相位**。** `⌥` 在悬停时是空档，落点之后才归 ticket 04 的"无阴影" —— 一个假冲突换来的是放大镜必须赖在落点之后不走，同时违背 PRD F4 与用户参照的微信行为。**冲突要按相位核对，不能按"这个键有没有人用"粗判。**
28. **`fillMask(punching:)` 的洞有多大，蒙层就少多少** —— 洞等于整屏时这个分支等于"没画"。长截图空状态就踩过：把整块屏当高亮镂空 → 用户看不出覆盖层在工作，以为"拖不了"。空状态要的是满屏蒙层 + 提示。
29. **依赖"前台→后台顺序"的命中，必须在应用切换后重取清单**：`NSWorkspace.didActivateApplicationNotification` → 重拉 `SCShareableContent` + 强制重算悬停（`updateHover` 只在鼠标移动时被调用，不动鼠标就会一直停在旧高亮上）。
30. **自动滚动的三类停稳判定缺一不可**：单步等待上限（无限加载）、步数熔断（永远滚不完）、连续"采不到画面"熔断。少任何一个都会变成"卡住不动"。
31. **滚轮事件是按「指针下方的窗口」派发的** → 自动滚动前必须先把指针对准选区，否则事件滚了别的窗口（用户看到的是"什么都没发生"）。且 CGEvent 的 `wheel1` **向下滚是负值**（同 `NSEvent.scrollingDeltaY`），写反不报错、只是方向相反。

## E. 测试与断言

32. **swift-testing 的 `#expect(...)` 宏展开里不能调 `mutating` 方法**（`$0 is immutable`）→ 先赋给局部变量再断言。
33. **"夹取"与"翻边"是两件不同的事，只断言不变量会漏掉后者。** 摆位时"不越界 + 不盖光标"靠夹取就能满足，翻边真正的价值是**让放大镜贴着光标**。变异测试里把翻边去掉曾经漏网，补了"水平间距 ≈ gap"才抓住。**写断言要写「意图」**，不能只写不能违反的边界。
34. **测"翻转"要用不对称的图。** "上黑下白各一半"关于**水平中线镜像对称**，翻转后逐像素相同，变异测试直接漏网。换成"顶部一条黑带"立刻抓住。
35. **区分两种"都能让细节变少"的滤镜，度量要选对。** 马赛克与模糊用"变脸次数"或"相邻像素是否相等"都区分不出（大色块模糊后中间会出现饱和平台）。可靠度量是**相邻像素跳变的最大幅度**：马赛克是台阶（能跳到接近满量程），模糊是斜坡（被摊薄到几十）。
36. **"放大"发生的地方要和"画"分开想。** 视图里 `interpolationQuality` 只在**非 1:1** 时起作用；图像尺寸与目标矩形严格相等时那个设置形同虚设。**问自己：重采样到底发生在哪一步。**
37. **放大图像必须 `interpolationQuality = .none`**（Core 与视图两处）：双线性会把相邻像素混起来，而放大镜的用途恰恰是"看清这一格是什么颜色"，混色等于把要看的抹掉。测试用"输出里只允许出现源图那两种颜色"来钉它。
38. **变异测试是"断言有没有空跑"的唯一证据。** 每个新模块做完跑一次：故意改坏一处实现，确认测试变红，再改回来。

## F. 工具链与工程

39. **`xcodebuild` 无法解析本地 SPM 包**（deny-default 沙箱在本机宿主环境不可应用）→ 用 `scripts/build.sh`。见 `DEV-NOTES.md` 4。
40. **被沙箱包裹的 shell 里 `xcodebuild` 编不过 SwiftUI 宏**：`swift-plugin-server` 启动时自己再套一层沙箱，外层不放行就被 SIGKILL，报 `StateMacro ... produced malformed response`。**判断方法：`./scripts/test.sh`（SwiftPM，按 `--disable-sandbox`）能过、`./scripts/build.sh` 不能 → 一定是宿主沙箱，别动代码。** App 层可改用 `swiftc -typecheck -sdk $(xcrun --show-sdk-path) -swift-version 6 -strict-concurrency=complete -I Modules/.build/out/Products/Debug App/Sources/*.swift` 验证。
41. **新增/删除源文件后必须 `xcodegen generate`** —— Xcode 的 Run **不会**替你生成，症状是报在**调用方**（"找不到某类型"）而不是新文件本身。已改用 `type: syncedFolder`（Xcode 16+ 文件系统同步组）根治。见 `DEV-NOTES.md` 2.2。
42. **别依赖 Xcode 自动创建的 user scheme**（在 `xcuserdata/`）。`xcodegen generate` 之后它可能不在了 → 必须在 `project.yml` 里声明**共享** scheme。
43. **bash + `set -u`：中文文案里 `$VAR` 紧跟全角字符会被当成变量名的一部分**（如 `$IDENTITY（team …）`）→ 报 "unbound variable"。写 `${VAR}`。
44. **模块缺 `import Foundation` 会让 `Equatable` 静默合成失败**（`URL`/`Date`/`UUID` 场景）。同源：`CGImageDestination*` 要 `import ImageIO`。

## G. 平台 API 细节

45. **`NSEvent.ModifierFlags` 的 ⌘ 是 `1<<20`（0x100000），不是 `1<<16`** —— `1<<16` 是 **Caps Lock**。位值：capsLock `1<<16`、shift `1<<17`、control `1<<18`、option `1<<19`、command `1<<20`（`NSEvent.h:168-172`）。写错不崩，只会让所有 ⌘ 组合静默变成"没按 ⌘"。已用测试钉死。
46. **Carbon 虚拟键码不是顺序的**：`kVK_ANSI_5 = 0x17`、`kVK_ANSI_6 = 0x16`（反序）。键码表一律从 `Events.h` 抄，别按下标推。
47. **Carbon 热键的冲突只能靠「独占注册」探测出来**（四种情形实测）：
    - 非独占注册：**永远是 0**，被占也返回成功 → 光看它永远发现不了冲突（微信同时响应就是这么来的）
    - 独占注册 + 同进程内已有自己的注册 → `-9878` → **必须先 `unregister()` 再探测**
    - 独占注册 + **别的进程独占**占着 → `-9878` ✅ 可用的探测手段
    - 独占注册 + 别的进程只是**非独占**占着（跨进程）→ **0**，探测无效；此时双方都收到事件
48. **`OptionSet` 的 Codable 是 `RawRepresentable` 单值编码**：`ShortcutModifiers` 编出来是 `"modifiers":9`，**不是** `{"rawValue":9}`。手写偏好做测试时别猜形状。
49. **`os.Logger` 的字符串插值里引用实例属性要写 `self.`**，否则 Swift 6 报 "requires explicit use of 'self'"。
50. **Swift 6 的 nonisolated `deinit` 不能碰非 Sendable 的存储属性**（如 `EventHotKeyRef` / `EventHandlerRef`，都是 `OpaquePointer`）→ 编译报错。解法：不写 deinit 做清理，改由显式 `unregister()` 负责。
51. **`NSLock.lock()` 在 async 上下文里不可用**（编译报 "unavailable from asynchronous contexts"）→ 把加解锁收进一个同步闭包（`withLocked`），在闭包外再做异步的事。
52. **屏幕录制之外还有两个「不弹框也能问」的探针**：`CGPreflightListenEventAccess()`（输入监控）、`CGPreflightPostEventAccess()`（辅助功能/事件注入）。它们的声明**不在头文件里**，但 Swift 能直接调用（符号在 `CoreGraphics.tbd`）。`AXIsProcessTrusted()` 则需要 `import ApplicationServices`。
53. **状态机类的东西必须放 Core**：`MarqueeOverlay` 里的东西无法自动化测试（需要真实屏幕），只有抽到 Core 才能单测。

## H. 窗口与呈现

54. **`.accessory` 应用（`LSUIElement`）里 `makeKeyAndOrderFront` 不够。**
    它**依赖应用已经是 active 的**，而 `Marquee` 是 `main.swift` 里
    `setActivationPolicy(.accessory)` 的后台应用 —— 从覆盖层（高层级 `NSPanel`）退下来、
    紧接着开一个**普通层级**的 `NSWindow` 时，窗口很可能开在别的窗口后面。
    用户看到的现象是"`⏎` 按了，编辑器窗口没出来"，而**它其实已经开好了**；
    更麻烦的是"窗口没出来"和"截图失败"在用户眼里完全一样，很容易查错方向。
    **修法：`window.orderFrontRegardless()`（不看激活状态）**，编辑器窗口与快捷键偏好窗口都要。
    > 判据：凡是"用户说某个窗口没出现"的反馈，先看这个窗口是 `NSPanel` 还是 `NSWindow` ——
    > NSPanel（覆盖层）有 `level` 兜着不容易暴露，`NSWindow` 才会踩到。
    > 同时补一条日志（"打开编辑器：W×H"），这样能先确认**到底有没有走到开窗那一步**。

55. **设置 `NSWindow.contentViewController` 会按 SwiftUI 视图的 `fittingSize` 重排窗口。**
    `GeometryReader` **没有固有尺寸**（它的 ideal size 就是 10×10），所以
    `NSWindow(contentRect: 960×680)` 之后紧跟一句 `contentViewController = NSHostingController(...)`，
    窗口会被缩成"工具栏那一条"。
    **修法：尺寸要在设完 `contentViewController` 之后用 `window.setContentSize(_:)` 再定一次**，
    不能只靠 `init` 里那个 `contentRect`。
    > 坑点：窗口**确实创建了、也叫到前台了**，只是面积几乎为零。
    > 现象上完全看不出是尺寸问题（用户只会说"窗口没弹出来"）。
    > 判据：凡是"`NSWindow` + SwiftUI hosting + 说窗口没出现"，先怀疑尺寸被 hosting 改过。

56. **`.nonactivatingPanel` 上"视图的 `keyDown`"靠不住 —— 覆盖层的功能键必须走应用级本地监听。**
    覆盖层面板刻意用 `.nonactivatingPanel`（不激活本应用，免得把用户从当前应用拽走），
    于是"面板是 key window 且视图是 first responder"这条链路在真实使用中**并不成立**。
    实测（2026-10-01，用户跑出来的日志）：`Esc` 生效（它走 `NSEvent.addLocalMonitorForEvents`），
    而 **`⏎` 完全没反应**（它走视图 `keyDown`）—— 用户拖完选区按 `⏎` 什么都没发生，
    只能按 `Esc` 退出，报上来的现象却是"**编辑器窗口弹不出来**"。
    **修法：把覆盖层全部功能键（`Esc` / `⏎` / `⌘S` / 空格 / 方向键）都放进那个本地监听**，
    闭包只回传"消费了没有"（`NSEvent` 不是 `Sendable`，跨隔离域回传它编译不过）。
    > 判据：**`Esc` 能用而别的键不能用 → 就是这个坑**（`Esc` 恰好走了另一条路）。
    > 更一般的教训：同一个功能绝不能留两条"只在特定前提下成立"的输入路径。

57. **一行控件加起来比窗口还宽时，右边那些会被「挤出可视区」—— 不报错、不压缩、只是看不见。**
    编辑器工具栏原先用文字按钮（"选择""矩形"…），整排实测约 **1110 点**，而窗口默认只有 960。
    `HStack` 空间不足时先缩 `Spacer()`（缩到 0），再不够就把超出部分直接裁掉 ——
    **最右边的控件首当其冲**。用户报的是"OCR 入口我不知道在哪""工具栏我没有看到"，
    查了半天代码，其实功能一直都在，只是**没画出来**。
    **修法**：① 控件图标化（30 点/个，中文标签进 `help`）；
    ② 窗口 `minSize` 不得低于工具栏的实际宽度。
    > 判据：用户说"某个按钮/入口看不见"时，先把那一行控件的宽度**加起来**跟窗口宽度比一比。
    > SwiftUI 不会为"放不下"报任何错，这一点和"静默错误"是同一类坑。

58. **同一个功能的"尺寸/位置/命中"若分几处各自推导，差几点就永远对不上 —— 而且只在贴边时暴露。**
    覆盖层浮动工具栏原先：宽度按"间距在**两组之间**"算，按钮偏移按"间距在**末尾**"算 ——
    差 4 点，最后一个按钮探出右边一点。两条规则各自都对，凑在一起才错。
    **修法：让 `layout()` 一次算出尺寸、每格位置、分隔线位置，绘制与命中都从它取。**
    单一来源之后，"画出来的框"和"点得到的区域"**不可能**分叉。
    > 更一般的判据：任何"看到的"与"点得到的"要一致的界面，几何只能有一份。
    > 附带教训：这条最初写成测试也没抓住 —— 我注入的变异（把组间距从 9 改成 1）
    > **全绿通过**了，因为原测试只断言"不重叠、不越界"，而这些在间距变小时照样成立。
    > 补了"组间间距必须明显大于组内间距"与"工具条必须放得进 1024 点的屏"两条**意图**断言才抓住。
    > **断言只写"不能违反的边界"是盲的，必须同时写"应该是什么样"。**

59. **坐标空间差一次「原点在上还是在下」，图形会整体镜像 —— 而它不崩、不报错、只在画了东西之后可见。**
    `Annotation` 的约定是"原点左上、y 向下"，而 Cocoa 的 `CGRect.origin` 是**左下角**（y 向上）。
    覆盖层取"选区左上角"当标注原点时必须用 `rect.maxY`，写成 `minY` 会让所有标注上下镜像。
    同理，视图里画标注要先 `translateBy(origin)` 再 `scaleBy(1, -1)`。
    > 判据：凡是"两个坐标系要接起来"的地方，**先写一条断言把换算钉住**，
    > 再写绘制。默认的那套坐标永远是最容易被想当然的。

60. **缩放标注时只缩位置、不缩线宽 —— Retina 上导出的线条会细成屏幕上的一半。**
    覆盖层用"点"、导出用"像素"，两者差一个屏幕倍率。
    `Annotation.scaled(by:)` 必须**一起**缩放 `frame` / `path` / `lineWidth` / `fontSize` / `effectStrength`。
    只缩位置的表现是"导出把线变细了"，很容易被当成显示问题去查渲染。
    > 判据：缩小/放大一个带样式的对象时，**列出所有带"长度"量纲的字段**，逐个确认。

61. **带阴影的窗口截图比窗口矩形大一圈 —— 有坐标叠加时必然整体偏移。**
    `.isolatedWindow(includeShadow: true)` 拍出来的图含外扩的阴影，
    而"就地标注"的坐标是相对**窗口矩形**算的。差这一圈，所有标注会整体偏移，
    且偏移量随阴影大小变（浅色背景下阴影大）—— 表现是"有时候对、有时候偏"。
    **修法：有就地标注时强制 `includeShadow: false`**（宁可这张图没阴影）。
    > 判据：任何"把 A 坐标系的图元叠到 B 坐标系的图上"的地方，
    > 先确认两个矩形的边界**逐点相同**，而不是"差不多是同一块"。

62. **「合成失败就回退成原图」在有打码的场景里是个安全缺陷，不是容错。**
    `CaptureOutput.finish` 把就地标注栅格化到截图上，失败时如果 `?? image` 回落，
    用户以为已经遮住的内容会被原样复制出去 —— 而且不会有任何提示。
    **修法：标注非空而栅格化失败时，直接让这次截图失败。** 宁可作废，不要静默降级。
    > 判据：任何"降级路径"经过**脱敏 / 打码 / 权限过滤**时，降级方向只能是"更安全"，
    > 不能是"更原始"。

63. **`#expect(...)` 里不能直接写可变调用（`session.undo()` 这类）—— 宏会把它放进闭包重算。**
    Swift Testing 的 `#expect` 会把操作数捕获成表达式再求值，遇到 `mutating` 调用会报
    `cannot use mutating member on immutable value: '$0' is immutable`。
    **修法：先算成局部常量，再断言常量。**（顺带也更可读：能看出断言的到底是什么。）

64. **吸附线不是越多越好："把所有窗口都丢进去"会让屏幕上到处都在吸。**
    40 扇窗 × 4 条边 = 160 条线；6 点的阈值下，屏幕上几乎每个位置都落在某条线的范围内 ——
    表现是"拖到哪都被吸住"，比**不吸**还难对准，而用户只会说"这框拖不动"。
    **修法：只取屏幕可见区 + 与当前选区相邻的那些窗口**（线少才吸得准）。
    同理**不收窗口中线**：想在窗口左边贴齐，结果先被窗口正中吸了一下，非常别扭。
    > 判据：任何"阈值触发"的辅助功能，先算一下**触发点的期望数量**。
    > 阈值 × 候选数 远大于可用空间时，这个功能就从"辅助"变成了"干扰"。

65. **变异测试要模拟"真实会写错的实现"，不是随便改一个字符。**
    我在选区吸附上注入过一处变异（把并列取舍的 `<` 改成 `<=` 并 `break`），**全绿通过**。
    当时差点得出"这条断言是盲的"的结论 —— 但真正的原因是那个变异**改不出错误**：
    最终位移仍由单点匹配决定，矩形不可能被拉伸。
    换成"把 x 方向改成每条边各吸各的"（有人真会这么写），立刻被 3 条断言抓住。
    > 判据：一件变异测试没变红时，先问**"这个变异到底产生了什么用户可见的错误？"**
    > 答不上来，就该换一个变异，而不是去改断言。
    > 反过来，如果一条断言**在任何变异下都不可能失败**，那才是真的空跑，该删。
    >
    > **补充（第二次踩到，2026-10-01，ticket 22）**：有一类代码**确实**没有任何可见症状。
    > 例：撤销之后把选中集合里"已经不存在的 id"清掉 —— 现有的几处 `guard` 恰好
    > 把后果挡住了（`deleteSelected` 会因为"一个都没删掉"而提前返回），
    > 所以任何**症状型**断言都是空跑。
    > 这时不要去删那段代码，也不要硬凑一个症状断言，而是**断言不变量本身**：
    > `#expect(!session.selection.contains(ghostID))`。
    > 前提是在测试里写清楚"这条守的是不变量，不是症状"，否则下一个人会把它当成冗余删掉。

66. **不要用"鼠标正按着吗"这种瞬时状态，去决定一个常驻 UI 的可见性。**
    我在覆盖层工具栏上加过一句"拖几何时收起工具栏"，判据是 `dragMode`。而 `dragMode`
    **只有 mouseUp 才会清** —— `endedDragAt` 里"重画选区"那条分支漏了重置，
    于是拖完选区后 `dragMode` 永远停在 `.select`，**工具栏再也不出现**。
    用户报的是"前面框选完成后会出现工具栏，现在没有了"—— 与"这个功能没做"一模一样。

    **修法有两层，缺一不可：**
    ① **把那条依赖整个删掉**。工具栏贴在选区**下方 10 点**，而控制点命中半径是 6 点，
       两者根本碰不到 —— 这条规则本来就没必要。删了，这一整类 bug 就不存在。
       （重画选区时工具栏本来就会消失，因为那时会话处于 `.dragging`、
       `isSettled` 已经是 false。**判"会话状态"就够了。**）
    ② 收尾只留**一个** `defer`，不在每条 `case` 里各自清。
       "每条分支各自收尾"这种写法，加第三种拖拽时一定会重演。

    > 判据：**一个只在某个事件里被重置的标志位，不允许决定任何"一直看得见/看不见"的东西。**
    > 凡是"某个 UI 再也不出现"，先查它依赖的标志位有没有一条分支漏了收尾。
    > 另外配一个**交叉验证的日志**（用一个独立事实去对：真的还有鼠标键按着吗）——
    > 这类 bug 的现象与"功能没做"无法区分，没日志就只能靠猜。

67. **"预览"与"导出"只要隔着一个坐标倍率，就必须有一条**逐像素**的回归盯着。**
    覆盖层里画标注用的是**点**，而底图是**像素**（来自冻结的整屏帧）。
    于是 `AnnotationDrawing` 多了一个 `sourceScale`，它同时作用于两处：
    裁底图的像素矩形，**以及传给滤镜的强度**（滤镜按底图像素工作）。
    漏掉第二处不会崩、不会报错，只是 2x 屏上预览的马赛克格子**小一半** ——
    而"格子小了点"会被当成强度没调对，没人会想到是倍率。
    **修法：写一条"同一个标注、同一块底图，一边按像素画、一边按点画（含倍率），
    两张图逐像素相同"的回归。** 它同时钉住了位置、格子大小、模糊半径三件事。
    > 判据：任何"两套坐标系渲染同一份模型"的地方，**逐像素比对**是唯一能提前发现
    > 漂移的手段。用肉眼看"差不多"永远不够 —— 这条正是这个项目里重复出现三次的教训。

68. **"缺数据就跳过那一块"在有脱敏语义的场景里是错的，要整体放弃。**
    打码底图是按屏拼的。我原本写的是"缺哪块就跳过哪块"，看起来更健壮
    （能出一张不完整的图总比不显示好）—— 但缺的那块会**显示成原图**，
    看着像"打码没生效"，而用户可能就这么发出去了。
    **修法：缺任何一块就整体返回 `nil`**，并让界面说清楚"预览不可用，但标记仍会写进成品图"。
    > 附带教训：这条最初只有一个**单屏**的用例，而单屏缺帧时因为"一片切片都没有"，
    > `ImageCompositing` 会碰巧返回 nil —— **测试是绿的，但没在测那件事**。
    > 变异测试（把 `return nil` 改成 `continue`）全绿通过才把它暴露出来。
    > **"测试通过"不等于"这条性质被测到了"**：跨屏那条用例补上之后立刻变红。

69. **删掉一个"过渡入口"之前，先查它是不是某个功能的**唯一**入口。**
    ticket 21 把覆盖层工具栏上的「编辑」按钮删掉（用户明确否掉了"点按钮跳进另一个窗口"），
    顺手也把 **OCR 的唯一入口一起藏了** —— OCR 的按钮一直在编辑器工具栏里，
    而普通截图从 21 起不再打开编辑器。
    现象是"OCR 好像没做" —— 与"功能确实没做"**一模一样**，
    所以用户连问两次"OCR 怎么验证"，我两次都在解释"走长截图或 `-marqueeDemoEditor`"，
    而没有意识到正确答案是：**它的入口没了**。
    > 判据：删任何"过渡 / 临时 / 快捷"入口之前，**grep 一遍那个功能的名字**，
    > 确认还有别的路能到。一张功能清单（"这个功能从哪几个地方进得去"）比重读代码快得多。
    > 这条与 PITFALLS 66 是同一族：**"某个东西再也不出现"的原因，
    > 十有八九在"它依赖的那条路被改掉了"，而不在它自己身上。**

70. **异步动作必须在界面上"动起来"，否则等于没点。**
    覆盖层的「识别文字」是异步的（首次没预热时约 25 秒）。什么都不做的话，
    用户点完看到的是一个**完全没有变化的界面** —— 那与"这个按钮是坏的"无法区分。
    修法两条：① 那一格换成 hourglass 并置灰；② 状态行的文字用**不会自动消失**的那一档
    （自动消失的文案在长任务里会先于任务本身消失，把"在跑"变成"什么都没有"）。
    > 判据：任何可能超过 200 ms 的操作，先问"用户在这段时间里看得见什么"。

71. **元组属性会破坏 `Equatable` 自动合成 —— 而且错误指向整个类型，不指向那个属性。**
    `OverlayAnnotationSession` 是 `Equatable` 的。我给它加了一个
    `private var moveAnchor: (point: CGPoint, before: [Annotation])?`，
    编译报的是 `type 'OverlayAnnotationSession' does not conform to protocol 'Equatable'` ——
    一句话指向那个**结构体**，而真正的原因是"元组不是 `Conforming` 类型"。
    **修法：用一个具名的小 struct 代替元组**（顺带也比元组好读：
    `MoveAnchor(point:before:)` 比 `(CGPoint, [Annotation])` 说得清）。
    > 附带教训：那条错误信息很容易让人去找"哪个属性不满足"，
    > 而实际上要换的是**属性本身的类型**。

72. **"收尾集中在一处"只在没人需要读它的那一刻成立 —— 要读，就得先取走。**
    覆盖层的 `endedDragAt` 原来写成"先 `switch dragMode` 分派、收尾交给 `defer`"。
    看起来比"每条分支各自清"干净多了，但分支里会调 `refresh()`，而 `defer` 要等函数
    返回才跑 —— 那几拍里 `refresh()` 读到的是**还没清掉的旧值**。
    两个后果：① 交叉验证探针误报"拖拽状态没收尾"（用户日志里连报两次）；
    ② 任何想读"这次拖拽是什么"的地方读到上一次的。
    **修法：进函数先 `let drag = dragMode; dragMode = .none`，再 `switch drag`。**
    > 反过来说，我第一版写 `defer` 的结果是：每条需要读它的 `case` 里又各自补了一句
    > `dragMode = .none` —— 也就是说"集中收尾"根本没成立，只是换了个地方分散。
    > **判据：一个状态如果在同一段逻辑里既被"收尾"又被"读取"，它就不能靠 `defer` 收尾。**

73. **探针报"没清干净"时，第一件事是问"它是在哪个时刻被读到的"，不是去找哪条分支漏了写。**
    第 72 条那次，探针的原话是"说明有条分支漏了 `defer` 收尾" —— 而真因是
    **读取时机**。我按那句话去找分支，找错了方向。
    > 附带：探针挂在高频路径（`refresh`）上时**必须自带去重**，
    > 否则一次泄漏会把日志刷满，反而看不出它第一次是什么时候出现的。

74. **局部变量名撞上属性名：只有两个类型"恰好没有同名成员"时才会报错。**
    我在 `endedDragAt` 里写了 `let mode = dragMode`，而控制层自己有一个 `mode: Mode`
    （采集模式）—— `mode == .scrollCapture` 立刻编不过（`DragMode` 没有这个成员）。
    **但这是运气**：如果哪天两个枚举有了同名成员（比如都叫 `.select`），
    这里会**悄悄换成另一个含义**，编译器一声不响。
    > 判据：给局部变量起名之前，扫一眼同类成员里有没有同名的。

75. **编辑器里能用的东西，覆盖层里不一定能用 —— 但也不一定不能用，要**测**。**
    「文字工具」卡了很久，卡点是一个未知项：**覆盖层的 `.nonactivatingPanel` 到底能不能
    成为 key window**（`NSTextField` 的前提）。文档说能，而本项目有一条反证
    （视图的 `keyDown` 曾经完全收不到 `⏎`，见 PITFALLS 56）。两者对不上。
    **做法：加一条探针把未知项变成可测的数据。**
    ```
    覆盖层焦点：panel.isKeyWindow=true firstResponder=true app.isActive=true
    ```
    用户跑一次覆盖层就定案了 —— `true`，于是直接用真的 `NSTextField`
    （中文输入法的候选窗 / 联想 / 光标全都白拿）。
    > 代价对比：靠猜的话，要么猜错（自绘输入框 → 自己实现一遍输入法，无底洞），
    > 要么白做一轮。而探针是**几行代码 + 用户跑一次**。
    > 判据：**当"能不能"取决于平台行为而不是你的代码时，先写探针，别写猜测。**

76. **本地键盘监听会吃掉输入框里的每一个字 —— 有输入框在编辑时必须整条让行。**
    覆盖层的键盘全部走应用级 `NSEvent.addLocalMonitorForEvents`（PITFALLS 56 的结论）。
    而本地监听在事件到达窗口**之前**就跑：不让行的话，用户敲的每个字都被当快捷键吞掉，
    表现得像"输入框是坏的"。
    **修法：编辑期间只拦 `Esc`，其余（含 `⏎`、`⌘Z`、输入法选词的上下键）全部返回"未消费"。**
    > 与之配套的一条产品决定：**"结算"（把内容落成标注）≠"丢弃"**。
    > 点工具条、点别处、按 `⏎` 都是结算；只有 `Esc` 才丢。
    > 这个区别要写在代码注释里，否则以后有人"顺手"把换工具时的结算改成丢弃，用户的字就没了。

77. **一个"点一下放下"的工具混进"拖一笔"的通道，会得到一个宽度等于拖拽距离的空框。**
    文字工具和矩形共用"选工具 → 按下 → 拖 → 松开"这条通道，但文字的落点是**点**，
    内容在事后才输入。放进同一条通道，用户按住鼠标拖一下就会得到一个
    `宽度 = 拖拽距离` 的空文字框 —— 而正文一个字都还没输。
    **修法：`OverlayTool.isStrokeBased`（`draws && self != .text`）当闸门。**
    > 判据：凡"有 kind 的工具"都自动能画一笔的写法，一定会在第一个
    > "放下方式不同"的工具上出事。**给"怎么放下"留一个显式判据**，别让它默认。

78. **同一排控件按上下文换意义时，把"意义"做成一个枚举 —— 别让各处自己 `switch` 工具。**
    覆盖层那三档尺寸有三处用户：控制层（改哪个字段）、视图（画成圆点 / 方块 / 字号）、
    以及默认值。三处各自写 `tool == .mosaic || tool == .blur` 的话，
    加第四种含义时一定会漏一处 —— 而漏掉的表现是"某一档点了没反应"。
    **修法：`OverlaySizeMeaning`（线宽 / 打码强度 / 字号），带 `values` 与 `defaultValue`，
    三处都从它取。** 顺带留两条断言：**三组档位必须一样长**（格子数是按其中一组建的）、
    **每组的默认值必须落在自己的档位里**（否则一进来三档全不高亮）。

79. **复用一套"按另一套坐标系命名"的几何工具之前，先读它**哪一端叫 top**。**
    标注缩放想复用 ticket 19 那套 `SelectionGeometry`（控制点、对边固定、最小尺寸停住、
    `⇧` 锁比例）—— 但它整个是按 **Cocoa 约定**写的：`.top` = **`maxY`**（y 向上），
    而 `Annotation` 的坐标系是"原点左上、y 向下"。
    直接复用的话，用户拖"上边"动的是**下边** —— 不崩、不报错，
    而且只在拖到极限或锁比例时才显得怪。
    **修法：`SelectionGeometry.YDown.flip(rect/point)` 这一层显式适配，进去翻一次、出来翻一次。**
    翻转是**对合**的（`flip(flip(x)) == x`），所以不会引入额外状态。
    > 有一对测试专门钉住它："控制点按标注坐标系摆" + "拖左上角时右下角不动"。
    > **变异验证**：把两处翻转分别去掉 → 8 条断言变红（两轮都验过）。
    > 判据：凡"复用别人的几何/布局工具"，第一步是找它的**原点在哪、哪一端叫 top**，
    > 而不是先接上去看效果 —— 接错了的现象是"方向反了"，而方向反了在拖到极限前都"看着挺对"。

80. **光标区（`addCursorRect`）是一份**快照**，它不会自己跟着新加的控件走。**
    给标注加上 8 个控制点之后，控制点画出来了，但鼠标移上去仍是十字 ——
    要等下一次"别的变化"才刷新。
    原因：`resetCursorRects` 只在 `presentation` 的**某几个字段**变化时被
    `invalidateCursorRects(for:)` 触发，而新加的 `selectedAnnotationHandles` 不在那个条件里。
    **修法：把新阵列加进 `didSet` 的比较条件。**
    > 判据：凡是"看得见的控件 + 摸得到的命中区"分开维护的地方，
    > **两边的刷新条件必须一起加** —— 只加一边的表现是"看得见、摸不着（或摸起来是别的光标）"。

81. **墙钟性能断言的抖动会让整个测试套件失去可信度 —— 取"多次里最快的一次"。**
    有一条"单次打码耗时 < 50 ms"的用例，在**同时还在编译别的东西**的时候偶发变红
    （实测抖动到 >50 ms，而单独跑是 0.2 ms）。
    它红的次数不多，但危害很大：**"红了一次又自己变绿"会让人开始怀疑所有断言** ——
    那比少一条用例糟得多（这个项目里"测试不空跑"是核心纪律）。
    **修法：跑 5 次取最小值再断言。** 最小值里没有"被打断"的成分，是微基准的通行做法。
    实测：马赛克 0.29 ms / 模糊 0.41 ms，预算是 50 ms（170 倍余量）——
    它现在只在真的坏掉时才红。
    > 判据：**任何拿墙钟时间做断言的用例，先问"别人机器忙的时候它会不会红"**。
    > 会的话就要么去掉、要么改成"取最快 / 中位数"，并且把余量留到几十倍。
    > 顺带：这类用例的断言本身仍然要验活（把预算改成 0.001 ms → 必须变红）。

82. **把"基准"的更新塞进一个每次更新都会跑的公共函数里，拖动就会越拖越快。**
    钉图控制条的拖动要"起始位置 + 总位移"。我把 `dragStart = 当前位置` 写进了
    `apply()` —— 而 `apply()` 在每一帧拖动里都会被调用。于是：
    第 1 帧 `起始+位移₁`，第 2 帧变成 `(起始+位移₁)+位移₂`…… **位移被反复累加**，
    表现是"拖一下它飞出去"。
    **修法：基准只在 `mouseDown` 那一刻取一次**（`onDragBegin`），
    `apply()` 里绝不重取。
    > 判据：**"每帧累加"与"以基准重算"混在一起时**，先问"这个基准是在哪一刻确定的、
    > 有没有可能被别的调用顺手改掉"。`apply()` / `refresh()` 这类"谁都会调"的公共函数，
    > **不适合放基准的更新**。（与移动/缩放的"基准取按下那一刻"是同一条道理，
    > 只是这次的破坏来自一个无辜的公共函数。）

83. **`ignoresMouseEvents = true` 没有回头路 —— 必须有**另一个窗口**当出口。**
    钉图的"鼠标穿透"只能整窗生效。而穿透一旦打开，那个窗口就收不到任何鼠标事件，
    也就**点不到自己身上那个开关**。用户会卡在"图挡着、点不动、也关不掉"。
    **修法：控制条做成一个独立的小窗口，它永远可交互** —— 那是唯一的出口。
    代价是每张钉图有两个窗口，收益是"穿透"这个功能真的可逆。
    > 判据：**任何"让某个东西不响应输入"的开关，先问"那谁负责把它关回去"**。
    > 关不回去的开关，比没有这个开关糟糕得多 —— 用户只能强退应用。

84. **`CGImage` 画进 `NSView` 要 `respectFlipped: true`，否则图是**上下颠倒**的。**
    `NSImage.draw(in:from:operation:fraction:)` 在 AppKit 的非翻转坐标系里默认按
    "图像左上角对视图左下角"映射 —— 不写 `respectFlipped: true`，钉出来的图会是倒的。
    它不崩、不报错，只是图反了（而"图反了"很容易被当成"截图截反了"去查采集）。
    > 这是 PITFALLS 里"位图行序 / CTM 翻转"那一族的 AppKit 版本。
    > 判据同旧：**凡是把位图画进某个坐标系，先确认"哪一行先被读出来"。**

85. **`UserDefaults.bool(forKey:)` 在 key 不存在时返回 `false` —— "默认打开"的项会变成默认关闭。**
    而且**只在全新安装时**表现出来：开发机上那个 key 早就被别的运行写过了，
    于是你测不出来，用户第一次装就发现"截图后没有声音"。
    **修法：`defaults.object(forKey:) as? Bool ?? 默认值`。**
    > 判据：**"没存过"与"存了 false"必须能区分**。用 `bool(forKey:)` / `integer(forKey:)`
    > 这类"有默认返回"的 API 时，先问一句"这个默认值我要的就是它吗"。
    > （已有一条测试专门钉住它。）

86. **写新接缝之前先想清楚它属于谁：**接缝归 Core**，实现归实现模块。**
    `CaptureHistoryWriting` 我一开始写在 `MarqueeHistory` 里，而 `CaptureOutput` 在 Core
    要用它 —— 于是形成 `Core → History → Core` 的循环。
    这次是编译器立刻拦下的（**不是**"悄悄错"那类），但它值得当规则记：
    Core 是唯一无依赖的一层，因此**任何被 Core 调用的东西，协议都必须落在 Core**。
    > 与 `ClipboardWriting` / `ScreenCapturing` / `PostEventPermission` 同一套做法 ——
    > 项目里已经有三处先例，照着抄就不会错。

87. **列表行里的动作绝不能"按下标去找条目"。**
    最近截图面板每行都有「编辑 / 删除」。如果按钮的 action 收到的是行号，
    那么**列表在用户点下去之前就重建过**（删了一条、或新截了一张）时，
    删掉的就是另一条 —— 而用户只会说"我删了 A，结果 B 没了"。
    **修法：把条目的 `id` 捎在按钮上（`identifier`），动作按 id 去查。**
    > 判据：任何"列表 + 每行动作"的地方，**动作必须携带条目的身份**，不是它在列表里的位置。

88. **缩略图不要"先把整图加载出来再缩小"。**
    一张 5K 全屏截图解码出来是几十 MB；最近截图面板列 12 张就是几百 MB，
    面板一打开就会卡住 —— 而 symptom 是"点「最近截图」没反应"，
    看起来像菜单坏了。
    **修法：`CGImageSourceCreateThumbnailAtIndex`** —— 它只解码到目标尺寸，
    代价与**目标大小**成正比、与源图大小无关。
    > 判据：凡"从一个大文件里取一个小预览"，先看有没有"按需解码到目标尺寸"的 API（ImageIO 有）。

## K. 外观、材质与视图层叠（ticket 17a）

> 这一组是 2026-10-01 做「悬浮面板换系统材质」时定下来的约束。
> ⚠️ 开发机是 **macOS 27**，所以 `NSGlassEffectView` 那条路是**实际生效**的、
> 可以肉眼验；15.x 的 `NSVisualEffectView` 降级路只能靠 `chrome.forceHUD` 强制走一遍来验。

89. **AppKit 的绘制顺序是「自己的 `draw` → 子视图」，子视图永远画在父视图自己画的东西之上。**
    想给一块"自己画内容"的区域换背景材质时，直觉是"给它挂一个材质子视图"——
    结果**内容是父视图画的、材质是子视图画的**，材质把内容整个盖住。
    表现是"工具条变成一块糊的东西、图标全不见了"，而且不报任何错。
    **修法：拆成两个兄弟子视图 —— 背景先 `addSubview`、前景后 `addSubview`**，
    两者 frame 相同，前景只画描边/分隔线/图标（`ChromeForegroundView`）。
    > 判据：任何"背景要换成系统材质"的地方，先问一句「这块内容是谁画的」。
    > 是父视图画的，就必须把它挪到与背景**并列**的一层去，不能挂在背景下面，也不能挂在自己身上。
    > **加子视图的顺序就是层叠顺序**，反了就是"背景盖住按钮"（钉图控制条就是这样）。

90. **`NSVisualEffectView` / `NSGlassEffectView` 默认会参与命中测试，会把鼠标事件吃掉。**
    把它们直接当子视图挂到一块靠 `mouseDown` 工作的视图上，表现是
    **"按钮看得见、点它没反应"** —— 与「入口没接线」的现象一模一样，很容易查错方向。
    **修法：包一层 `hitTest` 恒为 nil 的容器**（`ChromeBackground.makeBackgroundView`）。
    > 判据：只用来"给人看"的视图，一律不许出现在命中链上。

91. **悬浮面板的材质必须用 `.behindWindow`，不能用 `.withinWindow`。**
    覆盖层的面板底下是**变暗蒙层**（同一窗口内画好的东西）。
    `.withinWindow` 会拿那层纯色当素材去糊，糊出来还是一片纯色 ——
    看起来"材质没生效"，而其实生效了、只是没有可模糊的内容。
    `.behindWindow` 取的是**窗口背后**的屏幕画面，那才是有东西可糊的一层。
    > 前提：面板窗口本身是 `isOpaque = false` + `backgroundColor = .clear`（本项目一直都是）。

92. **材质是半透明的，必须自己垫衬底 —— 否则"两种系统上都可读"这条验收会挂。**
    玻璃与 HUD 材质都会透出下面的内容；压在一张纯白网页上时白字会糊到看不见。
    **修法：15.x 路在 `layer.backgroundColor` 垫一层黑、26+ 路给 `tintColor` 一个黑着色**，
    两者的强度都从 `ChromeStyle` 取（**同一套值**）。
    > 反例的教训：如果两条路各写各的常量，就会出现"26 上看着挺好、15 上字看不清"——
    > 而这种差别只有换机器才看得出来。

## L. 本地化（ticket 17b）

93. **本地化最容易的失败形态不是崩，而是「不崩不报错，只是英文用户看到中文」。**
    没有日志、没有报错，只有换台机器（或换系统语言）才看得见 —— 所以判据**必须是可执行**的：
    一条扫描测试，检查"生产代码里没有未包 `L10n.t` 的中文字面量"＋"源码用到的 key 都在 catalog 里"。
    > 判据要看**整体数量**，不是逐处看。漏翻恰恰是那种"每一处单独看都没问题"的错。

94. **插值文案不能「先拼好再查表」。**
    ```swift
    L10n.t("已复制 \(text)")        // ✓ 编译器把 key 记成 `已复制 %@`
    L10n.t("已复制 " + text)         // ✗ 查的是渲染后的串（"已复制 #FF0000"），永远匹配不上
    L10n.t(String(format: "已复制 %@", text))   // ✗ 同上
    ```
    错法**不崩、不报错、不警告**，只是那些句子在英文环境里仍然是中文。
    > 前提是 `L10n.t` 收的是 `String.LocalizationValue`（可被插值），而不是 `String`。
    > 收 `String` 的签名会让上面三种写法**看起来一样**，等于把坑埋进类型里。

95. **自己写源码扫描器时，行号会因为「行继续」而整体漂移。**
    多行字面量里 `\` 结尾换行的续行也是**一个换行**；扫描时漏计一次，
    后面所有报错的行号就整体前移 —— 而"报错指向别的行"会让**每一条诊断都变成误导**，
    比不报还糟。
    > 判据：扫描器报出行号之后，**先打开那一行看一眼**。第一次用就该对，不该"大概齐"。

96. **扫描器的两趟用途要用两套规则：收集 key 时不能看行标记。**
    `logger.info("…\(L10n.t("历史：重新合成失败"))")` 这种行里，被包过的 key **是算数的**；
    如果因为"这一行是日志"就把整行跳过，那条 key 会变成"孤儿"，然后**误报**成"catalog 里有没人用的条目"。
    > 规则要按**问题**分，不是按行分：行标记回答的是"这里的裸中文要不要翻"，
    > 不是"这一行的 key 算不算"。

97. **给扫描器本身写一条自检**（喂一段含目标特征的小样本，断言它认得出来）。
    没有这条，一个"什么都扫不到"的扫描器会让上面所有断言**全绿** ——
    绿灯的来源从"代码干净"悄悄变成了"检查没生效"，而这两者在输出上完全一样。

## M. 工具条与弹层（ticket 24）

98. **用例的参数要覆盖「最坏情况」，不是「典型情况」——否则断言是盲的。**
    我给「弹层必须留在屏幕内」写的第一版用例是"大屏 + 四个角"。那种参数下弹层**怎么放都放得下**，
    于是把 `paletteFrame` 里那段夹取**整段删掉**，测试**照样全绿**。
    补了"屏幕只有 140 点高"的用例之后，同一个变异立刻变红（4 条 issue）。
    > 变异不红时，除了 PITFALLS 65/68/73 那三问，再加一问：
    > **「我给的这组参数，有没有可能让那条路径真的被走到？」**
    > 典型参数（大屏、居中、内容不多）几乎永远走不到兜底分支。

99. **弹层的命中判定必须排在它**压着**的东西前面。**
    弹层是从工具条往外弹的，它会与工具条、选区、甚至别的面板重叠。
    按"工具条优先"的既有顺序判，点在重叠区就会被工具条吃掉 ——
    表现是"面板上的那个色点不动"，而面板看起来完全正常。
    > 修法：`mouseDown` 里**先判弹层、再判工具条**，两者都用各自的矩形整体判定（含空隙）。

100. **「把某个入口收掉」与「把某个能力删掉」是两件事，别顺手一起做。**
    这一票收掉了「选择」这个工具位与「模糊」这个工具位。做法是：
    - 「选择」：格子没了，但**能力改成隐式**（没选工具时按在标注上就选中它）——
      `isSelecting` 从 `tool == .select` 改成 `tool == nil`，分派顺序一字未动。
    - 「模糊」：格子没了，但 `AnnotationKind.blur` 与它的渲染/导出/编辑路径**一行未动**，
      编辑器里仍然有。
    顺手把 `AnnotationKind.blur` 也删掉的话，**已经存在的老数据会解读不了**，
    而"删一个枚举值"在编译期是绿的、只在读旧文件时才炸。
    > 判据：**删入口前，先问"模型里还有谁认它"**。模型是数据契约，UI 是入口，两者的生命周期不一样。

## N. 判据的适用前提（ticket 25 的回归）

101. **`nil` 兜底会**悄悄**把一个"不适用"变成"合法值"，而判据从此永远成立。**
    ```swift
    annotationPoint(globalPoint) ?? .zero     // ← "没有画布"变成了"画布左上角 (0,0)"
    ```
    于是"按在空白处"这类判据在**任何**状态下都成立 —— 包括根本没有画布的时候。
    ticket 24 就是靠这个把"自由框选"整条路堵死的：
    `dragMode` 被占成"画一笔"，草稿却没开始，现象是**拖着鼠标什么也不出现**。
    > 判据：**`?? 默认值` 之前，先问一句"这个默认值在业务上成立吗"。**
    > 不成立就别兜底，让 `nil` 一路传上去、逼调用方显式处理。
    > （这类错的可怕之处在于它**编译期全绿、运行期也全绿**，只是功能没了。）

102. **改一个"判据常量"的**含义**之前，先把它的所有使用者列出来。**
    `isSelecting` 从 `tool == .select` 改成 `tool == nil` 看起来只是"换了个等价条件"，
    但**两者的触发频率差了一个数量级**：前者要用户主动点一下，后者**默认就成立**。
    于是所有"只在特定模式下才走到"的分支，全都变成了"每次都走到"。
    > 判据：条件表达式等价 ≠ 运行路径等价。**默认值也是值。**

103. **把一块绘制从父视图搬到独立子视图之后，它的重绘时机就归你自己管了。**
    以前工具条画在父视图的 `draw` 里，父视图那条"只重画光标周围一小块"的快路径**天然**绕开了它；
    搬到子视图之后，每次 `presentation` 变化都去 `needsDisplay = true`，
    等于**鼠标一动就整条重画**（一次 15 个图标）。
    > 修法：记住上次同步过去的值，**真的变了才碰子视图**。

104. **`NSImage(systemSymbolName:)` 不是"取一个图标"，是"造一个图像"。**
    放在 `draw` 里就是每帧造一次；加上 `withSymbolConfiguration` 更贵。
    这种"看起来像个 getter、其实是 alloc"的 API，是绘制热路径上最常见的隐形开销。
    > 缓存键要带上**外观**（`effectiveAppearance.name`）：动态色解析出来的位图随外观变。
    > 取颜色分量用 `usingColorSpace(.sRGB)`，**不要用 `.redComponent`** ——
    > 后者对动态色（`controlAccentColor`）会**抛异常**，而异常在绘制回调里会直接崩。

## O. 鼠标光标（ticket 26）

> 用户的原话是「需要调整鼠标箭头，目前都是十字」。根因是一条
> `addCursorRect(bounds, cursor: .crosshair)` —— **一块整屏的十字**，
> 只有选区控制点靠"后加的赢"压在上面。工具条按钮、已有标注、选区内部全被它盖住了。

105. **十字是一种「含义」，不是一种「底色」。**
    它只在"**可以拉 / 重画选区**"和"正在画标注"时才是对的；其余场合它什么也没说，
    用户只能靠试。把整屏铺成十字，等于**取消了光标的全部语义** ——
    而它看起来像是"做了"，因为屏幕上确实有个光标在那儿。
    > 判据：任何"整块区域一个光标"的写法，先问一句「这块区域里**所有地方**
    > 的含义都一样吗」。不一样就得按位置分派。

106. **命中规则比矩形更细时，光标不能靠 cursor rect 表达。**
    cursor rect 只能给矩形；而"压着某个标注"要按**形状**判（斜箭头的包围盒里
    大半是空白，画笔是一条折线）。用包围盒近似的后果是
    **"箭头旁边的空白处也伸出一只可拖的手，点下去却什么都没选中"** ——
    比不做还糟，因为它在骗人。
    > 修法：光标改成**按点问规则**（`OverlayCursor.kind(at:in:)`），
    > 在 `mouseMoved` / `mouseDragged` / 状态变化三处各问一次。
    > 规则本身放 Core，就能脱离屏幕单测。

107. **`mouseDragged` 里也要更新光标 —— 拖拽期间根本不会有 `mouseMoved`。**
    只在 `mouseMoved` 里更新的话，**拖动过程中光标会僵在按下前那一个**
    （拖控制点时一直是十字、拖选区时一直是张开的手，直到松手才变）——
    而拖动恰恰是最需要反馈的时候。

108. **状态变了但鼠标一动没动时，光标也得跟着变。**
    控制点、工具条、弹层都是"鼠标停着不动"的时候出现的。
    只在鼠标事件里更新光标，用户看到的是"它出来了、但看起来还是不能用"。
    > 修法：`presentation` 变化时用 `NSEvent.mouseLocation` **补问一次**。

109. **多屏时"谁设光标"必须有唯一答案。**
    光标是系统级的，而每块屏一个覆盖层视图 —— 每个视图都设一次的话，
    结果变成"**最后刷新的那块屏说了算**"，而鼠标在另一块屏上。
    > 修法：设之前先判「自己这块屏的 bounds 是否包含该点」，不包含就什么都不做。

110. **同一个光标值不要每帧重设。** `NSCursor.set()` 是即时的，
    鼠标移动是每帧来的 —— 每帧重设一次会让光标**闪**，看起来像系统卡了一下。
    > 记住上一次设的值，一样就跳过。

## P. 档位与图标（ticket 27）

111. **"三档"的视觉大小不能按数值线性映射 —— 相邻两档会挤在一起。**
    编辑器与覆盖层的尺寸档原先是 `4 + value * 1.4` 再夹到格子上限。
    线宽 2/4/8 还能分开，但**打码强度那三档是 4/8/16**：
    算出来 9.6 / 15.2 / 16 —— 后两档差 0.8 点，在 20 点的格子里**看不出区别**。
    用户点了"最强"却毫无变化，只会以为那一档没生效（它其实生效了）。
    > 修法：按**档位序号**均分（`SizeSwatchGeometry.relativeSide`），
    > 与数值彻底解耦 —— 数值是给导出算的，画多大是给人看的。
    > 判据：给"几档并排"的东西写断言时，要断言**相邻两档的差足够大**
    > （我写的是 `> 0.15` 且最大 ≥ 最小 × 2），而不是只断言"递增"。

112. **图标名不要凭记忆写 —— 不存在的 SF Symbol 是「静默画不出东西」。**
    `NSImage(systemSymbolName:)` 对不存在的名字返回 `nil`，`Image(systemName:)` 画出来是空白。
    **不报错、不警告**，只是那一格看起来"就是没有图标"。
    这次挑字母/序号图标时，`text.number` 就不存在 —— 靠记忆写下去，
    结果是一格空白，而我大概会去怀疑布局算错了。
    > 做法：先跑一个探针，把候选名字逐个 `NSImage(systemSymbolName:)` 一遍再定
    > （和 ticket 17b 探测格式说明符同一套办法）。
    > 顺带：**测试里也钉不住这个** —— 它要真机上的图标库，属"只能靠探针 + 肉眼"的一类。

## Q. 图标（ticket 28）

113. **SF Symbol 会自动本地化 —— 名字一个字没错，画出来的却不是图标。**
    有些符号有**中文本地化变体**，系统按应用语言自动替换。实测（macOS 27 + zh-Hans）：

    | 名字 | 中文下画出来 |
    | --- | --- |
    | `textformat` | **两个字「格式」**（变体 `textformat.zh`） |
    | `character` | 字 |
    | `textbox` | 文 |
    | `textformat.size` | 大小 |
    | `textformat.abc` | 甲乙丙 |

    夹在一排图标里的两个汉字，看起来像"代码里写错了"，而名字一个字都没错 ——
    **这一条靠读代码看不出来，只能渲染出来看。**
    > 修法：文字工具改用 `t.square`（两种语言下都是"方框里的 T"，也正好是参考工具条那一格）。
    > 选图标时**必须在 zh-Hans 下渲染一遍**再定：`Tools/SymbolProbe/run.sh`。
    > 顺带两件事：① `text.viewfinder`（识别文字）中文下是「文」在取景框里 ——
    > 这是**预期**，别去"修"它；② 本地化按**应用声明的本地化**判定，
    > 裸二进制永远按英文渲染（`-AppleLanguages` 也改不动），
    > 探针必须放进一个声明了 zh-Hans 的 bundle 里才测得到。

114. **多色符号在 `paletteColors` 下会被「整片填充」。**
    `NSImage.SymbolConfiguration(paletteColors:)` 会把**第一层**刷成那个颜色。
    对 `face.smiling` 这种首选多色渲染的符号，第一层就是整张脸 ——
    画出来是**一个实心圆点**。它看起来只是"这个图标长得怪"，
    完全想不到是着色方式的问题（我第一反应是去查布局是不是算错了）。
    > 修法：配置上加 `.preferringMonochrome()`。我们本来就要"整格一种颜色"，
    > 所以单调渲染是**意图**而不是降级。逐格对比过：除 `face.smiling` 外其余完全一样。

115. **「有弹层开着就点亮某一格」是错的判据 —— 弹层不止一个。**
    「样式」格原先是"只要有弹层开着就亮"，而弹层有两个（样式、表情），
    于是打开**表情**面板时「样式」也一起亮（用户报的第三个问题）。
    这类错很温和：不崩、不报错，只是多亮一格 —— 而它只有把两个面板都开一遍才看得出来。
    > 修法：判据抽进 Core（`OverlayToolbarHighlight.isLit(_:activeTool:openPalette:)`）并单测。
    > 判据的写法是：**点亮必须由"这一格自己的状态"决定**，
    > 不能由"有没有别的东西开着"决定 —— 后者会随着"别的东西"变多而悄悄出错。
116. **文案目录会被 Xcode 在构建时重写，并把**全部**条目标成 `extractionState: stale`。**
    本项目的中文字面量几乎都在 **SPM 模块**里（`Modules/Sources/…`），
    而 catalog 挂在 **App target** 下 —— Xcode 的字符串抽取是**按 target** 做的，
    所以 App target 那次抽取看不到模块里的 `L10n.t(...)`，于是把 187 条全标成
    "源码里找不到"。**这个标记是错的，别照着它清理。**
    > 后果：① 构建后 `git status` 里 catalog 永远是脏的（格式 + 全量 stale），
    > 所以它的"当前状态"就该按 Xcode 重写后的样子入库，别去和它较劲；
    > ② **不要用 Xcode 的「Extract Strings」当这个项目的抽取工具** ——
    > 唯一可信的是 `LocalizationScanTests`（扫源码 ↔ 扫 catalog 双向对比）与
    > 生成 catalog 的那条脚本。
    > 判据：catalog 里条数对不对，**别数文件行数**（Xcode 重排会翻倍），
    > 解析 JSON 数 `strings` 的键。
    > **补记（ticket 29）**：生成 catalog 的脚本原先只存在于 `/tmp`，`ROOT` 还写死了
    > 本机绝对路径 —— 那就是"**唯一的生产工具放在临时目录里**"。
    > 已收进 `Tools/L10nCatalog/`（相对路径 + `run.sh`）。
    > 判据：一个东西如果是**唯一**能产出某件交付物的工具，它就不许在 `/tmp` 里。

## R. 测试与工具（ticket 29/30）

117. **变异不变红有两种可能：断言是盲的，或者那段代码是死的。**
    两种的处理**完全相反** —— 前者要补用例，后者要**删代码**。
    写许可状态机的天数计算时，我写了 `min(duration, max(1, raw))` 并配了一段
    "下限很重要：剩 0.3 天要说 1 天"的注释。变异时把 `max(1, …)` 删掉 ——
    **18 条测试一条都没红**。查下来是 `raw = Int(ceil(rem / 86400))`，
    而调用点已经保证了 `rem > 0` ⇒ `ceil` 对任何正数都 ≥ 1 ⇒ **那个夹取永远不生效**。
    > 判据：变异不变红时，在"补用例"之前先问一句
    > **「这个变异是不是等价的？」** —— 等价就意味着那段代码没人用。
    > 而"死代码 + 一段说它很重要的注释"比没有更糟：下一个人会照注释去维护它。
    >
    > 反过来的教训同样成立：**"我加了个防御"与"这个防御真的会生效"是两件事。**
    > 前者靠写，后者只能靠变异验证。

118. **只有校验器、没有生成器，等于把生成器留在了临时目录里。**
    本项目的文案目录有一整套**校验**（`LocalizationScanTests` 6 条，双向比对源码与 catalog），
    但**生成**它只有一份临时脚本，还写死了绝对路径。校验器能告诉你"错了"，
    却**不能帮你改正** —— 一旦生成器丢了，187 条翻译就只能手工重做。
    > 判据：一套工具链里，**"读"的那半容易被留下来，"写"的那半最容易被忘在临时目录**。
    > 补齐的办法是把生成器一起收进 `Tools/`，并把路径改成从脚本位置推导。

119. **图标要按每个尺寸原生渲染，不要缩图。**
    从 1024 缩到 16 点，虚线与圆角会糊成一片灰。`Tools/IconGen` 用同一份几何、
    按目标像素重画（`cgContext.scaleBy`），十档全部原生出。
    > 附带两条与图标有关的硬事实：
    > ① **macOS 的图标网格是 1024 画布里 824×824 居中、圆角约 185** ——
    >   不按它做，图标在 Dock 里会比别人大一圈或小一圈，而那种偏差说不清哪里不对；
    > ② **低 alpha 的幅向渐变在 8 位色深下会出可见色带**（第一版"中央柔光"就是这样）。
    >   要用**线性**渐变 —— 它只有一条轴，没有等值线圈。

120. **`lineWidth = 0` 不是"不画线"，是"1 像素的发丝线"。**（CoreGraphics / AppKit 同源）
    做图标工具时想试"只画四个角、不画框"，把 `lineWidth` 设成 `0` —— 结果
    **框还在**，只是变成一根极细的线，看起来像"模板里本来就有的装饰"。
    > 判据：任何"把线宽设成 0 就等于隐藏"的假设都要改掉。真要隐藏就不 `stroke()`，
    > 或者把颜色设成透明。这条在产品侧同样成立 —— 标注线宽是用户可配的，
    > 哪天允许配到 0，用户得到的不是"没有边框"，而是一根发丝线。

121. **"哪一档真的出问题"要渲染出来看，别按"看起来都不够大"划档。**
    图标的小尺寸分档，我一开始划在 96（把 16/32/**64** 都当成"小档"），
    于是 64 那档被改成"粗虚线 + 大控制点" —— 渲染出来一看，
    虚线断成了一颗颗**獠牙**（虚线起点正好落在四角控制点上，两者一叠就散架）。
    而**64 本来就是好的**。改成 48 之后（只动 16 与 32），64 及以上一个字节没变。
    > 判据：分档的依据是"**这一档渲染出来确实坏了**"，不是"这一档看着不够大"。
    > 改小尺寸的画法时，**先把每一档单独渲染出来比一遍**，
    > 再决定哪几档需要另一套 —— 而不是先划一个看起来合理的范围再一起改。
    > （同一个道理在 ticket 16 的"最近截图上限 20 / 面板 12"上也踩过：
    > 两个数字看着不一致，其实各有各的理由。）

## S. 改名与身份（ticket 31 第 0 步）

122. **批量替换会改掉那些「本来就要用旧名字」的地方 —— 测试里的旧标识符往往不是漏改。**
    把 `dev.tango.Marquee` 全量换成 `com.tango.Marquee` 时，脚本顺手改掉了
    `AppIdentityTests` 里的一条断言：那条**故意**拿旧 id 当反例
    （"前缀里的 `dev` 不该被当成开发版"）。改完之后它变成了与上一行**重复**的断言 ——
    测试还是绿的，但它测的东西已经没了。
    > 判据：**批量替换之后，逐条看 diff 里"被改动的断言"**。
    > 凡是"断言里出现旧名字"，先问一句：这是漏改，还是它**就是那个反例**？
    > （同一个坑的另一面：改名脚本也应当**跳过测试文件**，人工决定每一处。）

123. **写死的标识符是「只有改名时才会暴露」的那类债，而且症状离原因很远。**
    `scripts/build.sh` 里有 `codesign --identifier dev.tango.Marquee` 一句 ——
    它写死了 bundle id。改 bundle id 时漏掉它的表现是
    **"屏幕录制授权又留不住了"**，与"改过 bundle id"在现象上完全联系不起来
    （那一步当初加进来，正是为了修"授权留不住"）。
    > 修法不是"记得改"，是**把它变成派生的**：从产物的 `Info.plist` 读
    > `CFBundleIdentifier`，于是它永远跟着实际构建走。
    > 判据：任何"从别处能推出来的常量"都不该被写第二遍 ——
    > 一写死就多了一个会分叉的地方，而分叉的症状通常出现在离它很远的地方。

124. **`Dev` 与 `Release` 必须是同一套优化设置 —— 否则"性能预算"的数字换了配置就不可比。**
    为了隔离身份，Run 从 `Release` 换到了新的 `Dev` 配置。如果 `Dev` 是未优化构建，
    那么"落点→剪贴板 ≤150 ms""选区拖拽 120 fps"这些数字在两个构建之间就没法比 ——
    而当初 Run 走 Release，本来就是为了让这些数字有意义。
    > 落实的办法不是"记得同步两个配置"，而是**验证它们逐项一致**：
    > 生成工程之后把两份 `XCBuildConfiguration` 的 `buildSettings` 摊开对比
    > （本项目实际比了 53 项）。差一项都要有理由。

## T. 权益与商店（ticket 31）

125. **「撤销」是可以被撤销的 —— 任何把它记成永久状态的实现都会在这里失败。**
    Apple 的文档写明：退款被撤回之后，交易上的撤销字段会被**移除**，访问权限要恢复。
    所以同一笔交易在不同时刻会给出不同答案，判定必须每次都重算。
    > 反过来说：**"曾经被撤销"不许进任何"永久拉黑"的集合**。
    > 我在 `StorefrontMapper` 里没有留任何累积状态（每次从商店的当前事实重算），
    > 并为此写了一条回归测试（`revocationIsReversible`）—— 因为"顺手加个 `hasBeenRevoked` 缓存"
    > 是这类代码最常见的"优化"，而它的代价是**把一个已经恢复购买的用户永久锁在外面**。

126. **「商店里没有」只有在**真的问过**之后才算证据。**
    查询失败（断网 / 商店报错 / 还没查完）时，`records` 恰好也是**空数组** ——
    与"这个人确实没买过"长得一模一样。照它判，就会**把付过费的人在断网时锁在外面**。
    > 修法：`StorefrontMapper` 的文档里把"只在真的问过商店之后调用"写成硬前提，
    > 查询失败走**另一条路**（直接用缓存里那份输入），根本不进映射。
    > 这与 `LicenseResolver` 里"`unknown` 必须放行"是同一条原则的两处落点。

127. **关于「撤销」的三条事实，靠印象写会错两条。**
    ① **`revocationReason` 只有两档**（`.developerIssue` / `.other`）——
    Apple 的 Server Notifications 文档明确写：家人共享的撤销原因也是 `other`。
    ⇒ **退款与"被移出家人共享"在运行时区分不出来**，别对用户说"你退款了"。
    ② **`Transaction.currentEntitlements` 已经排除了已撤销的购买** ——
    只看它会**分不清"从来没有过"与"有过、后来被撤了"**，而这两种话术完全不同。
    要捞历史得用 `Transaction.all`。
    ③ 上面 125 那条（撤销可逆）。
    > 我原先把 `RevocationReason` 写成三档（退款 / 家人共享 / 收据丢失），
    > 其中两档**假装能区分**。代价是给用户一句很确定、但可能是错的解释。
    > 现在合并成 `.storeRevoked` / `.purchaseNotFound` 两档。

128. **手写的编码夹具漏一个非可选字段 → 解码失败 → 下游断言对 `nil` 求 `?.` 会**空跑通过**。**
    测试里手写了一段 JSON 去验"认不出的撤销原因要 fail-open"，
    但漏了结构里那个非可选的 `hasUsedTrial` ⇒ `JSONDecoder` 直接失败 ⇒ `load()` 返回 `nil` ⇒
    下面那句 `#expect(loaded?.revocation == nil)` 对 `nil` 求 `?.` 也是 `nil`，**通过了**。
    整条测试绿着，但它什么都没验。
    > 两条修法，缺一不可：
    > ① 夹具必须带齐**所有非可选字段**；
    > ② **先用一条 `#expect(loaded != nil)` 证明"确实读出来了"**，再断言内容。
    > 这一条对所有"解码 / 解析"类测试都成立 —— 解析失败的默认返回值往往是"最像成功"的那个。

129. **同一个接缝的两个实现必须逐条同规则 —— 差异只会在真机上现形。**
    `EntitlementCaching` 有两个实现（内存 / 落盘）。落盘那个拒绝缓存「还没查」，
    内存那个我一开始是无条件覆盖 —— 于是"内存里对、盘上不对"。
    > 这次是测试抓住的（专门写了一条"两个实现行为一致"）。
    > 判据：**接缝有多个实现时，就该有一条测试专门比对它们的可观察行为**，
    > 而不是各自测各自 —— 各自测各自永远不会发现分叉。

## U. StoreKit 与配置（ticket 31 第二批）

130. **适配器里**不许**做判断 —— 提前过滤掉的东西，那条规则就再也测不到了。**
    `StoreKitStorefront.fetchRecords()` 完全可以写 `case .unverified: continue`（把未校验的交易
    直接丢掉），看起来更干净。但那样一来，"未校验的交易一律不算数"这条规则就**只剩真机才跑得到**
    —— 本机没有沙盒账号，测不到，于是被改坏了也没人知道。
    做法：**如实记下来、标 `isVerified: false`**，让 Core 里那句 `filter(\.isVerified)`
    成为唯一的判据（它有 5 条测试盯着）。
    > 判据：写适配器/包装层时，凡是"我可以在这里顺手过滤掉"的念头，都要问一句
    > **「过滤之后，那条规则还有没有别的地方在管？」** 没有的话，就不许在这里过滤。

131. **`Transaction.updates` 每条都要按规矩处置：verified 必须 `finish()`，unverified 不要。**
    不 `finish()` 的话，那条交易会**一直被重发**（表现为日志里同一条反复出现、界面反复刷新）；
    而未校验的交易 `finish()` 等于**承认已经处理**，可我们什么都没接受。
    > 另外一条容易反过来做错：`Transaction.all` 里的**历史交易不要 `finish()`**
    > —— 那只是读取，不是消费。Apple 只要求 finish "updates 里来的"与"刚购买的"。

132. **测试替身必须能"挂住" —— 否则时序规则根本测不出来。**
    "启动不等网络"是这个设计里最重要的时序规则。但如果假 reader 立刻返回，
    那么**无论实现有没有 await 商店，断言都会通过** —— 等于没测。
    真实的做法是造一个"闸门"（`AsyncStream` + continuation），让 `fetchRecords` 挂在半路，
    先断言"此刻判定已经好了"，再放行。
    > 判据：凡是"**先做 A、再做 B、顺序不能反**"的规则，测试里都要有一个能停住 B 的装置。
    > 用一个即答的替身，测出来的是 A 的结果，不是两者的顺序。

133. **`Equatable` 上带"瞬时字段"的类型，相等比较是个地雷。**
    权益缓存 `load()` 会把 `now` 刷成**读的那一刻**（这是刻意的，见 `EntitlementCache`）。
    于是测试里写 `#expect(cache.load() == before)` **永远为假** —— 两次调用差几微秒。
    > 更危险的是反过来的写法：`#expect(cache.load() != something)` 会**永远为真**，
    > 那种"看起来通过了"的断言查起来极其费劲。
    > 修法：**比事实，不比整个值** —— 逐字段比（本项目写了 `sameFacts(_:_:)` 辅助函数），
    > 或者给类型加一个"忽略瞬时字段"的比较方法。

134. **配置文件与代码是两份独立的事实 —— 必须有一条测试把它们连起来。**
    `Products.storekit` 里的商品 id 与 `StoreCatalog` 的常量，不同步的两种后果都很难反查：
    ① 配置里有、代码里没有 → 开发期买得到但没人读结果（"点了购买没反应"）；
    ② 代码里有、配置里没有 → **本地能过、真机取不到商品**，而排障会先去怀疑网络。
    真机沙盒验不了这件事（它验的是"能不能买"，不是"两份配置是否一致"）。
    > 做法：解析配置文件 ↔ 比对常量，**两个方向都查**（少了哪一个方向，那一种错就漏了）。
    > 别忘了**解析器自检**（"确实读到了东西"）：否则一个解析不出任何东西的实现
    > 会让"空集合 == 空集合"永远通过。

135. **`@MainActor` 类型的属性不能被 `@Sendable` 闭包直接捕获。**
    ```swift
    EntitlementCoordinator(..., now: { self.origin })        // ✗ 编译错误
    ```
    被 `@MainActor` 标注的类型，它的属性访问是隔离的，而 `@Sendable` 闭包不带隔离。
    修法是先取成局部常量再捕（`let stamp = origin`）。
    > 这条本身只是编译错误，不值一提；值一提的是它**指向的那种设计**：
    > 把"现在几点"做成注入的闭包（而不是在内部 `Date()`）是这个项目里
    > 试用天数、权益判定能脱机单测的**全部原因**。

136. **XcodeGen 的 `storeKitConfiguration` 只拼前缀、不做相对路径计算。**
    源码里是 `Path(components: [options.schemePathPrefix, storeKitConfiguration])`
    —— 而 `schemePathPrefix` 默认 `"../../"`。所以配置文件写 `App/Products.storekit`，
    生成的 scheme 里就是 `../../App/Products.storekit`。
    > **不要自己重新推导这个前缀**：它相对哪个目录在 Apple 文档里没有明说，
    > 第三方说明互相矛盾（我看的两份就冲突）。正确的做法是**保留默认值**，
    > 然后在 Xcode 里**打开 scheme 的 Run → Options 看一眼**那个下拉框是否选中了文件
    > —— 10 秒就能确定，比读文档推导可靠。

## V. 构建环境与工程接线（2026-10-03）

137. **嵌套沙箱：`swiftc -disable-sandbox` 是那个逃逸口，而官方的三个参数不是。**
    `swift-plugin-server`（跑 `@State` 这类宏的辅助进程）**启动时会自己再套一层沙箱**。
    当外层已经被某个受限 profile 包裹（agent 会话、某些 CI 容器）时，那次 `sandbox_apply()`
    会被拒 —— 日志里的第一行永远是：

    ```
    sandbox-exec: sandbox_apply: Operation not permitted
    ```

    跟着才是 `external macro implementation type 'SwiftUIMacros.StateMacro' could not be found`。
    **后一句是症状，前一句才是根因** —— 只看后一句会一路去查宏插件的路径与缓存。

    Xcode 常被推荐的那三个参数（`-IDEPackageSupportDisableManifestSandbox=1`、
    `-IDEPackageSupportDisablePluginExecutionSandbox=1`、`ENABLE_USER_SCRIPT_SANDBOXING=NO`）
    **在本机实测无效**：它们关的是**内层**（清单求值 / 插件执行）沙箱，
    而外层那次 apply 本身就被拒。

    有效的是 `swiftc` 自己的开关（`xcrun swiftc -help-hidden | grep sandbox`）：

    ```
    -disable-sandbox        Disable using the sandbox when executing subprocesses
    ```

    它让**编译器根本不去套那层沙箱**，于是 `swift-plugin-server` 不需要 apply。
    实测：`OTHER_SWIFT_FLAGS="-disable-sandbox"` → **BUILD SUCCEEDED**。
    `scripts/build.sh` 里做成了显式开关 `MARQUEE_DISABLE_COMPILER_SANDBOX=1`，
    **默认不开** —— 那层沙箱是真实隔离，不该为了少数环境全局削弱它。

138. **`.storekit` 不进工程，Xcode 里那个下拉就是空的 —— 而且它显示为「红色」。**
    XcodeGen 的 `storeKitConfiguration:` 只往 **scheme** 里写了一个**路径字符串**，
    它**不会**把 `.storekit` 加进工程的文件引用。而 Xcode 的
    Run → Options → StoreKit Configuration 下拉框，列的是**工程已知的 `.storekit` 文件**。
    ⇒ 文件不进工程，下拉里就没有可选项、旁边那个引用显示为红色。
    （实测确认：那一版 `project.pbxproj` 里 `Products.storekit` 出现 **0 次**。）

    修法是在 `project.yml` 的 sources 里显式声明，并给 `buildPhase: none`
    —— 它只需要成为一个**文件引用**，不该进任何构建阶段（不是要拷进 app 包的资源）。

    > 判据：**"配置里写了个路径"与"工程里有个文件"是两件事**。
    > 任何"Xcode 编辑器里选一个文件"的设置（StoreKit 配置、GPX、`.xcconfig`…），
    > 都要先确认那个文件在工程里。

139. **XcodeGen 的 `schemePathPrefix` 默认值是给「非 workspace」的。**
    官方文档原文：默认 `"../../"`「suitable for non-workspace projects」，
    而「For use in workspaces, use `"../"`」。
    所以本项目的形态要先确认清楚：**scheme 实际在哪**。
    实测本项目的 scheme 只有一份、在 `Marquee.xcodeproj/xcshareddata/xcschemes/` 里
    —— 即使仓库里有 `Marquee.xcworkspace`，它 `xcshareddata/` 下**没有 schemes 目录**。
    因此这是「非 workspace」形态，默认前缀是对的，**不要**想当然地改成 `"../"`。
    > 顺带：它是**拼接**而不是解析（源码里是 `Path(components: [prefix, value])`
    > 然后简化 `..`），所以 value 里自己再补 `../` 会得到叠加的结果。

140. **macOS 自带的是 BSD grep —— `\s` / `\d` 不是字符类，而且它的"失败"是静默的。**
    写 `grep -E "^\s+iPhone"` 时，本意是"行首空白 + iPhone"。在 GNU grep 下能匹配，
    在 BSD grep 下**当作字面量 `s`** 去匹配 —— 于是**返回空结果、退出码 1，一个字都不报**。
    这类错的可怕之处与项目里其他几条一样：**它看起来像"没有数据"，而不是"表达式写错了"**。
    本次实测（`printf '  indented\n' | grep -E "^\s+indented"`）确认不匹配。

    **正解**：用 POSIX 字符类 —— `[[:space:]]` / `[0-9]` / `[[:alpha:]]`。
    同理还有两条 BSD 侧差异：`sed -i` 需要显式给后缀（`sed -i ''`）、
    `grep -P` 根本不存在。

    > 判据：在 macOS 上写"解析命令输出"的脚本时，
    > ① 能用 `--json` 就别 grep 人类可读格式（`xcrun simctl list devices available --json`）；
    > ② 非要用正则，**只用 POSIX 字符类**，别用 `\s` / `\d` / `\w` 这类 Perl 简写。
    > 更一般的教训：**"返回空"与"表达式错"必须能区分开** ——
    > 一条会静默失配的正则，比一条报错的正则危险得多。

141. **上面 140 的归因只对了一半 —— 沙箱里根本不是 BSD，是 toybox；而且 140 给的 `sed -i ''` 建议在这里正好是反的。**
    （2026-10-03 订正）agent 会话的 PATH 首部是 WorkBuddy 沙箱的 shim 目录，
    `grep sed find ls head tail cat wc …` 共 22 个命令被换成了 **toybox 0.8.13**
    （`toybox grep --version` 的输出自己就写着 "is not GNU grep 9.0"）。
    **你自己的终端走 `/usr/bin/grep`（BSD 2.6.0），agent 会话走 toybox** ——
    同一条命令、同一种写法，两个结果。

    更要命的是回退条件：shim 只在 stderr 出现 `Unknown option` 时才 exec 真工具
    ⇒ **语义差异永远不触发回退**，一律静默失配。所以"我在终端里跑是好的"这件事，
    **对 agent 会话没有任何证明力**。

    实测（2026-10-03）：

    - `grep 'a\|b'`（BRE 交替）→ toybox ❌ 静默 rc=1；BSD ✅ 命中
    - `grep -E` + 裸竖线 → 两边 ✅
    - `grep -E 'a\sb'` → toybox ❌ 静默 rc=1；BSD ✅ 命中
    - `grep -E 'a[[:space:]]b'` → 两边 ✅
    - `sed -i 's/a/b/' f` → toybox ✅；BSD ❌（unterminated substitute）
    - `sed -i '' 's/a/b/' f` → toybox ❌（把 `''` 当文件名）；BSD ✅

    **⇒ 140 里"`sed -i` 要加 `-i ''`"这条，在 agent 会话里是错的。**
    两边的 `-i` 语义相反 —— 所以**别再用 `sed -i`**：写临时文件再 `mv`。

    修法按确定性排序：

    ① **命令只写跨环境安全的形式**：永远 `grep -E`、交替用裸竖线、字符类只用 POSIX；
    ② 需要按 BSD 语义跑**单条只读**命令时，用逃生舱
    `CODEBUDDY_TOYBOX_BIN= grep …`（它让 shim 直接回退到 `/usr/bin/grep`）；
    ⚠️ 它同时绕开 shim 的分发层，**写 / 删命令别用**（safe-delete 与写入前备份会失效）；
    ③ **写脚本就照抄两个 build 技能脚本开头那段** —— 把 shim 目录从 PATH 摘掉
    （纯 bash，不调外部命令；普通终端里是 no-op），脚本内工具语义恒定。

    > 判据：**"环境不同"必须能被自己发现，不能靠"我这台机器上是好的"。**
    > 凡"同一个命令在不同 shell 里可能解析到不同实现"的东西，
    > 要么写成对三套实现都成立的**最小公共写法**，要么在脚本开头把环境**钉死**。
    > 顺带：内置的 Grep 工具是 ripgrep，**第三套**语法 —— 交替直接写裸竖线
    > （`\|` 在那边反而是字面竖线），`\s` 在那边是有效的。

142. **本地化生成器按「表达式名」猜说明符类型 —— 猜错不编译失败，只静默不翻译。**
    写升级卡片的标题时我写的是
    `L10n.t("\(Self.cardEntryName(content.feature))是 Pro 能力")`。
    `Tools/L10nCatalog/build_catalog.py` 判类型靠一份**字面子串**名单：

    ```python
    STRINGY = ("localizedDescription", ".path", "displayString", "reason",
               "detail", "title", "text", "conflict", "uppercased()", "String(")
    ```

    `cardEntryName` 一个都不沾 ⇒ 它按 **`%lld`**（整数）归一，catalog 里于是生出
    key **`%lld是 Pro 能力`**，而运行时传进去的是 `String` —— 说明符与实际类型不符。

    这条错的可怕之处和本文件里其他几条一样：**编译过得去、没有警告**，
    只在运行时表现为"这句中文没被翻译"。而人的第一反应会是"翻译没生效"，
    不会想到"key 根本是生成错的"。

    **正解：别拼。** 带变量的整句拆成独立文案 —— `"识别文字是 Pro 能力"`、
    `"钉图是 Pro 能力"`…… 顺带解决第二个问题：插值会把**中文语序焊死**，
    而英文里这个变量该在句首（"Text recognition is a Pro feature"），拼出来的句子翻不动。

    > 判据：**凡是"工具靠猜"的环节，加新用法时都要回头看它猜得对不对。**
    > 这次的灯是 `LocalizationScanTests` 亮的（它校验"源码用到的 key 都在 catalog 里"）——
    > 那条测试之所以存在，正是因为生成器**只能校验、不能判断对不对**：
    > key 生成了、catalog 里也有、测试全绿，可它就是错的。

143. **在沙盒进程之下再起一个沙盒 app —— 连 `main` 都进不去，而且一行输出都没有。**
    第一次跑 MAS 产物自检：

    ```bash
    DerivedData/Build/Products/MAS/Marquee.app/Contents/MacOS/Marquee -marqueeDiagnostics
    # 退出码 133
    ```

    **屏幕上什么都没有** —— 不是报错，是**寂静**。崩溃报告里才看得到真相：

    ```
    EXC_BREAKPOINT / SIGTRAP
    0. libsystem_secinit.dylib  _libsecinit_appsandbox.cold.9
    1. libsystem_secinit.dylib  _libsecinit_appsandbox
    2. libsystem_dylib          libSystem_initializer
    ```

    `libsecinit` 是 dyld 初始化阶段装 App Sandbox 的那个初始化器；它在**别人的沙盒里**
    装不上自己的沙盒，于是走 `__cold` 错误路径直接 trap。**崩在 `main` 之前**，
    所以任何 `print` 都不会执行 —— "一行都没有"这个现象本身就是判据。

    **判别三步**（顺序别换，第一步最容易被跳过）：

    1. `open -a <绝对路径>.app --args …` —— 经 launchd 启动，不在你的沙盒进程之下。
       **换一条路就好了 ⇒ 是嵌套，不是产物坏了。**
    2. 看有没有新崩溃报告（`~/Library/Logs/DiagnosticReports/`）——
       **连一条日志都没有**正是"崩在 main 之前"的特征。
    3. 只有前两步都排除了，才去看代码。

    ⚠️ `open` 的路径**必须是绝对的**：给相对路径它只会说
    `Unable to find application named '…'`，那是个与根因毫无关系的提示。

    > 判据：**同一个"什么都看不到"，在终端里和在 `open` 下含义完全不同。**
    > 与编译那条（`sandbox_apply: Operation not permitted` → 宏 `malformed response`）同源：
    > **症状在最外层，根因在最里层**；顺着症状去查，方向一定反。

144. **沙盒里 `NSHomeDirectory()` 是容器 —— 于是"默认目录"会落进用户永远找不到的地方。**
    沙盒进程的 `NSHomeDirectory()` 是 `~/Library/Containers/<id>/Data`。
    而 `FileManager.urls(for: .picturesDirectory, in: .userDomainMask)`
    是由它推出来的 ⇒ 沙盒下它指向**容器里的** Pictures。

    后果正好是本文件最忌讳的那一类：`⌘S` **成功**、剪贴板也**正常**、
    屏幕上没有任何提示 —— 图却存在
    `~/Library/Containers/com.tango.marquee/Data/Pictures/Marquee/`，
    用户翻遍桌面和访达都找不到。他不会认为"存到别处了"，他会认为**这 app 丢了东西**。

    **正解：默认落盘用真实家目录拼**，别问 `FileManager`：

    ```swift
    getpwuid(getuid())?.pointee.pw_dir   // passwd 条目，沙盒不会改它
    ```

    配 `com.apple.security.assets.pictures.read-write` 就能真写进用户的 Pictures。
    非沙盒构建下两者本来就相等 ⇒ **一条代码路径同时服务两种构建**，不用分支。

    ⚠️ **别在这个问题上押注**（我自己差点押错）。探针报告目录一度写成
    `<家目录>/Library/Logs/Marquee/`，理由是"`homeDirectoryForCurrentUser`
    在沙盒下应该是容器"。**这个假设我没能证实** —— 而在沙盒进程里，
    `~` 到底指哪儿、写不写得进去，都不是能从文档推出来的东西。
    押错的代价是：探针里写文件用 `try?`，失败被**静静吞掉**，
    表现出来与"这个入口没触发"一模一样。

    现在改成走 `.applicationSupportDirectory`（`.applicationSupportDirectory`
    在沙盒下**确定**是容器，这是沙盒的定义本身）⇒ **不需要任何关于家目录的假设**。

    > 判据：**凡是"沙盒下这个 API 会指向哪"的问题，不要推理，改走不依赖它的那条路。**
    > 能用 `.applicationSupportDirectory` 就别自己拿家目录拼 ——
    > 前者由系统按沙盒规则给，后者要你**知道**规则；而你一旦猜错，
    > 症状是"什么都没发生"，不是报错。

145. **`ENABLE_HARDENED_RUNTIME: NO` + 公证 —— 这条错在本地永远不显现，只在公证那一步爆发。**
    `project.yml` 的 `settings.base` 里一直是 `NO`，而 `scripts/package.sh` 走的是
    `notarytool`。Apple 对公证的**硬性要求**之一就是 hardened runtime 打开。

    ⇒ 那条流水线**必然**会在第 5 步（公证）被拒。但：

    - 本地构建：过
    - 本地运行：过
    - `swift test`：过
    - 出 DMG：过（签名核验那步用的是 `codesign --verify`，它**不检查** hardened runtime）

    一直走到**提交公证**才炸，而拒信要等几分钟。所以它**看起来像个"打包环境的偶发问题"**，
    而实际是一行配置 —— 顺着"公证服务是不是挂了"去查，方向全错。

    真正让这条错**活到今天**的是一个更朴素的原因：**ticket 18 的打包流水线
    一次都没跑过**（要 Developer ID 证书，只能由人跑）。
    **一条从没被执行过的流水线，它前面的每一行错误都还在。**

    > 判据：**"本地全绿"证明不了发行链路是通的。** 凡是只在发行期才生效的配置
    > （hardened runtime、entitlements、`exportOptions`、公证），
    > 要么**放进平时就会跑的路径**（放进 `settings.base`，四份配置同开），
    > 要么就得承认它**一次都没验过** —— 别把它当成"顺手加的一行"。
    >
    > 顺带一条实践：这一票最后把 `ENABLE_HARDENED_RUNTIME` 放进 `settings.base`，
    > 四份配置同开。理由与"`Dev` 照抄 `Release` 的优化设置"完全一样 ——
    > **本地跑的那个必须与发版同构**，否则问题只会在发版那天出现。

146. **同一个键在两个界面性格相反 —— 而且空缺的键位会把用户推给错的那个。**
    `Esc` 在覆盖层是「退一层，到底就取消」，在编辑器窗口却是「**完成并复制**」
    （把 `Esc` 当成 `✓` 用了）。于是：

    - 用户在覆盖层养成"`Esc` = 我反悔了"的肌肉记忆；
    - 进编辑器按同一个键，做的却是**写剪贴板** —— 一个**不可逆**的动作；
    - 与 macOS 的约定也相反：系统里 `Esc` 走 Cancel 按钮，`⏎` 才是默认按钮。

    ⇒ 两个键**互相错位**：`Esc` 干了确认的活，而 `⏎` 在编辑器里**什么都没绑**。

    ⚠️ **第二半比第一半更值得记**：`⏎` 是空的。所以"我想快点弄完"的人在那儿
    找不到确认键，**只能去按那个看起来最像的键**（`Esc`）—— 而它恰好是错的那个。
    **一个空缺的键位不是"少一个功能"，它是一块把用户推向错误键的吸铁石。**
    修的时候两件事必须一起做：给 `⏎` 绑上确认、把 `Esc` 恢复成退 —— 只做一半，
    用户仍然会按错。

    > 判据一（**修正过一次**）：**规则必须一致，字面可以不同。**
    > 最初写的是"一个键的性格必须全产品一致" —— 太粗。正确的是：
    > 两个界面可以有**不同的终点**，但必须有**同一条规则**
    >（"退最里面那一层；退无可退时朝『不丢东西』的方向退"）。
    > 真正危险的从来不是"终点不同"，而是**没有规则** ——
    > 那才是"用户按下去之前无法知道会发生什么"。
    >
    > 判据二（**也修正过一次**）：**退无可退时，朝「不丢东西」的方向退。**
    > 最初写的是"退出键不许做不可逆的事" —— 那条**把「产出」与「销毁」混为一谈**：
    > 两者都不可逆，**但方向相反**。写剪贴板是**留住**，丢标注是**销毁**；
    > 一律禁掉"不可逆"，结果会把该留的东西一起禁掉
    >（编辑器里 `Esc` 变成"取消"＝按一下丢掉几分钟的活）。
    > 正确的判据是**看底**：底下没东西 ⇒ 取消是零损失；底下有东西 ⇒ 带走才是零损失。
    >
    > 判据三：**这类错测不到，除非把"层级"做成能脱机跑的值。**
    > 键位分派在 AppKit 事件层（`NSEvent` 本地监听），原来的层级判断直接写在
    > 视图里 —— 没有任何测试碰得到它。这次把"退哪一层"抽成 Core 的纯函数
    > （`EscapeLadder.swift`：`EditorEscapeState.escapeStep()`），
    > 才第一次能对"层叠时退错层"写断言。
    > **"界面逻辑里有判断"就是测试的缺口；能不能把它变成值，决定它会不会第二次错。**

147. **"退无可退"的那一层，方向由「底」决定 —— 这是被设计稿推翻后才想清楚的一条。**
    同一个 `Esc` 梯子，覆盖层退到底是「取消」，编辑器退到底是「完成并复制并关闭」。
    看上去"没统一"，其实**必须如此**：

    | | 底 | 退到底做什么 | 为什么 |
    | --- | --- | --- | --- |
    | 覆盖层 | **还没有东西**（截图刚被叫起来） | 取消，不留痕 | 什么都没产出 ⇒「没有」就是零损失 |
    | 编辑器 | **已经有东西**（拼好的长图 + 刚画的标注） | 完成并复制并关闭 | 已经产出 ⇒「带走」才是零损失 |

    我第一次实现时把两边都做成"取消"，理由写成了"退出键不该做不可逆的事" ——
    而设计稿的原话直接点破了代价：**"编辑器里 `Esc`=取消意味着按一下丢掉几分钟的活"**。

    ⚠️ 这条最值得记的地方是**我当时为什么想错**：我把「写剪贴板」和「丢标注」
    都归成"不可逆动作"，于是要禁就一起禁。但它们**方向相反** ——
    一个是留住，一个是销毁。**用"可不可逆"当判据会同时禁掉这两种，
    而正确的判据是"会不会丢东西"。**

    > 顺带一条：编辑器里「丢弃」**只由 `✗` 承担** —— 它必须**用手点**，
    > 不能让人顺着下意识按出来。**危险的动作要"够不着"，不能只是"标红"。**

148. **半透明的"自己的底"，会让整张对比度表随屏幕内容失效。**
    读数框原来是「平的黑 72%」压在任意屏幕内容上。看上去"反正都是深色、白字都读得出"，
    但把同一行字对它的实际底量一遍就知道不是：

    | 框的底 | 白 64% 那行对它的对比度 |
    | --- | --- |
    | 黑 72% 压在**纯白**内容上 | 5.02 |
    | 黑 72% 压在**纯黑**内容上 | **2.52** ← 连正文级都不到 |

    也就是说"这段字够不够亮"这件事，**取决于用户此刻屏幕上是什么** —— 而那个不由我们决定。
    设计稿里本来有答案：它把「工具条 / 弹层 / **读数**」并列写在 `--c-panel` 那一行下，
    也就是**不透明材质**。换过去之后这张表对任何底都成立。

    ⚠️ 连带删掉的是 `ChromeStyle.readoutAlpha = 0.72` 与它那条断言 `alpha >= 0.5`。
    **那条断言写的是边界，不是意图**：0.5 与 0.72 都能过它，所以它给的保证比看起来的少
    （PITFALLS 98 的又一个实例）。真正的意图 —— "这几行压在任何内容上都读得出" ——
    现在由 `OverlayReadoutTests.backdropIsOpaque` + `everyRoleIsReadable` 承担：
    **先要求底不透明，再要求每枚颜色对那个底达标。**

149. **一个"小方块 + 描边"的控制点，用描边画会把足迹撑大 1 点。**
    稿子给的是「7 × 7 白芯黑边」，白芯 5 点，黑边 1 点 —— `5 + 1 × 2 = 7`。
    直觉上会写成 `path.lineWidth = 1; path.stroke()`，但**描边以路径为中心向两侧展开**：
    黑环会同时落在方块**内侧**与**外侧**各半点，外侧那半圈把足迹撑到 6 而不是 7。
    正确做法是**先铺一块 `insetBy(dx: -edge, dy: -edge)` 的黑底、再把白芯压上去**。

    ⚠️ 这类错的量级是"1 点"，肉眼几乎看不出来 —— 它的表现只是"控制点看起来有点糊"，
    或者相邻两个的黑圈互相咬在一起。所以不要靠看：把 `handleVisualFootprint`
    写成一个**加法表达式**并断言它等于 7，改了白芯忘了边就会红。

150. **"手不在了"这件事，没有任何坐标可以表达它。**
    悬停高亮要有两条消息才成立：`mouseMoved`（手在哪）**和** `mouseEnteredAndExited`
    （手在不在）。只注册 `.mouseMoved` 时一切都正常 —— 直到光标移出这块屏：
    被高亮的那一格会**一直亮着**，因为再没有任何事件会带着坐标进来。
    它的样子像"这一格被选中了"，而用户会说"我明明把鼠标移走了"。

    同样要主动清的两个地方，都是**"不会再有 `mouseMoved`"**的路径：
    会话开场（上一次的悬停与这一次无关）、以及**在画布上按下**（拖动全程走 `mouseDragged`）。
    判据：**凡是"某条通道上不再有后续事件"的入口，就得自己收尾。**

151. **"把瞬时状态画出来"之前，先数一数它是不是已经被别的东西表达了。**
    设计稿的工具条有六种状态（默认 / 悬停 / 按下 / 选中 / 置灰 / 带锁），
    其中"按下"是唯一一个**瞬时**的。实现前先把它可能出现的三条路走了一遍：

    | 按在哪 | 松手之后画面会变成什么 |
    | --- | --- |
    | 工具格 | 该工具变**填充蓝**（选中）—— 按下的样子看不见了 |
    | 样式格 | 弹层打开 → **底白 16%**（稿子明说这就是"按下未复位"） |
    | 动作格 | 面板直接关掉 / 立刻执行 —— 更没有"按下"可看 |

    三条路都被别的东西覆盖 ⇒ 那个瞬时标志位**没有任何一张画面上依赖它**。
    而它的代价是实打实的：多一个标志位，就要在**每一个出口**清它，
    漏一个就是"高亮粘住"（PITFALLS 66 那一类）。

    ⚠️ 判据不是"稿子上写了就做"，而是：**这个状态有没有一个时刻，是别的东西表达不了的？**
    没有的话，加它只是给未来的自己埋一个要收尾的坑。

152. **「≤ 34 字」是中文的预算 —— 英文要单独量，而"字数"这个尺子本身就是错的。**
    稿子 §10 给提示行定了物理前提：「六种文字全部 ≤ 34 字（11 pt → 约 374 pt），
    单行放得下 513 宽的提示行 —— 这是**不许换行、不许加高**的前提」。
    中文照这个数做了，全都放得下（最宽 350 pt）。

    但英文同样占这条行宽。按字数折算（34 字 × 11pt）是错的 ——
    中文字宽 ≈ 字号，拉丁小写只有它的六成。用**真字体**量一遍才发现：
    有一条英文是 **556 pt**，比可用的 533 多 23 pt，会在英文系统上**截断尾巴**。
    而它在中国开发机上永远看不见。

    ⚠️ 所以这条约束现在是一条**断言**（`LocalizationScanTests.hintLineTextsFitOnOneLine`）：
    拿 `NSFont.systemFont(ofSize: 11, weight: .medium)` 量中英两种文本。
    两个细节都不能省：
    - **查表用原样的 key**，不能用归一化之后的形状（`loadCatalog` 的字典按 catalog 原文键）；
      写错的症状是"13 条全缺英文"。
    - **`%lld` 要换成最坏情况的实数**（`9999`）再量，否则是按 5 个字符估的。

    > 顺带一条：宽度用的是**我们自己工具条的实际宽度**（545 − 2×6 = 533），
    > 不是稿子那个 513 —— 513 是按「内边距 5 / 组内间隙 2 / 分隔线两侧各 8」算的，
    > 我们实现里是 6 / 4 / 9。**约束要按自己的尺寸检查，不能按别人的。**

153. **挂在某个东西上的第二块面板，必须与它**整体**摆位 —— 不能"摆好一个再挂一个"。**
    提示行挂在工具条外侧。直觉的写法是"先按 `frame(for:)` 摆好工具条，
    再在它下面挂 22 点的一行"。这条路有两个当场就错的点：

    | 情况 | 挂上去之后发生什么 |
    | --- | --- |
    | 选区贴屏底 | `frame(for:)` 只保证**工具条自己**在屏幕内，它的下边正好压在屏底 —— 再往下挂一行就出屏 |
    | 工具条翻到选区上方 | 在它下面挂的一行会落在**工具条与选区之间**，把用户正要截的东西盖住 |

    两个都不会崩、不会报错，只是"那一行不知道跑哪去了"。
    正确做法（`OverlayToolbar.panelFrames`）是**先把 62 点（或 40 点）高的整块摆好，
    再切成两段**：靠选区的那段是工具条，外侧那段是提示行。
    切的时候要用**夹取之前**那条判据决定顺序 —— 夹取之后整块可能被推进屏幕里，
    那时"下面那侧"已经不代表"外侧"了。

    > 顺带：`frame(for:)` 现在转发到 `panelFrames(showingHint: false)`，
    > 于是"贴边 / 翻面 / 夹取"三条规则**只有一份**。有断言钉住两者逐字相同。

154. **面板的高度会变，圆角就得跟着收 —— 而 `makeBackgroundView` 只在创建时给过一次。**
    同一块面板有三种高度：40（只有工具条）、62（工具条 + 提示行）、22（只有提示行）。
    10 点的圆角放在 40 和 62 上是"圆角"；放到 22 高的条上，上下两个圆角一合就成了**胶囊** ——
    而胶囊读起来像一颗徽章，不像一条说明。

    两个坑叠在一起：
    1. **圆角是创建时定的**。视图复用了同一块背景视图、只改 `frame` ——
       所以"把圆角写进 `makeBackgroundView`"等于**永远**是第一次那个值。
       要显式地每次摆位都按下去（`ChromeBackground.setCornerRadius(_:on:)`）。
    2. **判据不能拍脑袋**。用 `min(圆角, 高度/3)`：`40/3` 与 `62/3` 都大于 10，
       所以那两个值一个都不变 —— 只有真的矮到放不下时才收。
       "高度的一半减几"这种写法会让常态也跟着变，而那种偏差只是"看着有点怪"。

    > 顺带记一句：设计稿说「圆角只在提示行的**底部**」，听起来要去做"只遮罩两个角的圆" ——
    > 而零间隙时那一块**就是**一个圆角矩形（工具条上圆角 + 中间方 + 提示行下圆角）。
    > **先算一遍并集，往往就不需要那个 trick 了。**

155. **自绘控件要付"无障碍"的入场费 —— 它不是可选项，是代价。**
    设计稿给的几个尺寸（开关 38 × 22 / 钮 18、分段控件 24 高、"选中段 = 键帽材质"、
    滑块 轨 4 钮 14 且**已选段填色**、标签条 28 高）用现成控件**一个都够不着**：
    `NSSegmentedControl` 的高度圆角由系统定、`NSSlider` 的轨是系统画的凹槽
    （没有"已选部分填色"）、macOS 也没有公开的 `NSSwitch`。所以只能自己画。

    而换成 `NSView` + `draw(_:)` 之后，`NSButton` 白送的那些
    `accessibilityRole` / `accessibilityValue` / `accessibilityPerformPress` **全都没了**。
    "用 VoiceOver 的人点不到这个开关"不会崩、不会报错、开发机上永远看不见 ——
    它只会让一部分用户用不了，而**那些人不会来报 bug，他们会直接卸载**。

    ⇒ 所以每一件自绘控件都显式实现了这几个方法。**这是自绘的入场费。**
    另外有一条是自绘**做不到**、只能退一步的：分段控件没法让"每一段"都是一个可点的
    radio（那要自己算每一段的无障碍帧，而帧又依赖文字宽度）。
    退到"整个控件一个角色 + 一个值"—— 至少**当前是哪一档**听得见。
    **这个取舍写在代码里**，免得下次被当成漏做。

156. **从两个数推导出来的那个关系式，写成断言等于没写。**
    开关的"钮在轨里、上下留边相等"我写成了：

        #expect(knob + inset * 2 == track.height)

    而 `inset` 的定义就是 `(track.height - knob) / 2` —— **这条恒真**。
    把轨高从 22 改成 24，它照样绿；而改完之后钮的留边确实还是均分的，所以判据本身没错，
    **错的是它测不到任何东西**。这正是 PITFALLS 98 那句"断言要写意图"的又一个实例，
    也是 117 那两分法里的第一种（**断言是盲的**，不是代码死了）。

    ⇒ 改成钉**字面值**：`#expect(track == CGSize(width: 38, height: 22))`。
    推导出来的关系式可以留着当文档，但它不能是唯一的那条判据。

    > 这条值得单列的原因：**它是我自己写的、而且在写完的那一刻看起来是对的。**
    > 变异测试（把 22 改成 24 看红不红）是唯一能当场发现它的办法 ——
    > 而"我觉得这条断言挺到位"恰恰是让人跳过变异测试的那种感觉。

157. **界面上摆出来的"清单"，必须与真正实现它的那张表**同源**。**
    `PAGE-LOGIC.md` 里写的可用变量是 `{date} {time} {n} {app} {title}`，
    而实现里序号变量叫 **`{index}`**，没有 `{n}`。

    这个差别的形态很特别：界面照着清单摆出一个 `render` 不认的变量，用户点一下 ——
    什么都不会发生（或者那个占位符**原样留在文件名里**，文件真的叫 `Marquee-{n}.png`）。
    而它看起来像"模板功能坏了"，不像"清单写错了"。

    ⇒ 清单与替换表**同源**（`FileNameTemplate.variables` 是唯一那份，
    `availableTokens` 由它派生），并加一条断言：**每个摆出来的变量渲染一遍，
    结果里不许还剩花括号**。这条断言第一次跑就抓住了 `{n}`。

    > 同类的东西还有几处，判据都一样：**"给用户看的清单"与"实际生效的规则"
    > 是同一份数据，就永远对得上；是两份，就总有一天会分叉。**

158. **"填充蓝"在一页里只能有一个含义 —— 否则用户会以为切页等于打开了什么。**
    这一批里填充蓝（`--c-fill`）出现在三个地方：开关的"开"、滑块的"已选段"、
    以及（覆盖层那套里的）"当前生效的工具"。而分段控件的**选中段**与标签条的**选中格**
    用的都是**键帽材质 / 软底 + 描边**，不是填充蓝。

    改错的表现很温和：把"选了 5 秒"画成蓝的，用户会以为"5 秒延时被打开了" ——
    而那是两回事（一个是参数取值，一个是功能开关）。
    它与 PITFALLS 里那条"两种亮谁也不冒充谁"是同一条纪律，只是换了一页。

159. **"我没去惹它"和"我惹了但失败了"，在断言里必须是两个不同的东西。**
    「文件已经不在了就别去问废纸篓」这条守卫，我给它写的断言是
    `#expect(can.received.isEmpty)` —— 而假废纸篓只在**成功移走**之后才记一笔。
    于是把那条守卫整个删掉，断言照样绿：假废纸篓会失败，失败也不算 `received`。
    变异测试当场抓到了这一条（"没红 ❌"，12/14 里唯一一个）。

    | 想表达的 | 该断言的 |
    | --- | --- |
    | 没去惹它（刻意的） | **被问到过的次数 == 0** |
    | 惹了但没成（退路了） | 收到的东西为空 + 记录仍离开索引 |

    ⇒ 假接缝要**分开记两件事**：`attempts`（被问过）与 `received`（成功收下的）。
    合成一个的话，这两行代码可以在测试里互换而全绿。

160. **生成器只看"有没有中文"，会静默跳过全 ASCII 的用户文案 —— 而测试不会跳。**
    `Tools/L10nCatalog` 抽 key 的判据原来是 `CJK.search(content)`：
    `L10n.t("\(dimensions) px")` 一整个字面量里没有汉字，于是它**消失了**。
    而 `LocalizationScanTests` 那条「源码用到的每个 key 都在 catalog 里」是按
    `L10n.t` 找的，**不会**跳 —— 于是两边对不上，先红的是测试。

    ⚠️ 这个不对称很坏：它让你去修"测试报了一个生成器根本没有的 key"，
    而最省事的修法（把测试放宽）恰好把真问题盖掉。
    ⇒ 判据改成「有中文 **或** key 里带格式符」。加完这条立刻多出一个 `%@ px`。

    顺带记一个配对的坑：`spec_for()` 靠**表达式文本**猜格式符，
    而 `\(dimensions)` 这种局部变量默认被猜成 `%lld` —— 明明它是 `String`。
    猜错的后果不是崩溃，是"英文用户看到一句中文"（查表永远匹配不上）。
    所以每加一个插值变量都要在 `STRINGY` 里点名。

161. **稿子上量的宽度是"按中文量的" —— 同一句英文往往放不下，而中文环境永远看不见。**
    这是上一批（提示行）那条的第二次、第三次发作。这一批一次抓到两处：

    | 位置 | 可用 | 中文 | 英文（初版） |
    | --- | --- | --- | --- |
    | 最近截图底部那一句（三段 + 一枚按钮） | 320 | 254 | **370** ← 超出 49 |
    | 行里第二行（尺寸 + 标注数，mono 11） | ~161 | 142 | **172**（`annotations` 太长） |

    两处都不是"不好看"，是**会被截断或挤掉**：底部那句的最后一段整个看不见。
    ⇒ 收短英文（`The free version keeps the last …` → `Free keeps the last …`；
    `annotations` → Apple 那边的说法 `marks`），并把这两条**变成断言**
    （`LocalizationScanTests` 里按真字体量中英两套）。

    ⚠️ 一个容易搞错的细节：量的时候要用**那一处真正的字体**。
    底部那枚「升级到 Pro」是 11pt **500 字重**，比正文宽一点 ——
    拿正文字体量会少算十几点，而它正好卡在边界上。

162. **`String(localized:)` 的整数插值会按语言加千位分隔符 —— 分辨率读数会变成 `1,234×768 px`。**
    `L10n.t("\(Int(width))×\(Int(height)) px")` 里那个 `Int` 走的是本地化数字格式化，
    中文下 `1234` → **`1,234`**。截图尺寸是一个**标识**（像型号），不是计数，
    任何语言下都不该有分隔符 —— 而它挂着"本地化"的名头，看起来像是正常行为。

    ⇒ 尺寸先自己拼成字符串再插进 `L10n.t`（`\(dimensions) px` → `%@ px`）。
    标注**数**则相反：那是个真正的计数，`1,000 个标注` 是对的。

163. **`NSStackView` 是按"对齐矩形"摆的，不是按 frame —— 看 frame 会以为整段被推左了 2 点。**
    底部那一行量出来第一段在 `x = -2`（栈里），看着像"句首被推出了内边距"。
    实际是 `NSTextField` 的 `alignmentRect` 比 frame 大一圈（AppKit 给焦点环留的余量），
    栈把**对齐矩形**的左缘钉在 0，frame 自然落在 -2。

    ⇒ 量 AppKit 摆出来的东西时，**量 `alignmentRect(forFrame:)`**。
    这条是冒烟报告里现形的一行 `(-2,5,116×14)` —— 差的就是"要不要去改一个本来没错的值"。

164. **菜单项一旦有图，AppKit 会给整张菜单留出一列图标位。**
    免费版给「滚动截屏」挂一把锁、买断之后 `image = nil` —— 于是那一列消失，
    **整张菜单所有标题一起往左跳一下**。用户看到的瞬间只会觉得"菜单变了"。

    ⇒ 解锁时给一枚**空的同尺寸占位**，把那一格占住。
    它没有可见的代价（空图什么都不画），换掉的是一处只在"买完那一刻"出现的跳动。

165. **约束拼出来的界面，Core 单测钉不住"视图有没有照它摆"。**
    `RecentPanel` 那一套数字全都有断言（四段之和、总高、徽章不出行），
    但把它们摆成视图要经过 Auto Layout —— 而**约束冲突与模糊布局都不会崩**：
    它们只是让某个视图位置不对，控制台那行
    `Unable to simultaneously satisfy constraints` 在应用日志里很容易被冲掉。

    ⇒ 加一个冒烟入口（`-marqueeSmokeRecent`），把"算出来的"与"排出来的"逐项并排打出来，
    并把 `hasAmbiguousLayout` 的视图列出来。它当场抓到两件事：
    底部第一段那个 `-2`（是错觉，见 163）、以及空态那一档的面板高度对不对。

166. **只保证"别超"的预算断言是半边的 —— 它测不出"少算了一项"。**
    编辑器工具条有一条"整条放得进窗口"的断言（窗口 + 工具条都是固定宽度，
    算不够就会被静默裁掉最右边那几格）。可它只写了上界：

        #expect(minimumToolbarWidth() <= defaultWindowSize.width)

    ⇒ 算式里**漏掉一项**会让它更容易通过 —— 而那条断言于是成了假话：
    "放得下"是因为我们根本没把托盘算进去。变异测试里把 `add(traySize.width)` 换成 `add(0)`，
    它**没红**。

    ⇒ 预算类断言要**两头都钉**。下界取"比答案低一档、但高于任何成组漏算"的数：
    整条 1146，下界 1100 —— 漏掉托盘（−174）或右簇（−222）会当场红。

    > 与 PITFALLS 156（"从两个数推导出来的关系式写成断言等于没写"）配对看：
    > 那一条说的是**两边同源**时的恒真；这一条说的是**只有一边**时的失明。
    > 判据很简单：**把它改坏，那条断言会不会红？**

167. **"跟着最高的那件长出来"的数，要写成推导式 —— 那不是恒真。**
    工具条高 48 = 内边距 5 ×2 + 尺寸芯片 38；托盘 174 = 内边距 6 ×2 + 色块 22 ×6 + 间隙 6 ×5；
    一条分组竖线吃掉 17 = 间隙 2 ×2 + 余量 6 ×2 + 线宽 1。

    这三条**与 156 那条不同**：156 说的是"等式两边取自同两个数"（恒真），
    而这里左边是**独立的一个字面量**（48 / 174 / 17），右边才是推出来的 ——
    所以它能抓住"芯片涨到 40 了、条高还是 48"（表现是芯片被裁掉两条边）。

168. **弹层的默认值必须落在档位表里 —— 否则一进来三档全不亮。**
    编辑器的打码默认是 12，而档位是 8 / 16 / 32。界面上没有报错、没有异常，
    只是三个芯片**一个都不高亮** —— 而那个状态在用户眼里长得像"坏了"。

    这类"两处数据必须对齐"的错在两端都不显眼：
    改档位的人不会想到默认值，改默认值的人也不会想到档位。
    ⇒ 断言写在**两套**上（覆盖层与编辑器），遍历所有含义：

        #expect(meaning.values.contains(meaning.defaultValue))
        #expect(meaning.editorValues.contains(meaning.editorDefaultValue))

169. **两套单位之间的关系，值得也钉住 —— 它能反过来证明设计没错。**
    编辑器那三档（线宽 4/8/16 px、打码 8/16/32、字号 36/56/88）与
    覆盖层那三档（2/4/8 点、4/8/16、18/28/44）**正好差 2 倍** ——
    目标机器是 Retina，2x 就是两套数之间的桥：**同一组视觉粗细，两套单位**。

    这个关系不是我推的，是量出来的。把它写成断言的价值不在"证明 2 倍"，
    而在**把两张表拴在一起**：谁改了其中一张而不管另一张，测试会红一次，
    逼人想一下"看起来还一样粗吗"。它与"两套不许相同"那条是配对的：
    同值不行（说明被合并了）、错位也不行（说明粗细漂了）。

170. **一个"从头到尾都是真的"标志位，会把两张脸合成一张。**
    裁切进行中时状态行要说两句话：「拖出保留框」（还没框）与「⏎ 应用」（框出来了）。
    最自然的判据是 `isCropping`，而它**从拿起裁切刀那一刻起就一直为真** ——
    于是用户永远等不到那句"可以按 ⏎ 了"。

    正确的判据是"草稿**变了**"：`beginCrop()` 把草稿设成当前的裁切矩形，
    所以刚进去时 `cropDraft == document.cropRect`。→ `isCropFrameAdjusted`。

    > 这类错的形态很固定：**判据比它想表达的东西宽**。
    > 检查办法：把那个变量在时间轴上从头到尾走一遍，问"它在我要区分的那一刻，值一样吗？"

171. **用户文案里出现孤零零的 `%` 是危险的：它随后会被当成格式串。**
    `L10n.t("适应窗口 \(n)%")` 的 key 会带上一个**后面没有转换符的 `%`** ——
    而那串东西正是运行时交给 printf 家族的格式串。百分号在两种语言里都是同一个符号，
    **它本来就不该进文案**：拼在外面（`L10n.t("适应窗口 \(n)") + "%"`）。

172. **图标名只有一份来源之后，"两处图标不一致"在结构上就不可能了。**
    覆盖层与编辑器原先各有一张 `switch` 把工具翻译成 SF Symbol ——
    它们靠"记得写一样"维持一致，而分叉时**不报错**，只是某天「文字」在两处长得不一样。

    搬进 Core（`AnnotationIcon`）之后要注意一个**新引入的风险**：
    两个枚举的 case 名字相同（`AnnotationEditorTool.rectangle` 与 `AnnotationKind.rectangle`），
    写 `symbol(for: .rectangle)` 会**歧义**；而写成 `symbol(for: tool.annotationKind ?? .rectangle)`
    则是一个 `??` 兜底 —— 它会把"这个工具没有对应类型"**悄悄变成矩形图标**。
    所以要**一个 case 一个 case 地穷尽写**：加新工具时编译就过不去。

173. **一次被中断的变异验证，会把变异**留下**——而它不会被任何东西发现。**
    变异测试的做法是"改坏源码 → 跑测试 → 还原"。还原写在脚本末尾 ——
    于是**脚本被中途杀掉**（用户取消、超时、我在中途关了会话）时，
    那一次已经应用、还没还原的变异就留在工作区里了。

    这次的形态：`ProCardLayout.height(includesMicro:)` 的 `return base + …` 被改成了 `return base`，
    于是载体 A 的高度从 140 变成 115。**它一声不响地待了十几分钟**，直到我下一次跑全量测试。
    期间我还用那个状态**重新渲染了三张对照截图**（升级卡片那张就是在那时出的）。

    ⇒ 两条纪律：
    - **每次跑完变异（尤其被中断之后），先 `git status` + 跑一次全量测试**再继续别的活；
    - 变异脚本自己也要能收尾：逐条 `try/finally` 还原（这次补上了），
      而不是"全部跑完再统一还原"。

    > 这条与"断言是盲的"是同一类问题的两个方向：那边是**测不到**，
    > 这边是**测的东西被改坏了还没发现**。两者都只能靠"跑一次全量"暴露。

174. **规格里写"五个槽"的地方，别按"三段文字 + 两个按钮"去实现。**
    升级卡片原先的实现是"标题 / 正文 / 两个等宽按钮"—— 看起来合理，而稿子给的是**五个槽**：
    ① 图标（**用户刚点的那个功能**）② 标题 ③ 正文（**一行**）④ 按钮组（**一个色块 + 一个文字按钮，右对齐**）
    ⑤ 微行（`esc` 键帽 + 一句承诺）。差得最远的是三点：

    | 项 | 原先 | 稿子 |
    | --- | --- | --- |
    | ① 图标槽 | **没有** | 16 pt，就是工具条上那一枚（证明"这张卡在回答你刚才的动作"） |
    | ④ 按钮 | 两个**等宽色块**，左右铺开 | **一个色块 + 一个文字按钮**，右对齐、宽度随文案 |
    | ⑤ 微行 | 没有 | `esc` 键帽 + 「关闭卡片，选区保留」（**只在载体 A**） |

    两个高度也是同一行加法：`16 + 18 + 6 + 18 + 17 + 24 [ + 11 + 14 ] + 16` = 140 / 115。

    > 教训不是"要看稿子"（那太显然），而是：**"看起来合理"的实现最容易整块漏掉规格里的槽** ——
    > 因为它的每一部分都自洽。判据是**数一遍稿子里列了几件事**，再数一遍自己画了几件。

175. **按钮要「按下只记状态、松手才执行」——按下即执行会让"手抖"变成一次购买。**
    卡片的两个按钮原先在 `mouseDown` 里就跑动作。稿子 §06 给了**默认 / 悬停 / 按下**三档，
    而按下那一档只有在"松手才执行"的模型下才有意义。

    三件事要一起做，少一件都会留下假状态：
    - `mouseDown` 只记"按着哪一个"，并只重画卡片那一层；
    - `mouseUp` 时**必须还压在同一个按钮上**才算（拖出去 = 我改主意了）；
    - `mouseExited` 里把"按着"一起清 —— **鼠标拖出屏幕再松手时 `mouseUp` 收不到**，
      不清的话那个按钮会一直是深色的按下态（PITFALLS 150 的同一类）。

176. **要让出去的东西，得在**开窗口之前**让开 —— 不然用户看到的是"点了没反应"。**
    覆盖层是 `.screenSaver` 层的**非激活**面板，整屏压在所有普通窗口之上。
    于是"从覆盖层里打开偏好设置（或拉起 StoreKit 的购买面板）"这条路，
    在覆盖层不退场时**什么都不会发生** —— 那个窗口在覆盖层底下开了。

    用户的原话是「弹出面板层，但是无法交互，因为此时截图的框线图还在显示」。
    判据写成了一个属性（`ProCardAction.needsAnotherWindow`）：
    `purchase` / `startTrial` 要开窗口 ⇒ 覆盖层先走 `cancel()`；
    `restore` 是**静默、原地完成**的 ⇒ 覆盖层留着，只收卡片（用户的选区不白丢）。

    > 顺带补了一条同源的通知：权益一变，覆盖层**重新问一次** `ProCard.content`
    > （而不是自己判断"现在解锁了没"）—— 这样"点了恢复购买 → 成功 → 锁当场消失"才成立。

177. **给不出来的反馈，用户会用"点不动"来解释。**
    卡片原先既没有悬停也没有按下（按钮画完就是一块死的色块），
    而且**整张卡都给手指光标** —— 于是"正文上点两下没反应"看起来和"按钮坏了"一模一样。

    两处一起改：光标只给那两个按钮（`OverlayCursorContext.proCardButtons`），
    正文与空白处一律箭头；光标的分派顺序也调到与 `mouseDown` 一致
    （**卡片 → 弹层 → 工具条** —— 它是最晚弹出来的那一层）。

    > ⚠️ 这条断言差点写成"没用的断言"：先写的版本用"卡片与工具条重叠的那一点"来证明
    > 卡片优先，而**拿掉卡片那一支之后那里的答案也是手型**（工具条给的）—— 变异不红。
    > 要钉住顺序，得用**卡片上"不是按钮"的那一点**（正文处），因为只有卡片那一支会给箭头。

178. **"哪一句"是判据，"那句话是什么"是文案 —— 前者放 Core，后者放视图。**
    正文选哪一句（"试用 7 天…" 还是 "试用已结束…"）原先写在视图层的 `switch` 里，
    于是**变异测试抓到了它没人管**：把判据改成恒真，全套测试照绿 ——
    而那时的表现是**对着一个已经用过试用的人说"可以试用 7 天"**。

    ⇒ 判据提成 Core 的 `ProCard.bodyVariant(for:)`（只看 `reason` + **主按钮是不是试用**），
    视图只负责把枚举翻成句子。这样"四档互不相同"与"哪一档说哪句"都能断言。

    > 同理的那一条已经犯过一次（`ProCard.content` 返回 `nil` 就是"该放行"）。
    > 判据与文案混在一起时，**改一个错别字就得动测试** —— 于是测试会被改成松的。

179. **全局快捷键会在按键到达响应链之前把它吃掉 —— 于是"录制快捷键"这个动作本身录不进去。**
    用户在「快捷键」页点一下录制框、按下**自己正在用的那颗键**（默认 `⌃Q`），
    得到的是两件事同时发生：设置毫无反应（用户的话是"设置会无效"），
    而且**屏幕上真的浮出截屏覆盖层**。

    机制：`RegisterEventHotKey` 是**系统级**的，它优先于本应用的 `keyDown` 分发 ——
    录制器（一个 `acceptsFirstResponder` 的自定义视图）根本收不到那次按键，
    而 Carbon 那边照常回调 `handler` ⇒ 一次真实的截屏请求。
    最讽刺的一点：**用户最可能按下的恰恰是当前那颗键**，所以这条 bug 撞上的概率极高。

    修法：录制开始 → `ShortcutService.suspendForRecording()`（注销全局注册），
    录制结束 → `resumeAfterRecording()`（把 `current` 装回去）。

    > ⚠️ **恢复注册不能走 `apply`。** `apply` 里那道独占探测一旦返回 `.conflict`
    > 就**什么都不注册** —— 而"别的应用也占着同一个键"时，非独占注册本来是成功的、
    > 共存在正常工作。挂起一次把它变成"被占用"，就是**用一个探测把我们自己弄瘸**。
    > 恢复只需要 `register`，因为这个组合此前已经注册成功过。

    > ⚠️ **收尾不能只挂在 `resignFirstResponder` 上。** 点窗口红叉关设置窗时
    > 第一响应者不一定变（按钮不抢焦点）⇒ 挂起状态留下 ⇒
    > **全局快捷键从此彻底失灵且毫无提示**，比原 bug 更糟。
    > 所以另加一道兜底：监听宿主窗口的 `didResignKey` / `willClose`（`viewDidMoveToWindow` 里挂钩）。

    > ⚠️ **顺序**：录到键时先 `change(to:)`（它内部会真正注册并清掉挂起标志）、
    > 再报"录制结束"。反过来会把同一个组合注册两遍 —— Carbon 对同一进程内
    > 同一组合的重复注册返回 `eventHotKeyExistsErr`，等于把刚设好的键弄坏。

    > ⚠️ **挂起要计数，不能是一个布尔。** 设置窗与引导窗**各有一个录制器**、
    > 共用同一个 `ShortcutService` —— 布尔会让"先结束的那个"把全局注册提前装回来，
    > 而另一个还在录 ⇒ 同一个 bug 从一个新入口复发。
    > 计数还有第二个作用：`apply` 里把它清成 0，于是"改键成功"之后那次收尾
    > 自然变成空操作，不必再另设一个"刚刚注册过"的标志位。

180. **报失败原因之前，得真的知道原因 —— 不知道时只能说"失败"。**
    用户的原话：「恢复购买后取消，提示网络失败，但是我的网络是好的」。

    机制：`AppStore.sync()` 会弹 Apple ID 登录/确认框，**用户按取消时它也抛错**。
    而编排层把所有抛出来的错一律归成 `.failed`，界面又只有一句
    「恢复失败 · 检查网络后重试」—— 于是**一个网络完全正常的人被派去查网**。
    这类错比"报不出原因"更糟：它给出一个**看起来可执行、实际是错的**下一步。

    修法分两半，而**分工正是关键**：

    - **翻译在适配器**（`MarqueeStore`）：平台错误码 → `StorefrontRestoreFailure`
      的三档（`cancelledByUser` / `network` / `other`）。只有这一层知道平台错误长什么样 ——
      而**同一个"取消"有三种形态**，只认一种就会漏：`StoreKitError.userCancelled`、
      老的 `SKErrorDomain` code 2（`SKErrorPaymentCancelled`）、
      以及 `NSURLErrorDomain` code **-1012**（`userCancelledAuthentication`）。
    - **态度在 Core**（`EntitlementCoordinator.RestoreOutcome` 五档）：
      哪一档配说什么话。Core 不 import StoreKit，所以这一层脱机测得动。

    > ⚠️ **最阴的一档是 -1012。** Apple《Handling errors》把 `NSURLErrorDomain`
    > 整体归成"StoreKit 的网络错误"，而那张表里就列着 -1012，含义是
    > **「用户取消了这次认证」**。按"域名是网络域 ⇒ 网络故障"整片处理，
    > 这条 bug 会**原地复活**：照样弹"检查网络后重试"，而用户只是按了取消。
    > ⇒ 网络域里也必须逐码判，别按域一刀切。

    > ⚠️ 认不出来的错误落 `.other` ⇒ 界面说"稍后再试"，**绝不冒充网络问题**。
    > 猜错的方向永远是"让用户去修一个没坏的东西"。

    > ⚠️ 这条与 126（「商店里没有」只有真的问过才算证据）是**同一条原则的两面**：
    > 那边不许把"没问到"当成"没有"；这边不许把"不知道"说成"具体原因"。

    > 变异验证时顺带抓出一处**死代码**：`error as? SKError` 与
    > `NSError.domain == SKErrorDomain` 两条路覆盖的是同一批错误，
    > 摘掉其中一条全套测试照绿（后者是死的，因为前者先接住）。
    > ⇒ 只留域那条 —— 它不需要定义"陌生错误码桥成什么"（见 117：
    > 变异不变红要么是断言盲，要么是代码死）。

181. **「点了没反应」= 把结果丢掉；而用瞬时状态决定按钮能否点，会把入口变成出不去的死胡同。**
    用户的原话：「点击升级到 pro 无效」。这条是**两个独立的缺陷**叠在同一个按钮上。

    ### ① 结果被整个丢掉

    `proActionTapped` 原本只有一行：`Task { _ = await …purchasePro() }` ——
    `_ =` 把结果扔了。于是五档结果里只有"买成"有可观察的后果（状态区自己会变），
    其余四档**全都表现为点了没反应**：取消没回话、失败没回话、待批准没回话、
    **商店里压根没有这个商品也没回话**。

    ⚠️ 而最后那一档（`.unavailable`）在开发机上**几乎必然发生**：
    StoreKit 配置是**由 Xcode 注入**的 —— `project.yml` 里那句
    `storeKitConfiguration: App/Products.storekit` 只写进 scheme，
    **只有从 Xcode 启动进程时才生效**。用 `open` / 双击启动的构建拿不到它，
    于是 `Product.products` 返回空 ⇒ `.unavailable` ⇒ 静默无反应。

    > 判据：`docs/design/对照检查/impl-03-偏好设置通用.png` 里状态句是
    > 「免费版（最近截图保留 5 张）」、按钮是亮的 —— 说明**入口是通的**
    >（`.unknown` 已经过去了），问题全在"结果被丢掉"这一半。

    ### ② 瞬时状态决定了常驻按钮的可用性

    主按钮的可点性原来是视图里一个 `switch snapshot.entitlement`，`.unknown`
    那一档被置灰，理由是"还没问出来、别让人买第二次"。那条理由有两处不成立：

    - **判据自相矛盾**：`.unknown` 在 `LicenseResolver` 里是**放行**的
      （"unknown 必须放行"，见 126 的邻居那条）；能力都放行了，购买入口却锁着。
    - 买断型（非消耗型）商品的重复收费由系统兜底，不需要我们替它把关。

    后果是一个**出不去的死胡同**：按钮上写着「升级到 Pro」、点它什么也不发生，
    而且**永远不会变** —— 核实一旦失败，判定就停在 `.unknown`。
    这与 66（瞬时标志位不许决定常驻 UI 的可见性）是同一条：
    **"还没问出来"是个过程，"按钮能不能点"是个常驻状态。**

    ⇒ 判据搬进 Core（`Entitlement.allowsUpgradePurchase`）。搬家的价值不在"哪种更礼貌"，
    而在**它现在能被断言**：从前散在视图的 `switch` 里，漏一档就是
    "某一类用户被关在门外"，而那种错不崩不报错。
    断言还钉了一条配对不变量：**关掉的那一档必须正是文字改成「已购买」的那一档** ——
    否则就是一个说着"来点我"的死按钮。

    > 顺带把回执的**宽度也变成断言**（`LocalizationScanTests.proPanelTextsFit`）：
    > 状态句单行、回执两行，中英一起量。最长的那句是开发版提示
    >（"…请用 Xcode 运行，且 scheme 要挂 Products.storekit"），
    > 它正是最容易撑破面板的一句 —— 而撑破的表现是**被截掉后半段**，
    > 而后半段恰好是唯一有用的那部分。

182. **大小写也是"对不上" —— 而 bundle id 那一处差异，症状是"商品取不到"。**
    IAP 商品只在「运行的 app 的 bundle id」与「ASC 里承载该商品的 app 的 bundle id」
    **完全一致**时才被返回。Apple TN3186 把这条列为商品取不到的**第一条原因** ——
    而"完全一致"是**逐字符**的，包含大小写：`com.tango.Marquee` 与 `com.tango.marquee`
    在 StoreKit 眼里是两个 app。

    ⇒ 危险的地方在于**能改的那一侧只有代码**：App ID（Identifiers）的 bundle id
    建了就不能改（只能删了重建），ASC 的 app 记录一旦创建也换不了 id。
    于是发现不一致时，改代码的代价是**一整套身份跟着换**：

    | 连带 | 后果 |
    | --- | --- |
    | TCC（屏幕录制授权） | 按 bundle id 记账 ⇒ 要重新授权一次 |
    | UserDefaults 的域 | 就是 bundle id ⇒ 偏好与权益缓存全"回到默认" |
    | 数据根目录 | `~/Library/Application Support/<id>/` ⇒ 老数据留在原地 |

    > 所以：**注册 App ID 之前先把工程里的 id 逐字符核一遍**（含大小写）。
    > 这次侥幸在"两个商品还没在 ASC 里建"的时候发现 —— 商品 id 也得跟着改
    > （有一条断言要求它们以正式 id 作前缀），而商品 id 一旦建了就是孤儿。

    > 顺带：`docs/DEV-VS-PROD.md` §7 有一条 2026-10-04 的日期注记下了这次改动，
    > 而 §7 与 §9 的正文**保持当时的样子** —— 实施记录改写之后就不再是记录了。

183. **设计稿的「描述」与「数据」会互相矛盾 —— 尺子以数据为准。**
    稿子 ⑩ §06 给钉图写的是「视觉边界 x 4.15–11.85 · y 1.65–14.15 —— **横竖向都居中**」。
    把它写成断言的第一版就红了：x 的上下余量是 4.15 / 4.15（居中），
    而 y 是 **1.65 / 1.85** —— 差 0.2 格。**那句话与它自己给的路径对不上。**

    ⇒ 实现时选**路径数据**（`circle 8 4.8 r2.4` + 两条折线），因为那是它真正画出来的东西；
    描述是给人读的，而数值是给机器执行的，**前者更容易先写错、也更不容易被发现**。

    ⚠️ 但**别把那条断言删掉**，要把它改成"记录这个差值"的形状
    （`abs(diff) < 0.25`，附一句"稿子的路径值是 0.2"）。理由：
    将来有人拿"居中"当依据去挪这枚图形时，删掉的那条不会响，
    而**留下一条宽松的反而会**（挪完余量就超了）—— 顺便还可能撞上下一条断言（锁位）。
    **一条搬得动的依据比没有依据更危险。**

184. **辅助功能开关不能拿"另一种半透明"去答。**
    稿子 ⑩ §07 有一条规则：「**「降低透明度」是回退开关**：一开，全部 `.glass`
    切回 `--c-panel` 不透明」。实装里这条**一条判断都没有** ——
    而更糟的是原来那两条材质路（`NSGlassEffectView` / `NSVisualEffectView(.hudWindow)`）
    **都半透明**：想省事把 `.hud` 当回退，等于对"我要减少透明"回答"给你换一种半透明"。
    开这个开关的人往往是最赔不起的那一类（低视力 / 高对比度）。

    ⇒ `ChromeMaterial` 加第三档 `.opaque`（实色 `--c-panel`）。
    ⚠️ **两条判据的顺序也是判据**：`reduceTransparency` 必须排在 `glassAvailable` 之前。
    写反了**只在 26+ 上发作**（15.x 上两条都落 hud/opaque，恰好也对）——
    于是它在开发机上看着挺好，在主流机型的用户那里是"这个开关没反应"。
    这种"错得很对称"的分支，值得为顺序单开一条测试。

185. **一枚图标换了来源之后，「唯一来源」的守卫要从「名字唯一」升级成「来源唯一」。**
    `AnnotationIcon` 一直靠一张「工具 → SF Symbol 名」的表来保证
    "同一功能同一图标"（编辑器那条验收第一条）。钉图改成自绘之后，
    如果那个函数仍然返回 `String`，钉图那一格就只能填一个占位字符串 ——
    **而占位字符串不会编译失败**，它只会在卡片上画出一枚和工具条不一样的钉图。

    ⇒ 引入 `AnnotationIcon.Icon`（`.symbol(String)` / `.glyph(AnnotationGlyph)`），
    并让**两个来源由同一个函数决定**。
    ⚠️ 配套加一条**边界断言**：除钉图外，任何能力的图标都必须是 `.symbol` ——
    否则"这次自绘一枚"很容易被顺手推广成"以后都自己画"，
    而那时"哪一枚来自哪里"就变成只有读实现才知道的事了。

186. **自绘一枚图形时，最危险的下一步是「顺手把别处也改掉」。**
    读数框改玻璃（稿子 ⑩ §07 的 `.rd`）时，同一个绘制函数还服务着**放大镜的色值框**。
    那一块**必须留成不透明**：它读的是被采样出来的像素，底就是那张放大图 ——
    做成玻璃等于让"这个色值读不读得出"取决于图上恰好有什么（稿子 §08 有原话）。

    ⇒ 两件事一起做：
    ① 把那个函数改名成带判据的名字（`drawOpaqueBox`）；
    ② 在调色板那边把令牌也改名（`Readout.opaqueBackdrop`），并留一条断言钉住它还是不透明的。
    **名字是这里唯一的守卫** —— 注释会被跳过，而"名字里写着 Opaque 却把它改透明"会让人停一下。

187. **玻璃材质任何离屏渲染都拍不到** —— 所以出图那条路一定会拍到「回退档」，
    而那张图看起来会像"忘了画底"。

    ① `NSVisualEffectView` / `NSGlassEffectView` 都要**真实窗口**才有东西可糊，

    ② 出图那条路落到回退档**是对的**，不是故障。别为了让 PNG 好看而去给渲染路径注入材质
       （那样只会得到一块"拍出来是空的"的视图，比实色更糟）。

    ⚠️ 顺带一条流程上的教训：这一条**第一版我写错了**（写成"PNG 上会少一块底色"），
    实际跑了一遍才发现底还在、只是换成了实色。
    **"我以为会怎样"必须用一次真实运行去换掉** —— 否则记进 PITFALLS 的就是一条假事实，
    而它会以"这是已知现象"的身份把下一个人的判断带偏。

188. **`CGWindowListCreateImage` 在 macOS 15+ 已经**不能用了** —— 抓屏只剩 ScreenCaptureKit 一条路。**
    想给玻璃拍张自证的图时，第一反应会是"抓**我自己**的窗口总不用授权吧"。
    **编译就过不去**：

    ```text
    error: 'CGWindowListCreateImage' is unavailable in macOS:
           Please use ScreenCaptureKit instead.
    ```

    ⇒ 也就是说"自己的窗口"这条豁免**根本没有出口**：SDK 把那个老 API 整个标成不可用，
    而 ScreenCaptureKit 一律要屏幕录制授权（TCC）。**没有任何"程序自己拍自己"的捷径。**

    这条要写下来，因为它把一件看起来能省事的事**关掉了**：
    下一个人（或下一个我）大概率会再想一次"抓自己的窗口不就行了"。
    结论是 **`-marqueeSmokeOverlayShot` 必须由人来点一次授权**，
    所以那条路的失败输出里**写清了怎么点** —— 而不是默默什么都不生成。

    > 顺带一条判据：`Marquee -marqueeDiagnostics` 会打印「屏幕录制权限」的真实状态
    >（`granted` / `notDetermined` / 进程内 denied）。**先看它再决定要不要跑需要权限的路径** ——
    > 免得把"没授权"误读成"功能坏了"。

189. **`open -a App --args <flag>` 会**静默丢参** —— 而被沙箱包裹的 shell 里，它 100% 丢。**
    症状极其像"这个开关根本没实现"：进程正常起来、正常进事件循环（`sample` 看到主线程
    空转在 `mach_msg`）、**一行输出都没有**、也不退出。

    本机实测（同一条命令，只换形式，全部失败）：

    | 写法 | 结果 |
    | --- | --- |
    | `open -a <路径> --args -flag` | ✗ |
    | `open <路径> --args -flag` | ✗ |
    | `open -b <bundleid> --args -flag` | ✗ |
    | `open -a Marquee --args -flag` | ✗ |
    | `open -n -a <路径> --args -flag` | ✗ |
    | **直接 exec 可执行文件** | ✓（但见下一条：TCC 会算到终端头上） |
    | `launchctl submit -l … -- <exe> -flag` | ✗（沙箱里静默不生效） |

    ⇒ 两条教训，**都要照做**：

    1. **加了命令行开关就顺手加一行"启动凭证"。** 这个应用现在只要 `arguments.count > 1`
       就落一份 `reports/launch-arguments.txt`。有了它，"参数没到"与"参数到了但分支没跑"
       **一眼分得开**；没有它，这两种情况在现象上一模一样。
       （这条我是先猜错方向才补上的：一开始怀疑权限、怀疑卡在启动序列，采样主线程才发现
       是参数压根没进来。）
    2. **要在"自己的终端"里跑 `open -a`**。它同时满足两件事：参数送得到 + TCC 把应用
       当成自己的 responsible process。少任何一件，这条路都不成立 ——
       而两件事各自失败时**都不报错**，只是什么都不发生。

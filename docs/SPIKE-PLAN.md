**三条最重要的结论**

1. **滚动截屏（原 R1，最高风险）已从"高风险"降为"已验证可行"**：合成数据下端到端拼接与真值**平均绝对误差 0.000/255**，且 Vision 平移配准给出**精确无误差**的位移。但自研 SAD 单次配准 258 ms 太慢 → 优先 Vision，见 D 组。
2. **全局快捷键不需要辅助功能权限**（Carbon `RegisterEventHotKey` 在未授权状态下注册成功），R4 消除；同时 `NSEvent` 全局监听强依赖输入监控权限，**不作为主方案**。
3. **Liquid Glass 是 macOS 26+ 的 AppKit API**，而最低系统定的是 15.0 → 所有玻璃效果必须包 `if #available`，且在 15.x 上要有材质降级方案。

### ⚠️ 顺带暴露的 3 个真实坑（已在验证过程中踩到并解决）

这三个不是"设计猜测"，是**实际写代码时踩出来的**，如果直接进 M4，每个都要花半天到一天排查：

| # | 坑 | 症状 | 正确做法 |
| --- | --- | --- | --- |
| K1 | **`CGBitmapContext` 内存行序 vs CG 用户坐标系** | 把位图"翻转为自上而下"后，帧间位移**符号被整体反转**，配准搜索永远找不到正位移，输出 788/753/658 之类的垃圾值 | `CGBitmapContext` 的内存行序**本就是自上而下**，不要再翻转；翻转是**相对各自图像高度**的镜像，会让裁剪块与整图方向不一致 |
| K2 | **用负坐标 rect 绘制取帧不可靠** | `ctx.draw(page, in: rect(origin.y = -8200))` 结果与预期不符 | 一律用 `CGImage.cropping(to:)`（图像坐标系原点在左上，语义明确）取帧 |
| K3 | **长图拼接的取行区间** | 拼接高度对了、但内容错位，MAE 75.78 | 新内容 = 本帧**顶部**的 d 行，即 `(viewH-d)..<viewH`，不是 `d..<viewH` |

> K1 的教训值得单列：这类 bug **不会崩、不会报错**，只是结果悄悄错。所以配准模块必须内置"装置自检"（用已知位移的合成图跑回归），否则线上出问题无从下手。

### D 组 · 滚动截屏（最高风险，**已全部自动验证通过**）

配置：长页 1200 × 9000 px，视口 800 px，真实步长 600 px（重叠 200 px）。

| ID | 验证项 | 结果 |
| --- | --- | --- |
| D0 | **装置自检**：确认取帧确实发生位移、内容非空 | ✅ PASS（帧差异 92760，非空像素 32.3%） |
| D1 | 整数滚动配准（朴素 SAD） | ✅ PASS `[600,600,600,600,600]` |
| D2 | 整数滚动配准（内容行加权 + 最小重叠 + 最小样本） | ✅ PASS `[600,600,600,600,600]`；单次配准 **258 ms** |
| D3 | **端到端拼接 vs 真值** | ✅ PASS **MAE 0.000/255**，拼接高度 3800 px = 真值 |
| D4 | 亚像素滚动（真实步长 600.5） | ✅ PASS：整数对齐最大误差 0.5 px → 抛物线精化后 **0.04 px** |
| D5 | 吸顶条 + 屏幕光标干扰（朴素） | ✅ PASS 抗干扰 |
| D6 | 吸顶条 + 屏幕光标（修正算法 / 排除顶部 70 px） | ✅ PASS 缓解有效 |
| D7 | 滚动到底检测（无位移） | ✅ PASS 位移 = 0，代价 0.000 → 可判定并停止 |
| D8 | Vision `VNTranslationalImageRegistrationRequest` 对照 | ✅ PASS **tx=-0.00, ty=600.00（精确无误差）** |

**D 组结论与实施建议**

1. **配准优先用 Vision**：`VNTranslationalImageRegistrationRequest` 在同样输入上给出精确值，而自研实现要处理内容稀疏性、最小重叠、亚像素等一堆细节。自研版本虽也正确，但 **258 ms/次** 的耗时不可接受（10 帧 = 2.6 秒卡顿）。
2. **待补测**：Vision 配准的**单次耗时**尚未测量 —— 若也在百毫秒级，则需降采样后再配准（先在 1/4 分辨率上求整数位移，再精化）。
3. **亚像素必须处理**：整数位移会累积 ±0.5 px 误差，长图越长错位越明显。做法：抛物线精化得到小数位移后，**按累计小数位移重新采样**，而不是简单向下取整。
4. **必须内置装置自检**：用"已知位移的合成图"做回归（本次正是靠它才发现 K1/K2/K3 三个坑）。这条写入 M3 的测试计划。
5. **仍需人工验证的真实场景**：浏览器长页、聊天记录、设置面板、含 sticky header 的列表页、滚动惯性未停即抓帧、动态内容（视频/GIF）。

### 补充发现 · Vision OCR 的真实成本

| 场景 | 耗时 |
| --- | --- |
| **首次调用（模型未缓存）** | **约 25 秒** |
| 模型缓存后冷启动 | 177 ms |
| 稳态（p50 / p95，900×260 px，accurate，中英双语） | **60 ms / 65 ms** |

→ 结论：**首次 OCR 必须后台预热**（应用启动时对 1×1 空图跑一次请求），否则用户第一次点 OCR 会以为死机。这条写入 M6 的实现要求。

## 6. 复现方式

```bash
cd Tools/Spikes
swiftc -O -swift-version 5 -o spikes main.swift

./spikes          # A/B/E/F/G 组基础探测（17 项）
./spikes scroll   # D 组滚动配准验证（含装置自检与方向诊断）
./spikes dump     # 导出 dump_page.png / dump_f0.png / dump_f600.png 用于目视核对
```

源码保留在 `Tools/Spikes/main.swift`（已从 `.scratch/` 迁出，与产品代码分离）。建议下一步把 `scroll` 子命令接成回归（防止 K1/K2/K3 类问题回归）。

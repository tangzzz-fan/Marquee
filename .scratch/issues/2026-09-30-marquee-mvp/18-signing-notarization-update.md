# 18: 打包签名公证与更新机制

**What to build:** 产出一个别人能直接下载安装、双击不会被 Gatekeeper 拦下来的 Marquee。同时具备版本更新能力，让后续版本能推送给已安装的用户。

**Blocked by:** 17

**Status:** 🟡 脚本与文档已就绪，待你用真证书跑一次（2026-10-01）

## 实现记录

- `scripts/package.sh`：七步（生成工程 → 归档 → Developer ID 导出 → **签名核验** →
  公证 → 装订 → 打 DMG 并对 DMG 本身再签再公证再装订）。每一步都单独判断成败，
  且**签名核验不过就停下** —— 公证必被拒，而拒信要等几分钟才回来。
- `docs/RELEASE.md`：一次性准备（证书 / 公证凭据 / 沙箱开关）、七步各自失败时看什么、
  验收步骤、版本与更新策略、待填的数字。

### 更新机制：选"手动更新"，并且说明白为什么

验收项允许"或至少给出清晰的手动更新指引"。选它是因为：自动更新要引入 Sparkle 之类，
会带来**第二个需要签名的可执行文件**、一套 appcast 签名密钥、以及"更新器自身被替换"
这类安全面 —— 那不是这一轮该背的。文档里同时写了"以后要做自动更新"的最小形态
（先做提示、不做静默替换）。

### ⚠️ 我没法替你跑这一步

出包需要你的 Developer ID 证书与公证凭据。**请在有证书的机器上跑一次
`./scripts/package.sh`**，把输出贴回来 —— 特别是第 4 步（签名核验）与第 6 步（装订）。
本机缺证书时脚本会在第 0 步就报错并告诉你去哪补。

## Acceptance criteria

## 设计约束（已定）

- 走 **Developer ID 公证分发**，**不上 Mac App Store**（沙盒会约束滚动截屏等系统级能力）
- 需要 `com.apple.security.device.audio-input` 等权限时明确列出，但不申请不必要的受限权限
- 首次启动不应有引导弹窗（保持"零弹窗打扰"原则），但权限申请必须是清晰的

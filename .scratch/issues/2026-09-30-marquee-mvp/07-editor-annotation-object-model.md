# 07: 编辑器与标注对象模型

**What to build:** 截完图后进入编辑器：画布上是刚截的图，工具栏有矩形与椭圆。画一个矩形，然后**能再用鼠标选中它**，拖动改位置、拖角改大小、换颜色、改线宽；`⌘Z` 逐级撤销，`⇧⌘Z` 重做；按 `Esc` 把标注栅格化后的成品复制到剪贴板并关闭编辑器。

这条 ticket 的核心不是"能画矩形"，而是**标注是对象而不是像素**——这是旧版 Snip 真正的手感优势，也是本项目相对系统截图的核心差异。对象模型做浅了后面就补不回来了。

**Blocked by:** 03

**Status:** 已实现，待人工验收（2026-10-01）

截图确认后，原图已经在剪贴板里，同时打开编辑器。编辑器里 `Esc` 把标注栅格化后再写回剪贴板并关闭。裁切的**界面**在 ticket 09；撤销栈里已经有裁切命令，用来保住「标注 → 裁切 → 再标注」的交错语义。

## 设计约束（已定）

- 画布渲染用 **SwiftUI `Canvas`**。实测依据：真实标注量级（几十个对象）下 Canvas 0.08 ms/帧，比 Metal 更快（Metal 有固定提交流水线开销）；详见 `docs/RENDER-BENCH.md`
- 渲染入口收敛为一个协议（如 `CanvasRendering`），为将来可能的 Metal 实现留边界，但**首期不实现 Metal**
- 标注一律以**对象**存储，**导出时才栅格化**；不要画进一张位图了事
- 撤销用命令模式，必须支持"标注 → 裁切 → 再标注"的交错撤销语义
- 文字输入用 AppKit/SwiftUI 文本框作为 overlay，Canvas 只负责绘制已落定的文字
- 排除选用 CG 位图来回重绘做交互（实测 2400 图元 252 ms，是性能陷阱）

## Acceptance criteria

### 自动化已验证

- [x] 命中测试：上层对象先中；椭圆包围盒的角点不中，会落到后面的矩形；同层以后画的为准；已选中对象的角点优先于对象本身
- [x] 画矩形后可拖动、拖角、改色、改线宽，每一步撤销只退一件
- [x] `⇧` 多选后一起移动、一起改色；`Delete` 一起删除，撤销后顺序还在
- [x] 「标注 → 裁切 → 再标注」逐级撤销，再重做回到原样
- [x] 导出尺寸等于裁切区；描边画进图里；裁切外的背景像素还在
- [x] 100 个标注栅格化最快一帧 < 4 ms（交互绘制走 SwiftUI Canvas，预算依据见 `docs/RENDER-BENCH.md`）
- [x] 缩放以锚点为中心，锚点下的图像像素不动

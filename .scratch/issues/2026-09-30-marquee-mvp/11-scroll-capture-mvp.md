# 11: 滚动截屏 MVP（手动滚动）

**What to build:** 选中一个可滚动区域后进入长截图模式：用户自己往下滚，Marquee 连续抓帧并在后台自动配准、拼接，滚到位按回车结束，得到一张无缝长图并在编辑器里打开。拼接失败时明确告知"这一帧没对齐"，而不是默默产出一张错位的图。

这是旧版 Snip 的另一张王牌，也是全项目技术风险最高的一条。**先做手动滚动**：把配准与拼接的正确性拿下来，再考虑自动滚动（12）。

**Blocked by:** 04, 07

**Status:** 已实现，待人工验收（2026-10-01）

## 入口与键位（已定）

菜单栏新增 **「滚动截屏」**（PRD 3.1 的 6 项里本就有它，加完正好 6 项，到上限了）。

| 操作 | 行为 |
| --- | --- |
| 拖出区域 | **立即开始抓帧**（长截图不需要"停住再确认"） |
| 单击窗口 | 以该窗 frame 为区域开始抓帧（旧版 Snip 也是"选定窗口后自动拼"） |
| `⏎`（没划区域） | 以指针所在整屏为区域开始抓帧 |
| 滚动中 `⏎` | 结束 → 长图进剪贴板并打开编辑器 |
| 滚动中 `⌘S` | 结束 → 剪贴板 + 按模板落盘 |
| `Esc` | 取消（丢弃） |

抓帧期间面板设 `ignoresMouseEvents = true`，**滚轮穿透给下面的应用** ——
否则覆盖层会把滚轮吃掉，用户根本滚不动。键盘仍回到本面板（`⏎`/`Esc` 照常）。
代价：此时若用户点了别的应用导致面板失去 key 焦点，`⏎`/`Esc` 会失效（已知限制）。

## 已提前验证的结论（直接用，不要重新试）

- 配准**优先用 Vision** `VNTranslationalImageRegistrationRequest`。合成数据实测给出精确无误差位移；自研 SAD 虽然也正确，但**258 ms/次太慢**
- 配准前若耗时超标，先在 1/4 分辨率上求整数位移再精化
- **亚像素必须处理**：整数位移会累积 ±0.5 px 误差，长图越长错位越明显。用抛物线精化得到小数位移后，按**累计小数位移重新采样**
- **取帧用 `CGImage.cropping(to:)`**，不要用负坐标 rect 调 `ctx.draw`
- **`CGBitmapContext` 的内存行序本就是自上而下**，不要再做一次"翻转到自上而下"——那是相对各自图像高度的镜像，会让帧间位移**符号反转**，配准静默出错
- **拼接时新内容 = 本帧顶部的 d 行**，即 `(viewH-d)..<viewH`
- 以上三条都来自实际踩坑，详见 `docs/SPIKE-PLAN.md` 的 K1/K2/K3

## 本次新增的三条已实测结论（2026-10-01，改动前先看）

1. **`rows = +ty`，不要取负。** `targetedCGImage:` 给**上一帧**、handler 跑**当前帧**时，
   Vision 的 `ty` 就是"自顶向下滚了多少行"。按"Vision 原点在左下"去取负的后果是
   每一帧都被判成"没动"，长图永远只有一屏 —— 不崩不报错，只是没有内容。
   由 `VisionScrollRegistrarTests` 的符号断言钉住。
2. **画图时不要翻转 CTM。** 翻转后 `draw(image, in: rect)` 仍把图像顶行放在 `rect.maxY`，
   而翻转后 `rect.maxY` 已是视觉上的下边 → **整张图上下颠倒**。
   实测：自上而下 10/20/30/40 的四行图落在第 2 行，翻转得 `40,30,20,10`，不翻转才对。
   顺带发现 `AnnotationRasterizer`（ticket 07）踩的是同一个坑，已修并补了回归测试。
3. **长图总高取 `floor`、每片底边也取 `floor`。** 取 `ceil` 会多出一行"只覆盖了一半"
   的行，谁都不完整覆盖它 → 长图上留下一条**半透明横线**。

## Acceptance criteria

- [x] 选中区域后进入长截图模式，有明确的"滚动中 / 结束 / 取消"提示（HUD 三行：进度 / 告警 / 操作）
- [x] 抓帧与配准不阻塞主线程（`register` 是 nonisolated async，实际跑在通用执行器上）
- [x] 回车结束后得到长图，在编辑器中打开，可继续标注与导出
- [ ] 对浏览器长页面、聊天记录、设置面板三类场景，拼接结果**无可见错位**（人工）
- [x] 检测到"已经滚到底"时停止追加，不产生重复内容（连续 3 帧判定"没动" → `atBottom`）
- [x] 配准置信度不足（页面几乎没动、或帧间完全不匹配、横向漂移过大）时明确提示而非产出错图；
      已拼好的部分**保留可用**，不因为一帧失手丢掉整次长截图
- [x] **装置自检回归**：合成长页 + 真实 Vision，整数步长端到端 **MAE 0.0**（阈值 < 1/255），
      已进常规测试集（`Modules/Tests/MarqueeCaptureTests/`）
- [x] 实测记录：**单次配准 8.3 ms**（首次调用 68 ms 是一次性开销）、**5 帧拼接 1 ms**、480×600 帧、输出 480×2200 px

## 收尾时要一起看的风险

- 抓帧期间面板失去 key 焦点后 `⏎`/`Esc` 失效（无全局键盘监听，因为那要输入监控权限）
- 拼接在 `finish()` 里同步做（观测 1 ms/5 帧）。长图逼近 `maximumCanvasHeight`（40000 px）时
  这一步会明显变长，属于**已知未测**项

## 「滚到底」的判定语义（2026-10-01 修正）

**踩到的 bug**：一进长截图、用户还没开始滚，约 1 秒后（3 帧 × 0.35 s）就报"已经滚到底了"。

根因是判定里少了前提：**"没动" 只有在"真的滚过"之后才能解读成"到底了"**；
在那之前它只意味着"还没开始"。

现在：
- 还没拼进任何内容时，连续静止**不报警**（`hasAppendedContent == false`）
- 滚过之后连续 3 帧静止 → 提示"看起来已经滚到底了"，措辞明确是**看起来**
- `atBottom` **不再停止抓帧**（`Phase.isAcceptingFrames` 把它算作可接收）：
  用户接着滚就能继续拼，回去 `capturing` 并清掉告警

第三条尤其重要：把"误判到底"做成**终局**比误报本身更糟 ——
抓帧循环一停，用户再往下滚就彻底没反应，长图还会缺掉后半段。
判定阈值因此改名为 `stationaryFramesBeforeBottomHint`（原来叫 `...beforeStop`，名副其实是停）。
